🗺️ Abstraction
Chỉ: đường · địa điểm · khoảng cách
Nguyên tắc
Abstraction phụ thuộc vào người dùng và mục đích. Cùng 1 thành phố nhưng: tài xế cần đường đi, kiến trúc sư cần cấu trúc, cứu hỏa cần vị trí hydrant. Mỗi abstraction phục vụ 1 mục đích.
💻 Abstraction trong code
❌ Không abstraction
openSocket(host, 587)
auth(user, pass)
helo(domain)
rcptTo(email)
data(content)
quit()
// 6 bước chỉ để gửi email!
✅ Có abstraction
sendEmail({
  to: 'user@mail.com',
  subject: 'Hello',
  body: 'Welcome!'
})
// Người dùng không cần biết SMTP
🏗️ Abstraction theo tầng — Click để xem từng layer
Mọi hệ thống có nhiều tầng abstraction. Người dùng mỗi tầng chỉ cần biết tầng ngay dưới.
🧑‍💻 Application Code — sendEmail(to, subject, body)
Lập trình viên dùng hàm sendEmail. Không cần biết gì về SMTP hay mạng.
📬 Email Library — SMTP client, retry, auth
Library xử lý SMTP protocol, retry khi gặp lỗi, authentication. Không cần biết về TCP/IP.
🌐 OS Network Stack — TCP/IP, sockets, TLS
OS quản lý TCP connection, TLS handshake, packet routing. Không biết về physical hardware.
⚡ Hardware — NIC, cables, signals
Card mạng chuyển đổi bits thành tín hiệu điện/quang. Đây là "thực tế" cuối cùng.
❓ 3 câu hỏi để thiết kế abstraction tốt
1. Người dùng cần biết điều này không?
Nếu không cần → ẩn đi. Ví dụ: người gọi saveUser() không cần biết transaction logic.
2. Interface này có thể thay thế implementation không?
Abstraction tốt: swap MySQL sang MongoDB mà không đổi caller code. Abstraction tệ: caller biết quá nhiều về implementation.
3. Abstraction này có "rò rỉ" không?
Leaky abstraction: file.read() có thể throw DiskFragmentedException → bạn phải biết về disk internals. Đây là abstraction tệ.
🎯 Key Takeaway
  • Ẩn đi chi tiết phức tạp, chỉ lộ interface cần thiết — "program to interface, not implementation"
  • Abstraction giúp code dễ đọc, dễ dùng, dễ thay thế (swap implementation không ảnh hưởng caller)
  • Câu hỏi hay: "Người dùng hàm này có cần biết điều này không?" — Nếu không → ẩn đi

🏋️ Mini Exercises

Ex 1 Mô tả "xe hơi" với abstraction khác nhau cho 3 đối tượng 🟡 Trung bình ▶
Abstraction phụ thuộc vào người dùng. Hãy thiết kế interface (TypeScript) cho "xe hơi" cho 3 đối tượng khác nhau:

A. Tài xế Grab — chỉ quan tâm đến vận hành
B. Thợ sửa xe — quan tâm đến kỹ thuật
C. Hệ thống ETC (thu phí) — chỉ cần định danh + thanh toán
💡 Gợi ý: Mỗi đối tượng chỉ cần thuộc tính phục vụ công việc của họ. Bỏ mọi thứ không liên quan.
// A. Tài xế Grab interface DriverView { fuelLevel: number // 0-100% gps: Location passenger: Passenger | null startTrip(): void endTrip(): TripSummary } // B. Thợ sửa xe interface MechanicView { engineCode: string oilLevel: number diagnosticCodes: string[] lastServiceDate: Date runDiagnostic(): DiagReport } // C. Hệ thống ETC interface ETCView { licensePlate: string rfidTag: string vehicleClass: 'car' | 'truck' | 'bus' charge(amount: number): Receipt }

Cùng 1 vật thể nhưng 3 interface hoàn toàn khác nhau. Đây là sức mạnh của abstraction!

Ex 2 Nhận diện "leaky abstraction" trong code 🟡 Trung bình ▶
Hàm sau có "leaky abstraction" — caller phải biết về implementation detail. Hãy xác định vấn đề và đề xuất cách fix:

async function getUserById(id: string): Promise<User> {
// có thể throw: MongooseError, CastError, ValidationError
return User.findById(id).lean()
}
💡 Gợi ý: Caller của getUserById có nên biết về Mongoose, MongoDB, hay CastError không?
Vấn đề: Caller phải catch MongooseError, CastError — đây là MongoDB implementation details. Nếu sau này đổi sang PostgreSQL thì tất cả catch blocks của caller phải sửa.

Fix — abstract lại errors:
class UserNotFoundError extends Error {} class InvalidUserIdError extends Error {} async function getUserById(id: string): Promise<User> { try { const user = await User.findById(id).lean() if (!user) throw new UserNotFoundError() return user } catch (e) { if (e instanceof CastError) throw new InvalidUserIdError() throw e // re-throw unknown errors } }
Giờ caller chỉ cần biết UserNotFoundError và InvalidUserIdError — không phụ thuộc Mongoose.
