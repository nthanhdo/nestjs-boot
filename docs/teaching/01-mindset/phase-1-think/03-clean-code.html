Khái niệm 01
Đặt Tên Có Ý Nghĩa
"Code được đọc nhiều hơn viết." Tên biến, hàm, class phải tự giải thích mà không cần comment. Liên quan chặt chẽ với abstraction → Bài 2.
❌ Tên xấu
let d = 86400
let tmp = getList()
function proc(l) {
  return l.filter(i =>
    i.f === 1)
}
✅ Tên tốt
const SECONDS_PER_DAY = 86400
const activeUsers = getUsers()
function filterActive(users) {
  return users.filter(user =>
    user.isActive === true)
}
📋 Quy tắc đặt tên
✅ BIẾN — noun phrase
elapsedTimeInDays
userAccountBalance
isEmailVerified
MAX_RETRY_COUNT
✅ HÀM — verb phrase
getUserById()
sendWelcomeEmail()
calculateMonthlyFee()
isValidEmail()
🎯 Key Takeaway
  • Nếu cần comment để giải thích tên → tên đó cần đổi
  • Tránh: d, tmp, data, info, manager, processor (quá mơ hồ)
  • Boolean: is/has/can prefix (isActive, hasPermission, canEdit)
Khái niệm 02
Hàm Nhỏ
Hàm lý tưởng đủ nhỏ để thấy toàn bộ trên màn hình. Đây là áp dụng của SRP từ bài 2 vào thực tế. Khi hàm làm nhiều việc → tách ra.
❌ processUserRegistration() — 100 dòng
Validate input + Hash password + Save DB + Send email + Create session + Log event + Notify admin...
✅ 5 hàm nhỏ, mỗi hàm 15-20 dòng
validateInput()
hashPassword()
saveUser()
sendEmail()
createSession()
Rule of Thumb
Nếu bạn cần scroll để đọc hết 1 hàm → hàm đó quá dài. Nếu bạn cần comment "// Step 1:", "// Step 2:" trong 1 hàm → đó là dấu hiệu cần tách hàm.
🎯 Key Takeaway
  • Hàm nhỏ → dễ đọc, dễ test, dễ tái sử dụng, dễ debug
  • Mỗi hàm chỉ làm 1 việc ở 1 level abstraction
  • Extract method là refactoring an toàn nhất để học
Khái niệm 03
DRY · KISS · YAGNI
Ba nguyên tắc cốt lõi giúp code không bị "thối" theo thời gian. Kết hợp với abstraction levels → Bài 2.
🔁 DRY — Don't Repeat Yourself
❌ Lặp code
// Ở User service
email = email.trim()
        .toLowerCase()

// Ở Auth service
email = email.trim()
        .toLowerCase()
✅ Extract
function normalizeEmail(e) {
  return e.trim().toLowerCase()
}

// Dùng ở mọi nơi
normalizeEmail(email)
💎 KISS — Keep It Simple, Stupid
❌ Over-engineered
class AbstractUserFactory
extends BaseEntityBuilder
implements ICreatable {
  createFromStrategy()
  ...
}
✅ Đủ đơn giản
function createUser(data) {
  return { ...data,
    id: uuid(),
    createdAt: new Date()
  }
}
🚫 YAGNI — You Aren't Gonna Need It
❌ Anti-pattern
"Tôi sẽ thêm multi-tenancy ngay từ đầu... thêm caching layer... thêm plugin system..." → Tốn 3 tuần cho tính năng mà chưa ai cần.
✅ Build when needed
Ship MVP → nhận feedback → refactor → thêm tính năng thực sự được yêu cầu.
🎯 Key Takeaway
  • DRY: mỗi piece of knowledge có 1 nơi duy nhất trong hệ thống
  • KISS: simple code làm đúng > clever code làm sai
  • YAGNI: đừng viết code cho tương lai tưởng tượng
Khái niệm 04
SOLID Principles
5 nguyên tắc OOP giúp code linh hoạt, dễ mở rộng, ít bug. Patterns trong bài 4 → sẽ hiện thị rõ SOLID trong thực tế. Click vào từng card.
S
Single Responsibility
Mỗi class chỉ có 1 lý do để thay đổi
// ❌ UserService làm quá nhiều
class UserService {
  getUser() { ... }
  sendEmail() { ... } ← sai chỗ
  generatePDF() { ... } ← sai chỗ
}

// ✅ Mỗi service 1 việc
UserService, MailService, PdfService
O
Open/Closed
Mở để mở rộng, đóng để sửa đổi
// Thêm shape mới không cần
// sửa code cũ
interface Shape {
  area(): number
}
class Circle implements Shape { }
class Square implements Shape { }
L
Liskov Substitution
Subclass thay thế được parent class
// Code dùng Bird phải hoạt động
// với mọi subclass của Bird
function makeFly(bird: Bird) {
  bird.fly() ← phải work
}
// Penguin extends Bird ← sai!
I
Interface Segregation
Nhiều interface nhỏ hơn 1 interface lớn
// ❌ 1 interface quá rộng
interface Worker { work(); eat(); sleep() }

// ✅ Tách nhỏ
interface Workable { work() }
interface Feedable { eat() }
D
Dependency Inversion
Depend on abstractions, not concretions. High-level không phụ thuộc low-level.
// ❌ Tight coupling
class OrderService {
  private db = new MySQLDatabase() ← bad
}

// ✅ Inject dependency
class OrderService {
  constructor(private db: IDatabase) {} ← good
}
🎯 Key Takeaway
  • SOLID không phải rules phải follow mọi lúc — đây là guidelines
  • Áp dụng khi thấy code khó test, khó thay đổi, hay break
  • Bắt đầu với S và D — 80% benefit từ 2 nguyên tắc này
Khái niệm 05
Code Smells
Code smells là dấu hiệu cảnh báo — code có thể chạy đúng nhưng có vấn đề về thiết kế. Click vào từng smell để nhận diện.
🔍 Tìm code smells trong đoạn code sau:
function doThings(a, b, c, d, e, f) {
  if (a === 1) {
    if (b === 2) {
      if (c === 3) { // Arrow code!
        if (d === 4) {
          result = process(e, f)
        }
      }
    }
  }
  const x = a * 0.1728
  return x
}
📦 Long Parameter List (6 params)
🏹 Arrow Code / Deeply Nested
🔮 Magic Number (0.1728)
🔁 Duplicate Code
💀 Dead Code
📝 Danh sách Code Smells phổ biến
Long Method — hàm > 30 dòng
God Class — class biết quá nhiều
Shotgun Surgery — 1 change → sửa nhiều nơi
Feature Envy — method dùng data class khác nhiều
Data Clumps — nhóm biến luôn đi cùng nhau
Comments — comment giải thích code xấu
🎯 Key Takeaway
  • Code smell ≠ bug, nhưng là tiền thân của bug
  • Khi thấy smell → không phải lúc nào cũng refactor ngay, nhưng ghi chú lại
  • Boy Scout Rule: "Leave the code cleaner than you found it"
Khái niệm 06
Refactoring từng bước
Refactoring = thay đổi cấu trúc code mà không thay đổi behavior. Click để xem từng bước.
❌ Code gốc — messy
function a(u) {
  if (!u.email || !u.email.includes('@')) return false
  if (!u.password || u.password.length < 8) return false
  db.save({ email: u.email.trim().toLowerCase(), password: hash(u.password), createdAt: new Date() })
  mail(u.email, 'Welcome!', '...')
  return true
}
🔨 Bước 1: Extract method
function isValidEmail(email) {
  return !!email && email.includes('@')
}
function isValidPassword(pw) {
  return !!pw && pw.length >= 8
}
function a(u) {
  if (!isValidEmail(u.email)) return false
  if (!isValidPassword(u.password)) return false
  ...
}
🏷️ Bước 2: Rename + Separate concerns
function registerUser(userData) {
  if (!isValidEmail(userData.email)) return false
  if (!isValidPassword(userData.password)) return false
  const user = buildUser(userData)
  db.save(user)
  sendWelcomeEmail(user.email)
  return true
}
✅ Final: Clean, readable, testable
// Mỗi hàm 1 việc, tên rõ ràng
async function registerUser(userData: CreateUserDto) {
  validateRegistrationData(userData)
  const user = await userService.create(userData)
  await mailService.sendWelcome(user)
  return user
}
🎯 Key Takeaway
  • Refactor thành từng bước nhỏ, test sau mỗi bước
  • Không refactor và thêm feature cùng lúc — nguy hiểm
  • Có test coverage trước khi refactor — safety net
Khái niệm 07
Technical Debt
Nợ kỹ thuật tích lũy theo thời gian. Giống như lãi suất ngân hàng — càng để lâu, càng tốn kém.
📉 Velocity giảm theo thời gian khi không refactor
💸 Deliberate Debt
Cố tình "nợ" để ship nhanh. Chấp nhận được nếu có kế hoạch trả nợ rõ ràng. "Cần ship trong 2 ngày, sau đó refactor sprint sau."
☠️ Reckless Debt
Không biết mình đang nợ. Không có kế hoạch. Accumulate mãi đến khi team không dám đụng vào code nữa.
🎯 Key Takeaway
  • Tech debt không phải xấu — là công cụ nếu quản lý có ý thức
  • Track tech debt: ghi vào backlog, schedule refactoring sprints
  • 20% thời gian sprint cho tech debt — đây là investment, không phải waste
🎯 Bài Tập Thực Hành
Áp dụng những gì vừa học vào code thực tế. Hoàn thành ít nhất 3/5 bài trước khi sang bài tiếp theo.
1
Đặt lại tên 10 biến/hàm xấu
🌺 Dễ ▼

Nhìn vào đoạn code dưới đây. Đặt lại tên cho tất cả các biến và hàm theo naming conventions đã học:

let x = 0
let tmp = []
let flag = false
function calc(n) { ... }
function proc(d) { ... }
function chk(e) { ... }
const mgr = new UserManager()
let dt = new Date()
const info = user.getData()
function handleClick(e) { return e.target.value }

Gợi ý: sử dụng noun phrases cho biến, verb phrases cho hàm, prefix is/has/can cho boolean.

Gợi ý đặt tên:

x → itemCount hoặc totalPrice (phụ thuộc context)
tmp → activeUsers hoặc filteredResults
flag → isProcessing hoặc hasError
calc(n) → calculateMonthlyFee(months)
proc(d) → processOrderData(orderData)
chk(e) → validateEmail(email)
mgr → userService (Manager là anti-pattern name)
dt → createdAt hoặc currentDate
info → userProfile hoặc userData
handleClick(e) → getInputValue(event) (tên nói rõ output)
2
Nhận diện 5 code smells
🌺 Dễ ▼

Đọc đoạn code dưới. Xác định các code smells hiện diện và đặt tên chúng:

class UserService {
  processUser(name, email, age, phone, address, zip, country, role, dept, mgr) {
    if (role === 'admin') {
      if (dept === 'IT') {
        if (age > 25) {
          // valid user
          db.save(...); db.save(...); db.save(...);
        }
      }
    }
    sendEmail(email, 'Welcome', '...') // Feature Envy?
    analytics.track(email) // ...
  }
}
5 Code Smells trong đoạn trên:

1. Long Parameter List — 10 params (name, email, age...). Fix: đóng gói thành CreateUserDto.
2. Arrow Code / Deeply Nested — if lồng 3 tầng. Fix: early return + extract conditions.
3. Duplicate Code — db.save() gọi 3 lần. Fix: tổng hợp lại.
4. God Method — 1 method làm quá nhiều (validate + save + email + analytics). Fix: tách methods.
5. Feature Envy — sendEmail và analytics.track thuộc service khác. Fix: di chuyển lọi logic.
3
Áp dụng SRP cho UserService vi phạm
🍑 Trung bình ▼

UserService dưới đây vi phạm SRP (Single Responsibility Principle). Hãy phân tích và tách thành các service riêng:

class UserService {
  createUser(data) { ... } // DB operation
  deleteUser(id) { ... } // DB operation
  sendWelcomeEmail(user) { ... } // Email
  sendResetEmail(email) { ... } // Email
  hashPassword(pw) { ... } // Security
  verifyPassword(pw, hash) { ... } // Security
  generateToken(user) { ... } // Auth
  validateToken(token) { ... } // Auth
  exportToPDF(users) { ... } // Report
  sendSlackNotif(msg) { ... } // Notif
}

Yêu cầu: (1) Phân nhóm theo responsibility, (2) Đặt tên các service mới, (3) Viết interface cho mỗi service.

Phân chia thành 5 services:

UserRepository: createUser, deleteUser (DB concerns)
MailService: sendWelcomeEmail, sendResetEmail (Email concerns)
PasswordService: hashPassword, verifyPassword (Security concerns)
AuthService: generateToken, validateToken (Auth concerns)
NotificationService: sendSlackNotif (Notif concerns)
ReportService: exportToPDF (Report concerns)

Mỗi service có 1 lý do duy nhất để thay đổi. Nếu thay email provider, chỉ sửa MailService.
4
Refactor từng bước: hàm 80-dòng messy
🍑 Trung bình ▼

Hàm processOrder() dưới đây dài 80 dòng và vi phạm nhiều nguyên tắc. Hãy liệt kê các bước refactor:

async function processOrder(uid, items, cc, addr, promo) {
  // Step 1: validate user
  const u = await db.query('SELECT * FROM users WHERE id=?', [uid])
  if (!u || !u.email || !u.isActive) return { err: 'invalid user' }
  // Step 2: validate items (50 lines of validation...)
  // Step 3: apply promo
  let total = items.reduce((s,i) => s + i.price, 0)
  if (promo === 'SAVE10') total *= 0.9
  if (promo === 'HALF') total *= 0.5
  // Step 4: charge card (20 lines...)
  // Step 5: save order, send email, log...
}

Phân tích: (1) Liệt kê tất cả "responsibilities" trong hàm, (2) Thứ tự áp dụng refactoring, (3) Viết pseudo-code cho version cuối.

Refactoring plan:

Bước 1 — Extract methods:
validateUser(uid), validateOrderItems(items), applyPromoCode(total, promo), chargeCard(cc, amount), saveOrderAndNotify(order, user)

Bước 2 — Magic number fix:
0.9 → PROMO_SAVE10_RATE = 0.9, 0.5 → PROMO_HALF_RATE = 0.5

Bước 3 — Final version:
processOrder chỉ còn ~10 dòng, gọi 5 hàm con — mỗi cái dễ test riêng.
5
Phân tích và lập kế hoạch xử lý Tech Debt
🔴 Khó ▼

Bạn vừa join một project và phát hiện danh sách vấn đề sau. Phân loại và lập kế hoạch xử lý:

1. AuthService.ts: 800-line file, mọi thứ trong 1 hàm
2. Không có tests nào cho payment flow
3. Magic strings rải rác: 'admin', 'user', 'moderator' ở 12 files
4. getUsers() gọi API 3 lần trong 1 request (duplicate call)
5. TODO comment từ 2 năm trước: "// Fix this later"
6. Database connection được hardcode trong 5 files
7. OrderService import trực tiếp MySQLAdapter (vi phạm DIP)

Yêu cầu: (1) Phân loại: P0 (critical), P1 (high), P2 (medium), (2) ước lượng effort, (3) Đề xuất thứ tự xử lý.

Phân loại và kế hoạch:

P0 — Critical (fix ngay):
• Item 6: Hardcode DB connection → security risk. Fix: env vars. 2h effort.
• Item 2: No payment tests → revenue risk. Fix: write unit + integration tests. 1-2 days.

P1 — High (sprint này):
• Item 4: Duplicate API call → performance. Fix: cache/memoize. 4h.
• Item 7: DIP violation → hard to swap DB. Fix: inject IDatabase interface. 4-8h.

P2 — Medium (backlog):
• Item 3: Magic strings → extract to enum UserRole. 2h.
• Item 1: God file → extract services. 1-2 days.
• Item 5: Old TODOs → investigate và close hoặc create proper issue.
