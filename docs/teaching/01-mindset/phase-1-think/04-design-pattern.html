Creational Patterns
Cách Tạo Objects
Kiểm soát quá trình khởi tạo objects — linh hoạt, có thể cấu hình, dễ thay thế. Thể hiện cụ thể của OCP và DIP → Bài 3.

Thay vì new Dog() hay new Cat(), bạn gọi AnimalFactory.create(type). Factory quyết định tạo loại nào.

❌ Không dùng khi

Singleton — Chỉ 1 instance duy nhất
Đảm bảo class chỉ có 1 instance và cung cấp global access point. Ví dụ: Logger, DB Connection Pool, Config.

Builder — Tạo object phức tạp từng bước
Tách construction của complex object khỏi representation. Tạo object có nhiều optional params một cách readable.
// ❌ Không có Builder
new HttpRequest('GET', '/api', null, {}, 30, true)

// ✅ Có Builder
new HttpRequestBuilder()
  .method('GET')
  .url('/api/users')
  .timeout(30)
  .withAuth()
  .build()
🎯 Key Takeaway
  • Factory: khi cần linh hoạt trong việc tạo objects
  • Singleton: dùng cẩn thận, tránh global state
  • Builder: khi object có nhiều optional configurations
Structural Patterns
Cấu Trúc Classes & Objects

Anti-Patterns
Khi Nào KHÔNG Dùng Patterns
Pattern áp dụng sai chỗ còn tệ hơn không có pattern. Over-engineering là vấn đề phổ biến nhất.
⚠️ Over-Engineering Trap
❌ Factory cho 1 loại object
Dùng Factory khi chỉ tạo UserObject → needless complexity
❌ Singleton cho mọi thứ
Global state = testability nightmare. NestJS DI đã handle việc này.
❌ Observer cho simple data flow
Gọi function trực tiếp rõ ràng hơn event chain khó trace.
❌ Builder cho 2-3 params
new User(email, name) đơn giản hơn UserBuilder().setEmail().build()
Rule of Three
Chỉ áp dụng pattern khi bạn thấy cùng vấn đề 3 lần. Lần đầu — giải thẳng. Lần hai — ghi chú. Lần ba — refactor với pattern.
🏆 Tổng kết Bài 04
  • Patterns = vocabulary — ngôn ngữ chung cho team thảo luận
  • Học pattern → hiểu vấn đề nó giải quyết, không chỉ code mẫu
  • Creational: Factory, Singleton, Builder
  • Structural: Adapter, Decorator, Facade
  • Behavioral: Strategy, Observer, Command
  • Anti-pattern: over-engineering > no pattern

1
Nhận diện pattern từ code snippet
🌺 Dễ ▼

Đọc các đoạn code dưới đây. Xác định tên pattern được sử dụng và giải thích tại sao:

// Snippet A
class Logger {
  private static instance: Logger
  static getInstance() {
    if (!Logger.instance) Logger.instance = new Logger()
    return Logger.instance
  }
}

// Snippet B
eventBus.on('order.paid', sendEmail)
eventBus.on('order.paid', updateInventory)
eventBus.emit('order.paid', order)

// Snippet C
const sorter = new Sorter(new QuickSortStrategy())
sorter.setStrategy(new MergeSortStrategy())
sorter.sort(data)
Đáp án:

Snippet A = Singleton. Dấu hiệu: private static instance + getInstance() kiểm tra trước khi tạo. Ếng dụng: Logger nên là Singleton.

Snippet B = Observer (EventEmitter). Dấu hiệu: nhiều subscribers đăng ký cùng event, publisher emit mà không biết ai nhận.

Snippet C = Strategy. Dấu hiệu: setStrategy() cho phép swap algorithm lúc runtime mà không thay đổi Sorter context.

Implement Factory cho NotificationService
🌺 Dễ ▼

Implement NotificationFactory tạo ra 3 loại notification: Email, SMS, Push. Tất cả implement chung interface INotifier:

interface INotifier {
  send(to: string, message: string): Promise<void>
}

// TODO: Implement EmailNotifier, SmsNotifier, PushNotifier
// TODO: Implement NotificationFactory.create(type: 'email'|'sms'|'push')

// Usage:
const notifier = NotificationFactory.create('email')
await notifier.send('user@example.com', 'Welcome!')

Bonus: Thêm fallback: nếu type không hợp lệ → throw UnsupportedNotifierError.

Gợi ý implementation:

class EmailNotifier implements INotifier { async send(to, msg) { /* sendgrid... */ } }
class SmsNotifier implements INotifier { async send(to, msg) { /* twilio... */ } }
class PushNotifier implements INotifier { async send(to, msg) { /* firebase... */ } }

class NotificationFactory {
  static create(type: string): INotifier {
    const map = { email: EmailNotifier, sms: SmsNotifier, push: PushNotifier }
    const Cls = map[type]
    if (!Cls) throw new UnsupportedNotifierError(type)
    return new Cls()
  }
}

Lưu ý: dùng object map thay vì if/else chain — dễ mở rộng (OCP).
3
Observer cho Shopping Cart
🍑 Trung bình ▼

Implement Observer pattern cho Shopping Cart. Khi user thêm item vào cart, 3 hành động phải xảy ra:

// Events cần handle khi addItem() gọi:
// 1. CartUI.update(cart) — re-render cart counter
// 2. Analytics.track('item_added', item) — analytics
// 3. RecommendationEngine.suggest(item) — gợi ý

class ShoppingCart {
  items: Item[] = []

  // TODO: implement subscribe/unsubscribe/notify
  addItem(item: Item) {
    this.items.push(item)
    // TODO: notify all observers
  }
}

Yêu cầu: (1) Tạo IObserver interface với method onCartUpdate(cart), (2) implement 3 observers trên, (3) Cart có thể subscribe/unsubscribe observer.

Gợi ý:

interface IObserver { onCartUpdate(cart: Cart): void }

class ShoppingCart {
  private observers: IObserver[] = []
  subscribe(obs: IObserver) { this.observers.push(obs) }
  unsubscribe(obs: IObserver) { this.observers = this.observers.filter(o => o !== obs) }
  private notify() { this.observers.forEach(o => o.onCartUpdate(this)) }
  addItem(item) { this.items.push(item); this.notify() }
}

Observers tự quản lý logic của mình — Cart không cần biết Analytics hay RecommendationEngine.
4
Strategy cho nhiều thuật toán sort
🍑 Trung bình ▼

Thiết kế DataSorter sử dụng Strategy pattern. Hệ thống có 3 strategy: BubbleSort, QuickSort, MergeSort. Runtime có thể swap:

// Expected usage:
const sorter = new DataSorter(new BubbleSortStrategy())
sorter.sort([3,1,4,1,5]) // dùng Bubble

// Khi dataset lớn → swap sang QuickSort
if (data.length > 10000) {
  sorter.setStrategy(new QuickSortStrategy())
}
sorter.sort(data) // dùng Quick

Challenge: Context code (DataSorter) không thay đổi khi thêm strategy mới. Đây là hiện thị OCP từ bài 3.

Gợi ý design:

interface ISortStrategy { sort(data: number[]): number[] }

class BubbleSortStrategy implements ISortStrategy { sort(data) { /* O(n²) impl */ } }
class QuickSortStrategy implements ISortStrategy { sort(data) { /* O(n log n) */ } }

class DataSorter {
  constructor(private strategy: ISortStrategy) {}
  setStrategy(s: ISortStrategy) { this.strategy = s }
  sort(data: number[]) { return this.strategy.sort(data) }
}

Thêm RadixSortStrategy sau? Chỉ thêm class mới, không sửa DataSorter — đúng OCP.
5
Kết hợp Decorator + Strategy cho Payment
🔴 Khó ▼

Thiết kế hệ thống Payment kết hợp 2 patterns:

  • Strategy: cho phép swap payment method (Credit Card, PayPal, Crypto)
  • Decorator: thêm layers mà không sửa class gốc (Logging, Retry, FraudCheck)
// Expected final usage:
const basePayment = new PaymentProcessor(new CreditCardStrategy())
const withLogging = new LoggingDecorator(basePayment)
const withRetry = new RetryDecorator(withLogging, maxRetries: 3)
const withFraud = new FraudCheckDecorator(withRetry)

await withFraud.process(amount, card)

Giải thích: tại sao đây là thiết kế tốt? Điều gì xảy ra nếu swap sang PayPal và bỏ Retry?

Phân tích thiết kế:

Tại sao tốt:
• Strategy cho phép swap payment method không ảnh hưởng Logging/Retry/Fraud.
• Decorator stack linh hoạt: có thể có FraudCheck mà không có Retry, hoặc ngược lại.
• Mỗi decorator có 1 trách nhiệm — đúng SRP.

Swap sang PayPal + bỏ Retry:
const base = new PaymentProcessor(new PayPalStrategy())
const withLogging = new LoggingDecorator(base)
const withFraud = new FraudCheckDecorator(withLogging)
→ Chỉ thay 2 dòng, không sửa bất kỳ class nào — đúng OCP.
