Tại sao cần Architecture?
Blueprint Trước Khi Xây
Không ai xây nhà mà không có bản thiết kế. Software cũng vậy — architecture là blueprint. Facade & Adapter (Bài 4) là building blocks cấu thành Architecture.
🏗️ Hậu quả của "code trước, nghĩ sau"
❌ Không có Architecture
  • • Code controller 2000 dòng
  • • Query SQL nằm trong View
  • • Business logic lẫn với UI
  • • Thêm 1 tính năng → sửa 10 file
  • • Không ai hiểu code của người khác
✅ Có Architecture
  • • Mỗi layer có trách nhiệm rõ ràng
  • • Thêm tính năng → đúng chỗ
  • • Dễ test từng layer riêng lẻ
  • • Team mới onboard nhanh
  • • Có thể swap DB/Framework
Architecture = Quyết định sớm, impact lâu dài
Architecture là những quyết định khó thay đổi. Chọn sai từ đầu → refactor tốn kém.
🎯 Key Takeaway
  • Architecture = cấu trúc cấp cao của system
  • Quyết định architecture phải dựa trên constraints thực tế
  • Không có "perfect architecture" — chỉ có "appropriate architecture"
Pattern 01
Layered Architecture
Tổ chức code theo các tầng với trách nhiệm rõ ràng. Controller là Facade (Bài 4) che giấu Business Logic bên dưới.
📚 Click vào từng tầng để xem chi tiết
🖥️
Presentation Layer
Xử lý HTTP request/response, validation, serialization
Controllers, DTOs, Middleware, Guards
↓ chỉ gọi xuống
⚙️
Business Logic Layer
Rules nghiệp vụ, orchestration, domain logic
Services, Use Cases, Domain Objects
↓ chỉ gọi xuống
🗜️
Data Access Layer
Tương tác với database, external APIs, file system
Repositories, Entities, Migrations, ORMs
🎯 Key Takeaway
  • Dependency hướng xuống — không bao giờ hướng lên
  • Business logic KHÔNG biết về HTTP, Database cụ thể
  • Test Business layer mà không cần HTTP hay DB thật

Pattern 04
Clean Architecture
Vòng tròn đồng tâm — dependency chỉ hướng vào trong. Business logic ở trung tâm, không phụ thuộc vào framework hay DB.
⭕ Concentric Circles — Dependency Rule
Frameworks & Drivers
(Express, MongoDB, React)
Interface Adapters
(Controllers, Presenters)
Use Cases
Entities
Business
Rules
→ Dependencies chỉ hướng vào trong
The Dependency Rule
Code ở vòng ngoài biết về vòng trong. Code ở vòng trong KHÔNG BIẾT về vòng ngoài. Entities không biết về HTTP. Use Cases không biết về Database cụ thể.
🎯 Key Takeaway
  • Business logic ở center → độc lập hoàn toàn với framework
  • Có thể swap Express → Fastify, MongoDB → PostgreSQL mà không sửa business logic
  • Test business logic mà không cần start server hay connect DB
Pattern 05
Event-Driven Architecture
Components giao tiếp qua events thay vì gọi nhau trực tiếp. Observer pattern (Bài 4) là nền tảng của Event-Driven.
📡 Pub/Sub — Publisher không biết về Subscribers

📡 Event Bus
"order.created"

EmailService (sub)
Analytics (sub)
Inventory (sub)
OrderService không biết EmailService tồn tại. Thêm subscriber mới → không sửa OrderService. Perfect loose coupling.
✅ Strengths
  • • Loose coupling giữa services
  • • Dễ thêm subscriber mới
  • • Async — không block
  • • Audit trail tự nhiên
❌ Challenges
  • • Khó trace flow phức tạp
  • • Event ordering issues
  • • At-least-once delivery
  • • Debugging khó hơn
🎯 Key Takeaway
  • Dùng khi cần decouple producers và consumers
  • Side effects (email, analytics) → perfect use case cho events
  • Critical path (payment) → nên gọi trực tiếp, không qua event

Separation of Concerns — Always Apply
Bất kể chọn architecture nào, luôn tách riêng: What (business rules) vs How (implementation) vs When (orchestration) vs Where (infrastructure).
🏆 Tổng kết Bài 06
  • Layered: Presentation → Business → Data, đơn giản và phổ biến
  • Monolith: Phù hợp team nhỏ, bắt đầu nhanh
  • Microservices: Khi team lớn, domain rõ, cần scale độc lập
  • Clean Architecture: Business logic độc lập với framework/DB
  • Event-driven: Loose coupling, async side effects
  • Rule: bắt đầu đơn giản, refactor khi có vấn đề thực
🏋️ Bài tập thực hành
🌀 Dễ Ex 1: Identify architecture — nhận ra kiểu từ folder structure ▼
Folder: controllers/, services/, repositories/, entities/ — đây là pattern gì? Giải thích dependency flow.
Giải
→ Layered Architecture (3 tầng) controllers/ = Presentation Layer services/ = Business Logic Layer repositories/ = Data Access Layer entities/ = Domain Models (Data Layer) Dependency: Controller → Service → Repository → Entity (chỉ hướng xuống, không bao giờ ngược lại)
🌀 Dễ Ex 2: Vẽ dependency diagram — tìm circular dependency ▼
Dependencies: UserModule→OrderModule, OrderModule→PaymentModule, PaymentModule→UserModule, ProductModule→OrderModule. Tìm circular dependency và đề xuất fix.
Giải
Circular dependency: UserModule → OrderModule → PaymentModule → UserModule ^__________________________________| ProductModule → OrderModule: OK (không có vòng) Fix options: 1. Tách UserSharedModule chứa shared logic 2. Dùng forwardRef() trong NestJS 3. Emit event thay vì gọi trực tiếp (event-driven)
🌁 Trung bình Ex 3: Tách monolith — Shopping App → 3 modules (User, Product, Order) ▼
App hiện có tất cả trong 1 file app.ts (500 dòng). Thiết kế cách tách thành Modular Monolith với 3 modules. Xác định: boundaries, shared code, communication pattern.
Thiết kế
src/modules/ user/ ← User boundary user.module.ts user.service.ts ← createUser, getUser, authUser user.repository.ts product/ ← Product boundary product.module.ts product.service.ts ← listProducts, updateStock order/ ← Order (orchestrator) order.module.ts order.service.ts ← inject UserService + ProductService shared/ ← Shared utilities database.module.ts events.module.ts Communication: - Order → User/Product: Dependency Injection (sync) - Side effects: Event Bus (order.created → email, inventory)
🌁 Trung bình Ex 4: Event-driven — thiết kế flow Order → Payment → Notification ▼
Thiết kế event flow: User đặt hàng → thanh toán → email xác nhận + cập nhật inventory. Xác định events, publishers, subscribers, error handling.
Event flow
Events & Handlers: order.created → PaymentService.processPayment() payment.success → EmailService.sendConfirmation() → InventoryService.deductStock() payment.failed → OrderService.markFailed() → EmailService.sendFailureNotice() Error handling: - Retry 3x với exponential backoff - Dead Letter Queue cho unprocessable events - Compensating transaction: nếu stock đã trừ nhưng email fail → retry email (idempotent)
🔴 Khó Ex 5: Architecture Decision Record — Monolith vs Microservices cho startup 3 người ▼
Bạn là CTO startup 3 dev. Product: SaaS B2B, 100 users/tháng đầu. Viết Architecture Decision Record (ADR) đầy đủ cho lựa chọn architecture.
ADR-001
# ADR-001: Monolith vs Microservices ## Status: Accepted ## Context: - Team: 3 engineers (full-stack) - Timeline: MVP in 3 months - Users: 100 → target 10K year 1 - Budget: no dedicated DevOps ## Decision: Modular Monolith ## Rationale: + 3 devs không đủ bandwidth quản lý distributed system + 100 users không có scale problem + 1 container deploy, đơn giản + Debug nhanh (no distributed tracing needed) + Tách microservice SAU khi domain rõ ## Constraints added: - Module boundaries STRICT (no cross-module direct DB access) - Each module owns its DB tables - Communicate via Service injection or Events only ## Review trigger: - Team > 8 người - Traffic > 100K requests/day - Module release cycles diverge significantly
📋 Tóm tắt Bài 6 — Architecture
🏗Layered: Controller→Service→Repository, dependency 1 chiều xuống
🏰Monolith phù hợp team nhỏ; Microservices khi domain rõ + scale
⭕Clean Architecture: business logic trung tâm, không phụ thuộc framework
📡Event-driven: loose coupling, side effects qua pub/sub
🗼Decision dựa trên team size + scale yêu cầu thực tế
📋ADR: ghi lại quyết định và reasoning cho sau này review
