Layered Architecture

Phân tầng code theo trách nhiệm: Presentation nhận request → Business xử lý logic → Data truy cập storage. Mỗi tầng chỉ nói chuyện với tầng liền kề.

3 Tầng — Bấm để khám phá

🎨 Presentation Layer (Controller)
HTTP requests · Response formatting · Input validation · Auth check
Trách nhiệm: Nhận HTTP request, parse params/body, validate format, gọi Service, format response.

KHÔNG được: Chứa business logic, truy cập DB trực tiếp, biết cách data được lưu.

Ví dụ NestJS: @Controller(), @Get(), @Post(), DTO validation via class-validator.

class ProductController { getProduct(@Param('id') id) { return this.productService.findById(id); } }
⚙️ Business Logic Layer (Service)
Domain rules · Calculations · Orchestration · Validation logic
Trách nhiệm: Implement business rules, orchestrate multiple repositories, throw domain errors.

KHÔNG được: Biết HTTP exists (không import express/fastify), format response, truy cập DB trực tiếp.

Ví dụ: ProductService.findById() check exists, check permissions, log access, apply discount rules.

Key insight: Service phải có thể được gọi từ Controller, từ Queue Worker, từ CRON job — vì nó không biết caller là ai.
🗄️ Data Access Layer (Repository)
DB queries · ORM models · Cache · External APIs
Trách nhiệm: Truy cập data sources (DB, Redis, external API), abstract query logic.

KHÔNG được: Chứa business rules, biết format response.

Lợi ích: Swap MongoDB → PostgreSQL? Chỉ đổi Repository, Service & Controller không đổi.

Ví dụ: ProductRepository.findById(id) → Mongoose Product.findById(id).

Dependency Rule — Chỉ phụ thuộc xuống

✅ Đúng — dependencies xuống

Controller
↓ calls
Service
↓ calls
Repository

❌ Sai — dependency ngược

Controller
↓
Service
↑ calls back!
Controller 🔴

Code Example — NestJS 3 Layers

// Layer 1: Controller (Presentation) @Controller('products') export class ProductController { constructor(private service: ProductService) {} @Get(':id') findOne(@Param('id') id: string) { return this.service.findById(id); // không biết DB là gì } } // Layer 2: Service (Business Logic) export class ProductService { constructor(private repo: ProductRepository) {} async findById(id: string) { const product = await this.repo.findById(id); if (!product) throw new NotFoundException(); return this.applyDiscountRules(product); // business logic } } // Layer 3: Repository (Data Access) export class ProductRepository { findById(id: string) { return ProductModel.findById(id).lean(); // chỉ biết Mongoose } }

Common Violations — Nhận biết để tránh

  • ❌ Controller gọi trực tiếp Product.findById() (Mongoose) — bypass Service + Repository
  • ❌ Service import Request, Response từ express — Service không được biết HTTP exists
  • ❌ Repository chứa business logic như discount, permission check
  • ❌ Controller gọi 5-6 Services khác nhau và combine logic — Controller quá béo
  • ❌ Service gọi ngược lên Controller để "notify" — circular dependency
  • ✅ Fix: mỗi tầng chỉ gọi tầng ngay dưới nó. Logic phức tạp = Service orchestrating Repositories.

🛠 Bài tập — Layer Audit

  • 1Mở 1 controller bất kỳ. Đếm xem có bao nhiêu dòng "business logic" (if/else, calculation) không phải validation/formatting?
  • 2Trace 1 API endpoint từ Controller → Service → Repository. Vẽ sơ đồ 3 tầng, ghi rõ trách nhiệm từng bước.
  • 3Tìm 1 chỗ vi phạm trong code hiện tại (Controller gọi DB trực tiếp, hoặc Service biết HTTP). Refactor theo đúng layer.
  • 4Viết 1 Service method có thể được gọi từ cả Controller lẫn CRON job mà không thay đổi logic.

Key Takeaways

  • 3 tầng: Presentation (Controller) → Business (Service) → Data (Repository).
  • Dependency rule: chỉ phụ thuộc xuống. Không circular, không skip tầng.
  • Service không biết HTTP exists — có thể được gọi từ Controller, Queue, CRON, test.
  • Repository abstraction = swap DB mà không thay đổi Service/Controller.
  • Fat controller = anti-pattern. Business logic thuộc về Service.
