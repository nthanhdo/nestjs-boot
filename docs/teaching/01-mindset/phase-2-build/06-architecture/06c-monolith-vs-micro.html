Monolith vs Microservices

Microservices không tự nhiên tốt hơn Monolith. Amazon, Netflix bắt đầu từ Monolith. Câu hỏi đúng: bạn đang ở giai đoạn nào?

So sánh chi tiết

Tiêu chí 🏢 Monolith ⚡ Microservices

TestingDễ test end-to-endPhức tạp: contract tests, integration tests
Observability1 log file đơn giảnCần distributed tracing, centralized logging
Phù hợpStartup, <10 devs, MVPScale-up, >20 devs, domain rõ ràng

Rule: "Monolith first" — Martin Fowler. Refactor sang Micro khi đã hiểu domain.

Strangler Fig — Migration Pattern

Không "rewrite toàn bộ". Bóc tách service từng bước từ Monolith — như cây bóp chặt dần:

1
Identify bounded context
Tìm module nào có domain rõ ràng, ít coupling nhất. Ví dụ: Notification module.
2
Create new service alongside
Tạo notification-service riêng, chạy parallel với monolith. Không xóa code cũ.
3
Route traffic gradually
Dùng feature flag hoặc API gateway để route 1% → 10% → 50% → 100% sang service mới.
4
Remove old code
Khi 100% traffic trên service mới ổn định → xóa code cũ trong monolith. Lặp lại cho module tiếp theo.

🛠 Bài tập — Architecture Decision

  • 1Vẽ diagram kiến trúc hiện tại của project bạn đang làm. Monolith hay Microservices? Modular không?
  • 2List tất cả modules/features. Đánh dấu: module nào có "bounded context" rõ ràng (có thể tách service)?
  • 3Chọn 1 module để "strangler fig". Phác thảo: API contract mới, DB riêng, và migration plan 4 bước.
  • 4Tư duy: nếu bạn phải scale user-service ×10 trong khi product-service dùng ít resource — Monolith có làm được không? Cost là bao nhiêu?

Key Takeaways

  • "Monolith first" — hiểu domain trước, tách micro khi domain đã stable.
  • Microservices không free lunch: cần CI/CD mature, distributed tracing, contract testing.
  • Modular Monolith = best of both worlds cho team <10 người với domain không quá phức tạp.
  • Strangler Fig pattern: migrate từng phần, không rewrite toàn bộ — giảm rủi ro.
  • Decision driver: team size, domain complexity, độc lập deploy, scale requirements.
