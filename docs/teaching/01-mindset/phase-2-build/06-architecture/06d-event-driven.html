Event-Driven Architecture

Publisher phát event, không biết ai lắng nghe. Subscriber lắng nghe, không biết ai phát. Decoupling đạt mức tối đa — hệ thống mở rộng không cần đụng code cũ.

Pub/Sub Flow — Order Placed Event

Khi user đặt hàng, order-service publish event. Nhiều services lắng nghe và react độc lập:

🛍️ OrderService
→ publish →
ORDER_PLACED
→
📨 Message Broker
(Redis/RabbitMQ/Kafka)
📧 NotificationService → gửi email xác nhận
📦 InventoryService → trừ tồn kho
💰 AffiliateService → ghi nhận commission
📊 AnalyticsService → track conversion

OrderService không import NotificationService, InventoryService, hay AffiliateService. Thêm AnalyticsService? Chỉ cần subscribe — không sửa OrderService.

Synchronous vs Asynchronous

❌ Synchronous (direct call)
1. User places order
2. Save to DB
3. Gọi email service → đợi...
4. Email chậm → timeout?
5. Gọi inventory → đợi...
6. Total: 2-3 giây!

User đợi response trong khi order service làm việc không liên quan đến đặt hàng.

✅ Asynchronous (event)
1. User places order
2. Save to DB
3. Publish ORDER_PLACED ← 1ms
4. Return 201 Created ← ngay lập tức
... background: email, inventory, affiliate xử lý parallel

User nhận response ngay lập tức. Background jobs chạy parallel, không block nhau.

Code Example — NestJS EventEmitter

// Publisher — OrderService export class OrderService { constructor(private events: EventEmitter2) {} async placeOrder(dto: PlaceOrderDto) { const order = await this.orderRepo.create(dto); this.events.emit('order.placed', { orderId: order.id, ... }); return order; // không biết ai nhận event này } } // Subscriber — NotificationService export class NotificationService { @OnEvent('order.placed') async onOrderPlaced(payload: OrderPlacedEvent) { await this.sendConfirmationEmail(payload.orderId); } } // Subscriber — InventoryService (thêm mà không sửa OrderService) export class InventoryService { @OnEvent('order.placed') async onOrderPlaced(payload: OrderPlacedEvent) { await this.decrementStock(payload.items); } }

Common Event-Driven Patterns

📨 Pub/Sub

1 publisher → N subscribers. Loose coupling. Ví dụ: NestJS EventEmitter, Redis Pub/Sub.

📋 Message Queue

1 producer → 1 consumer. Guaranteed delivery. Ví dụ: BullMQ, RabbitMQ.

📡 Event Streaming

Persistent log, replay. N consumers tại offset khác nhau. Ví dụ: Kafka.

📖 Event Sourcing

State = sequence of events, không phải snapshot. Audit trail đầy đủ, rebuild từ events.

🔄 CQRS

Command (write) và Query (read) tách biệt. Read models optimized riêng.

🧩 Saga Pattern

Distributed transaction qua events. Compensation events khi fail.

Tradeoffs — Không phải silver bullet

✅ Lợi ích

  • • Loose coupling — thêm feature không sửa code cũ
  • • Non-blocking — response nhanh hơn
  • • Fault isolation — 1 subscriber fail không ảnh hưởng publisher
  • • Scale subscribers độc lập

⚠️ Chi phí

  • • Eventual consistency — data không ngay lập tức consistent
  • • Debug khó hơn — flow không linear
  • • Event schema phải backward compatible
  • • Infrastructure: message broker cần vận hành

🛠 Bài tập — Refactor to Events

  • 1Tìm 1 Service method đang gọi 3+ service khác trực tiếp (chaining). Đây là candidate tốt để chuyển sang events.
  • 2Cài @nestjs/event-emitter. Định nghĩa event class: class OrderPlacedEvent { orderId: string; items: [] }.
  • 3Refactor: publisher chỉ emit event sau khi save to DB. Subscribers xử lý async với @OnEvent().
  • 4Test: thêm 1 subscriber mới (ví dụ: log analytics) mà không sửa publisher. Verify nó hoạt động.
  • 5Đo thời gian response trước và sau refactor. Document sự khác biệt.

Key Takeaways

  • Event-Driven = Publisher phát event, không biết ai subscribe. Open/Closed Principle ở system level.
  • Async events → response nhanh hơn (không đợi side effects), scale độc lập.
  • Tradeoff: eventual consistency, flow khó debug, cần backward-compatible event schema.
  • NestJS EventEmitter cho in-process. BullMQ/Redis cho cross-service, guaranteed delivery.
  • Dùng events cho side effects (notification, audit, analytics) — không dùng cho critical synchronous flow.
