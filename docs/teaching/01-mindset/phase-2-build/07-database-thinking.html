Tại sao cần Database?
Vấn Đề Của File Storage
Lưu data vào file hoạt động tốt cho một người. Nhưng sẽ sụp đổ khi có nhiều người dùng cùng lúc. Đây chính là trade-off mà Computational Thinking (Bài 1) dạy bạn phân tích.
💥 File Storage gặp vấn đề gì?
❌ Race Condition
User A và B cùng đọc balance=1000. A trừ 200 → ghi 800. B trừ 300 → ghi 700. Balance đúng phải là 500!
❌ Search chậm
Tìm user theo email → phải đọc toàn bộ file. 1M records = đọc 1M dòng mỗi lần tìm.
❌ Integrity
Không có cách nào đảm bảo email là unique, hay quantity > 0.
❌ Crash recovery
Server crash giữa chừng khi đang ghi → file corrupt, data mất một phần.
Database giải quyết tất cả những vấn đề này
ACID Transactions, Indexes, Constraints, WAL (Write-Ahead Logging) — database là software phức tạp được build để handle những vấn đề này một cách reliable.
🎯 Key Takeaway
  • Database = file system + concurrency + search + integrity + recovery
  • Hiểu vấn đề nó giải quyết → mới hiểu tại sao ACID quan trọng
  • JSON file là DB đơn giản nhất — SQLite là bước tiếp theo

Khái niệm 02
Normalization
Chuẩn hóa database để tránh data trùng lặp và update anomalies.

Khái niệm 03
Index — Mục Lục Của Database
Index giống mục lục sách — thay vì đọc hết, bạn tra ngay vào trang cần. Đây là trade-off kinh điển: đánh đổi write speed và storage lấy read speed — trade-off analysis (Bài 1).
🔍 Tìm email trong 1 triệu records
❌ Không có Index
SELECT * FROM users
WHERE email = 'z@mail.com'
→ Full Table Scan: đọc 1,000,000 rows
→ Thời gian: ~500ms
✅ Có Index trên email
CREATE INDEX idx_email
ON users (email)
→ B-tree lookup: ~20 nodes
→ Thời gian: ~1ms
B-Tree Index — Simplified
m
f
s
a-e
g-l
n-r
z@…
Tìm 'z' → đi phải (>m) → đi phải (>s) → found! Chỉ 3 bước thay vì 1M bước.
Index Trade-off
Index tăng tốc READ nhưng làm chậm WRITE (phải cập nhật index khi insert/update). Đừng index mọi column — chỉ index những column thường được query/filter.
🎯 Key Takeaway
  • Luôn index FK columns (foreign keys)
  • Index columns thường xuất hiện trong WHERE, JOIN, ORDER BY
  • EXPLAIN ANALYZE để kiểm tra query có dùng index không
Khái niệm 04 + 05
ACID & N+1 Problem
ACID đảm bảo data integrity. N+1 là bug phổ biến nhất khi làm việc với DB trong code.
💸 ACID — Chuyển tiền A→B, server crash giữa chừng
⏳

📤
Trừ tài khoản A: 1,000,000 → 800,000
💥
SERVER CRASH! Chưa cộng được vào B
↩️
ROLLBACK! Tài khoản A phục hồi về 1,000,000. Không mất tiền!
A
Atomicity
Tất cả hoặc không gì

Rules luôn được giữ

Đã commit = không mất
⚠️ N+1 Query Problem
Lấy 100 orders, mỗi order gọi thêm 1 query để lấy user. Kết quả: 1 + 100 = 101 queries!
0
queries
✅ Fix: JOIN hoặc eager load
// 1 query thay vì N+1
SELECT o.*, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
→ 1 query, thay vì 101!
🎯 Key Takeaway
  • Dùng Transaction cho operations cần atomicity
  • N+1 hay xuất hiện khi dùng ORM + lazy loading
  • Detect N+1: đếm queries trong log, dùng query analyzer
Thực hành
Scale từ 100 → 10M Users
Mỗi level có challenges khác nhau. Click vào từng level để xem phải làm gì. Đây là bài toán trade-off điển hình từ Computational Thinking (Bài 1).
100 users
Simple setup
Single server, single DB. SQLite hoặc PostgreSQL. Không cần gì phức tạp. Tập trung vào features, không phải infra.
10K users
Add indexes + basic caching
Tạo index cho các queries chậm. Thêm Redis cache cho data ít thay đổi. Connection pooling. Bắt đầu monitor query performance.
1M users
Read replicas + CDN
Primary DB cho writes, Read Replicas cho reads (80-90% traffic thường là reads). CDN cho static assets. Horizontal scaling app servers. Queue cho heavy operations.
10M users
Sharding + Microservices
DB sharding theo user ID. Tách services theo domain. Message queues (Kafka). Distributed cache (Redis Cluster). Đây là "Google scale" — hầu hết app không cần đến đây.
Bài học quan trọng nhất
Đừng over-engineer ngay từ đầu. Xây cho 100 users trước. Khi có vấn đề ở 10K users — fix. Mỗi optimization tốn chi phí, đừng trả chi phí trước khi cần.

🏋️ Bài tập thực hành
🌀 Dễ Ex 1: ERD — vẽ Entity Relationship cho Library (Book, Member, Borrow) ▼
Xác định entities, attributes (với PK/FK), và relationships (1-to-many, many-to-many) cho hệ thống thư viện.
Giải
Entities: Book : id(PK), title, author, isbn(UNIQUE), quantity Member : id(PK), name, email(UNIQUE), joinDate Borrow : id(PK), bookId(FK), memberId(FK), borrowDate, dueDate, returnDate Relationships: Member 1 ---< N Borrow (1 member có nhiều lần mượn) Book 1 ---< N Borrow (1 book bị mượn nhiều lần) → Borrow là junction table cho M:N giữa Member và Book Business rules: - dueDate = borrowDate + 14 days (default) - returnDate NULL = chưa trả - quantity phải > 0 mới cho mượn
🌀 Dễ Ex 2: Normalization — đưa bảng từ 1NF lên 3NF ▼
Bảng gốc: Orders(order_id, customer_name, customer_city, customer_zip, product_name, product_category, qty). Đưa lên 3NF.
Giải — 3NF
1NF: đã atomic (mỗi cell 1 giá trị) 2NF → tách partial dependencies: Customers(id, name, city, zip) Products(id, name, category) Orders(id, customer_id FK, created_at) OrderItems(id, order_id FK, product_id FK, qty) 3NF → tách transitive dependencies: city phụ thuộc vào zip (transitive) → tách ra: ZipCodes(zip PK, city, state) Customers(id, name, zip FK) Result: 5 bảng, không có data nào lặp lại
🌁 Trung bình Ex 3: Index — xác định nên đặt index ở đâu cho 5 query patterns ▼
Cho bảng Orders(id, user_id, status, total, created_at, product_id). Quyết định index cho 5 queries sau.
Giải
Q1: WHERE user_id = ? → INDEX ON user_id (FK luôn index) Q2: WHERE status = 'pending' ORDER BY created_at DESC → COMPOSITE INDEX ON (status, created_at DESC) Q3: WHERE created_at BETWEEN ? AND ? → INDEX ON created_at Q4: WHERE user_id = ? AND status = ? → COMPOSITE INDEX ON (user_id, status) (đặt cột selectivity cao hơn trước) Q5: SELECT COUNT(*) FROM orders WHERE product_id = ? → INDEX ON product_id KHÔNG index: total (range query ít dùng), id (PK đã có index tự động)
🌁 Trung bình Ex 4: N+1 Query — detect và fix trong code MongoDB ▼
Đọc code dưới đây và xác định N+1 problem, sau đó fix bằng populate() hoặc aggregation.
Vấn đề + Giải
// BUG: N+1 problem const orders = await Order.find({}); // 1 query for (const order of orders) { order.user = await User.findById(order.userId); // N queries! } // → 1 + N queries nếu có N orders // FIX 1: Mongoose populate (2 queries total) const orders = await Order.find({}) .populate('userId', 'name email'); // FIX 2: Aggregation $lookup (1 query) const orders = await Order.aggregate([ { $lookup: { from: 'users', localField: 'userId', foreignField: '_id', as: 'user' } }, { $unwind: '$user' } ]);
🔴 Khó Ex 5: Scale — thiết kế DB cho 100 → 10K → 1M users, giải thích thay đổi ▼
Bạn build Twitter clone. Thiết kế database strategy cho 3 giai đoạn: 100 users (MVP), 10K users (traction), 1M users (growth). Giải thích từng thay đổi và tại sao.
Scale Plan
Phase 1 — 100 users (MVP): PostgreSQL single server Tables: users, tweets, follows, likes No special indexes (premature optimization) Heroku free tier Phase 2 — 10K users (traction): Add indexes: - tweets.user_id (FK) - tweets.created_at DESC (timeline query) - follows.(follower_id, following_id) UNIQUE Redis cache: home timeline (cache invalidate on tweet) Connection pooling: PgBouncer Move to dedicated DB server Phase 3 — 1M users (growth): Read Replicas: 1 primary write, 2+ read replicas Timeline fanout: pre-compute on write → cache user's timeline in Redis on tweet create Separate hot data: - tweets (PostgreSQL, indexed by date) - timeline cache (Redis sorted set by timestamp) - media (S3 + CDN) Monitoring: slow query log, pg_stat_statements NOT YET needed at 1M: sharding, Cassandra, Kafka
