N+1 & Caching

N+1 là silent killer — code trông đúng nhưng DB bị hammer. 10 orders = 11 queries. 100 orders = 101 queries. Caching đặt đúng chỗ giảm 90% DB load.

Fix N+1 — Mongoose Populate

// ❌ N+1 Problem const orders = await Order.find({}); for (const order of orders) { // N queries! 100 orders = 100 extra queries order.user = await User.findById(order.userId); } // ✅ Fix 1: Mongoose populate (JOIN equivalent) const orders = await Order.find({}) .populate('userId', 'name email'); // 2 queries total // ✅ Fix 2: Aggregation $lookup (1 query) Order.aggregate([ { $lookup: { from: 'users', localField: 'userId', foreignField: '_id', as: 'user' }}, { $unwind: '$user' } ]);

Caching Layers — Bấm để xem chi tiết

🌐
Browser Cache
HTTP Cache-Control, ETags, Service Worker
~0ms
Cache ở client side. Dùng Cache-Control: max-age=3600 cho static assets. ETag cho conditional requests. Service Worker cho offline. Không query server khi cache hit.
🔗
CDN Cache
Cloudflare, CloudFront — geographic edge
~5-20ms
Distributed globally. Request served từ nearest edge node. Excellent cho static files, images, pre-rendered HTML. Vary header để cache per-locale.
🔴
Redis In-Memory Cache
Application-level cache, shared across instances
~1ms
Key/value store in RAM. Perfect cho: session data, rate limiting, frequently-read DB results, computed aggregations. TTL per key. Pub/sub for invalidation. GETSET/SETNX cho distributed locks.
🗄️
DB Query Cache
MongoDB query plan cache, connection pool
~5-50ms
MongoDB caches query plans. Working set (hot data) stays in RAM if total size fits WiredTiger cache (50% RAM by default). Proper indexing ≈ automatic caching for common queries.
💾
Disk (No Cache)
Cold reads from storage
~10-100ms
When nothing is cached — full disk read. SSD: ~0.1ms random read. But DB overhead, parsing, network latency adds up to 10-100ms. Avoid hot paths hitting disk.

Cache Invalidation — Vấn đề khó nhất

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton

Strategies:

  • ⏰ TTL (Time-To-Live): cache expire sau X giây. Đơn giản, eventual consistency.
  • 🗑️ Cache Aside: write invalidates cache key. Read: check cache → miss → DB → populate.
  • ✏️ Write-Through: write cả DB lẫn cache cùng lúc. Consistent hơn, 2x write.
  • 🔔 Event-Driven: invalidate on domain events (product.updated → delete product:* keys).
// Cache-Aside pattern async getProduct(id) { const cached = await redis.get(`product:${id}`); if (cached) return JSON.parse(cached); const product = await Product.findById(id); await redis.setEx( `product:${id}`, 3600, // 1h TTL JSON.stringify(product) ); return product; } // On update: invalidate await redis.del(`product:${id}`);

🛠 Bài tập — Fix N+1 & Add Cache

  • 1Enable Mongoose query logging: mongoose.set('debug', true). Navigate app và đếm queries per request. Tìm N+1.
  • 2Refactor N+1 query dùng .populate() hoặc aggregation $lookup. Verify query count giảm.
  • 3Cài Redis + ioredis. Implement Cache-Aside pattern cho 1 endpoint hay được gọi nhất.
  • 4Set TTL phù hợp: data thay đổi ít = TTL dài (product info), data thay đổi nhiều = TTL ngắn (stock count).
  • 5Implement cache invalidation: khi product được update → delete cache key. Test: update product → next GET trả data mới.

Key Takeaways

  • N+1: fetch 100 orders rồi loop query từng user = 101 queries. Fix: populate/JOIN = 2 queries.
  • Caching hierarchy: Browser (~0ms) → CDN (~10ms) → Redis (~1ms) → DB (~50ms) → Disk (~100ms).
  • Cache-Aside pattern: check cache → miss → DB → populate cache. Invalidate on write.
  • Cache invalidation strategies: TTL (đơn giản), write-through (consistent), event-driven (scalable).
  • "Cache everything" is wrong. Cache hot paths only. Wrong cache = stale data bugs.
