5 Whys — Root Cause Analysis

Surface symptoms hide deeper causes. Ask why five times to reach the system problem, not the patch target.

Interactive Example: Production Crash

Scenario: "The app crashed in production at 2am." Click each Why to dig deeper.

Why 1
Why did the app crash?
▶
Because the server ran out of memory.
Most teams stop here → "Add more RAM." But that's a band-aid. Keep asking.
Why 2
Why did the server run out of memory?
▶
Because there was a memory leak — objects were being created but never garbage collected.
Getting warmer. Is the leak in code, or is it systemic?
Why 3
Why were objects not garbage collected?
▶
Because event listeners were being added in a loop without being removed.
Specific code smell identified. But why was this written this way?
Why 4
Why were listeners added without cleanup?
▶
Because the developer didn't know the component lifecycle — no one explained it in onboarding.
This is a process/knowledge gap, not just a code bug.
Why 5
Why wasn't this covered in onboarding?
▶
Because there is no structured onboarding checklist — knowledge transfer is ad-hoc.
Root cause → Create structured onboarding + add memory leak lint rule + write test for cleanup

Shallow Fix vs Root Fix

❌ Shallow Fix (Why 1 response)

Add 4GB RAM to the server.

Crash delayed 2 weeks, then happens again.

Root cause unchanged. Team on call every month.

✅ Root Fix (Why 5 response)

Add lifecycle cleanup docs to onboarding.

Add ESLint rule for listener cleanup.

Write test asserting zero active listeners on component unmount.

5 Whys Template

Problem: [1 sentence describing the symptom]
Why 1: [immediate technical cause]
Why 2: [cause of the cause]
Why 3: [deeper systemic issue]
Why 4: [process or knowledge gap]
Why 5: [organizational or structural root]
Root cause: [concise statement of the real problem]
Fix: [action that addresses Why 5, not Why 1]

Note: You might only need 3 Whys, or you might need 7. The number is a heuristic — stop when you hit a systemic issue you can actually fix.

🔬 Exercise — Run 5 Whys

Scenario: "Users report they can't log in with Google OAuth."

  1. Write Why 1 (technical surface symptom)
  2. Write Why 2 (what caused the symptom)
  3. Write Why 3 (why that cause exists)
  4. Write Why 4 (process gap)
  5. Write Why 5 (structural root)
  6. Define ONE fix that addresses the root, not the surface

Key Takeaways

  • Every visible bug has a root cause that isn't the visible bug
  • Fixing Why 1 creates a recurring incident; fixing Why 5 closes it permanently
  • Root causes are usually process, knowledge, or systemic — not just code
  • 5 Whys pairs with post-mortems: the RCA section IS a 5 Whys exercise
  • Stop asking when you reach something you can measurably fix
