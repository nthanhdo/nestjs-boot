Git Bisect

Binary search your commit history to find the exact commit that introduced a regression — in O(log n) steps.

Why Bisect?

Problem: "This worked 3 months ago. Now it's broken. Which of the 200 commits broke it?"

Naive approach: Check commits one by one → 200 steps
Bisect: Binary search → ⌈log₂(200)⌉ = 8 steps max

Git bisect automates this. You just say "good" or "bad" after each checkout.

Bisect Simulation

16 commits. The bug is hidden somewhere. Mark "good" or "bad" to find it.

Press "Start Bisect" to begin.

Real Commands

# Step 1: Start bisect session
git bisect start

# Step 2: Mark the current (broken) commit as bad
git bisect bad         # or: git bisect bad HEAD

# Step 3: Mark a known-good commit (e.g. 3 months ago)
git bisect good v2.1.0  # tag, branch, or hash

# Git checks out the midpoint automatically
# → Test it. Does the bug exist?
git bisect bad   # bug exists in this commit
git bisect good  # bug doesn't exist — it was introduced later

# After ~8 rounds, git tells you:
# "abc123def is the first bad commit"
# "commit abc123 — feat: refactor auth middleware"

# Step 4: End the session
git bisect reset  # returns to your original HEAD
# Automate with a test script
git bisect run npm test

# Git runs the test on each commit automatically
# Exit 0 = good, exit non-0 = bad
# Finds the bad commit with zero human interaction

🔬 Exercise — Plan a Bisect

Scenario: Your POST /products endpoint suddenly returns 400 for valid payloads. Last known working version was tag v3.0.0 from 3 weeks ago. There are 64 commits between then and now.

  1. How many bisect steps at most to find the bad commit?
  2. Write the exact 3 commands to start the bisect session
  3. What would you "test" at each midpoint to mark good/bad?
  4. Write a one-liner test script for git bisect run
  5. After finding the commit — what do you do next?

Key Takeaways

  • git bisect = binary search on commits — O(log n) not O(n)
  • 200 commits → found in ≤8 steps, 1000 commits → ≤10 steps
  • Always end with git bisect reset or your HEAD is detached
  • git bisect run <cmd> is fully automatic — use it with a test script
  • Once you find the bad commit, use git show <hash> to see exactly what changed
