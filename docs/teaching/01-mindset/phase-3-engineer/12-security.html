A08:2021

NestJS: Download script không verify checksum.

🔑 Password Security Evolution

Click từng giai đoạn để hiểu tại sao nó bị deprecated.

1990s
💀 Plaintext — password: "abc123"
Lưu nguyên văn trong DB. Nếu DB bị dump → tất cả passwords bị lộ. Vẫn có sites dùng năm 2024 (!). NEVER.
2000s
💀 MD5/SHA1 — hash: "5f4dcc3b..."
Hashing nhưng không có salt. Rainbow table attacks: precomputed hash lookup. MD5 crack trong giây. SHA1 không tốt hơn nhiều.
2010s
⚠️ SHA256 + Salt — hash(password + salt)
Tốt hơn MD5. Nhưng SHA256 quá NHANH — GPU có thể thử 10 tỷ combinations/giây. "Fast hash = bad for passwords."
2015+
✅ bcrypt — bcrypt.hash(password, 12)
Có cost factor — intentionally SLOW (100ms vs microseconds). Adaptive: tăng cost khi phần cứng mạnh hơn. Salt built-in. Vẫn được recommend.
2020+
🏆 Argon2 — Winner of Password Hashing Competition
Memory-hard: cần RAM lớn → GPU attacks kém hiệu quả hơn. 3 variants: argon2i (side-channel safe), argon2d (GPU resistant), argon2id (best of both). Recommendation hiện tại.

📚 Real Case Study: Path Traversal

🚨 1 dòng code = security hole

Từ nestjs-boot codebase — file serve endpoint.

// ❌ VULNERABLE — Path Traversal Attack
async serveFile(filename: string) {
  const path = `./uploads/${filename}`;
  return fs.readFile(path);
  // Attacker: filename = "../../etc/passwd"
  // Đọc được: /etc/passwd (user list trên server)
  // Hoặc: "../.env" → lộ DATABASE_URL, JWT_SECRET
}

// ✅ FIXED — 1 dòng check:
async serveFile(filename: string) {
  const resolvedPath = path.resolve('./uploads', filename);
  if (!resolvedPath.startsWith(path.resolve('./uploads'))) {
    throw new ForbiddenException('Invalid file path');
  }
  return fs.readFile(resolvedPath);
}

Lesson: Mọi user input được dùng trong file system operations đều phải validate. Canonicalize path và check nằm trong allowed directory.

🏋️ Bài Tập Thực Hành

🟢 EASY
Tìm 3 lỗ hổng trong login endpoint sau

Code dưới đây có ít nhất 3 security issues. Liệt kê và giải thích từng lỗi.

// auth.controller.ts — CÓ BUG, tìm và fix
@Post('/login')
async login(@Body() body: any) {
  const user = await this.db.query(
    `SELECT * FROM users WHERE email='${body.email}' AND password='${body.password}'`
  );
  if (!user) throw new UnauthorizedException('Wrong email or password — email not found');
  const token = jwt.sign({ userId: user.id, role: user.role }, 'secret');
  return { token, user }; // trả về toàn bộ user object
}
💡 Xem lời giải

Lỗi 1 — SQL Injection: String interpolation trực tiếp vào query. Hacker nhập email = ' OR '1'='1 → bypass login.

Lỗi 2 — Password Plaintext: So sánh password trực tiếp, không hash. Phải dùng bcrypt.compare(body.password, user.passwordHash).

Lỗi 3 — Hardcoded JWT Secret: 'secret' là string literal. Phải lấy từ process.env.JWT_SECRET.

Bonus — Error Enumeration: Message "email not found" tiết lộ thông tin. Hacker biết email tồn tại. Fix: luôn trả về generic "Invalid credentials".

Bonus — Data Exposure: return { token, user } trả về toàn bộ user (kể cả passwordHash). Chỉ trả về token + public fields.

🟢 EASY
Viết DTO validation cho CreateUserDto

Dùng class-validator để validate: email (valid format), password (min 8 chars, có uppercase + number), age (18-120), role (enum: user/admin, default user).

💡 Xem lời giải 
import { IsEmail, IsString, MinLength, Matches, IsInt, Min, Max, IsEnum, IsOptional } from 'class-validator';

enum UserRole { USER = 'user', ADMIN = 'admin' }

export class CreateUserDto {
  @IsEmail({}, { message: 'Email không hợp lệ' })
  email: string;

  @IsString()
  @MinLength(8, { message: 'Password phải ít nhất 8 ký tự' })
  @Matches(/(?=.*[A-Z])(?=.*[0-9])/, {
    message: 'Password phải có ít nhất 1 chữ hoa và 1 số'
  })
  password: string;

  @IsInt()
  @Min(18) @Max(120)
  age: number;

  @IsOptional()
  @IsEnum(UserRole)
  role: UserRole = UserRole.USER;
}

// main.ts — enable globally:
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,        // strip unknown fields
  forbidNonWhitelisted: true,
  transform: true,
}));
🟡 MEDIUM
JWT expiry — tại sao cần và implement như thế nào?

Giải thích: (1) Tại sao JWT cần expiry? (2) Access token vs Refresh token nên có TTL bao lâu? (3) Implement refresh token flow trong NestJS.

💡 Xem lời giải

1. Tại sao cần expiry: JWT không thể revoke sau khi issue (stateless). Nếu token bị đánh cắp mà không có expiry → attacker dùng mãi mãi. Expiry giới hạn window of opportunity.

2. Recommended TTL:

  • Access token: 15 phút (short-lived, stateless check)
  • Refresh token: 7-30 ngày (long-lived, stored in DB để có thể revoke)
// auth.service.ts — issue tokens
async issueTokens(userId: string) {
  const accessToken = this.jwtService.sign(
    { sub: userId },
    { expiresIn: '15m', secret: process.env.JWT_ACCESS_SECRET }
  );
  const refreshToken = this.jwtService.sign(
    { sub: userId },
    { expiresIn: '7d', secret: process.env.JWT_REFRESH_SECRET }
  );
  // Store hashed refreshToken in DB để có thể revoke
  await this.tokenRepo.save({
    userId,
    tokenHash: await bcrypt.hash(refreshToken, 10),
    expiresAt: new Date(Date.now() + 7 * 24 * 3600 * 1000)
  });
  return { accessToken, refreshToken };
}

// POST /auth/refresh — dùng refresh token đổi access token mới
async refresh(refreshToken: string) {
  const payload = this.jwtService.verify(refreshToken, {
    secret: process.env.JWT_REFRESH_SECRET
  });
  // Verify token còn trong DB (chưa bị revoke)
  const stored = await this.tokenRepo.findByUserId(payload.sub);
  const valid = await bcrypt.compare(refreshToken, stored.tokenHash);
  if (!valid) throw new UnauthorizedException();
  return this.issueTokens(payload.sub); // Rotate both tokens
}
🟡 MEDIUM
Fix IDOR vulnerability trong orders API

Code dưới đây có Insecure Direct Object Reference (IDOR). User A có thể xem/xóa order của User B. Fix nó.

// orders.controller.ts — IDOR vulnerable
@Get(':id')
async getOrder(@Param('id') id: string) {
  return this.ordersService.findById(id); // Không check ownership!
}

@Delete(':id')
async deleteOrder(@Param('id') id: string) {
  return this.ordersService.delete(id); // Ai cũng xóa được!
}
💡 Xem lời giải 
// orders.controller.ts — FIXED
@Get(':id')
@UseGuards(JwtAuthGuard) // Bước 1: require auth
async getOrder(
  @Param('id') id: string,
  @CurrentUser() user: User  // Bước 2: lấy user từ JWT
) {
  const order = await this.ordersService.findById(id);
  if (!order) throw new NotFoundException();
  // Bước 3: check ownership — QUAN TRỌNG NHẤT
  if (order.userId !== user.id && user.role !== 'admin') {
    throw new ForbiddenException('Access denied');
  }
  return order;
}

@Delete(':id')
@UseGuards(JwtAuthGuard)
async deleteOrder(@Param('id') id: string, @CurrentUser() user: User) {
  const order = await this.ordersService.findById(id);
  if (!order) throw new NotFoundException();
  if (order.userId !== user.id) throw new ForbiddenException();
  return this.ordersService.delete(id);
}

OWASP Security Audit Checklist — audit 1 feature end-to-end

Chọn 1 feature bất kỳ (ví dụ: upload avatar, payment, comment system). Tạo checklist 10 items tương ứng với OWASP Top 10, điền trạng thái ✅/❌/⚠️ và action nếu cần.
