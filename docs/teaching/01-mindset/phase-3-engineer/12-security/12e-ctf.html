Defender's Mindset Principles

👿

Think like an attacker, act like a defender

Before shipping any feature, ask: "How would I break this?" Enumerate inputs, bypass flows, find edge cases the happy path misses.

🔒

Deny by default

Every endpoint denied unless explicitly allowed. Every field rejected unless explicitly expected. Never "allow all and filter" — always "deny all and allowlist."

🧅

Defense in depth

One layer of security failing shouldn't mean total breach. Validation at HTTP layer + service layer + DB layer. If SQL injection bypasses input check, parameterized query still blocks it.

🧪

Test the negative path first

For any security control: verify it BLOCKS before verifying it allows. A guard that doesn't block is not a guard. Write a test with no token, bad token, wrong role — before the happy path.

🔬 Exercise — Security Review

Apply the CTF mindset to your last feature. For each question, write a specific answer:

  1. What are all the inputs this feature accepts? (URL params, body, headers, cookies)
  2. What's the worst thing an attacker could do with malformed input?
  3. What authorization checks are in place? Can you bypass them?
  4. What does the error response reveal? (stack trace? DB errors?)
  5. What rate limiting is in place? Can you brute-force it?
  6. Write one failing test for each security concern you found

Key Takeaways

  • Attacker mindset = the best security tool — think "how would I break this?"
  • Deny by default — allowlist, not blocklist
  • Defense in depth — multiple layers so one failure isn't catastrophic
  • Test negative paths first — a guard you haven't verified blocking is not a guard
  • Practice on legal platforms (HTB, PortSwigger) — real skills, safe environment
