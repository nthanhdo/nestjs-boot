Thiết kế cho 1 user khác với 1 triệu user. Hiểu trade-offs để đưa ra quyết định đúng.

📚 Prerequisites
  • Bài 6: Architecture — layered design, separation of concerns

🤔 Tại sao System Design quan trọng?

Architecture patterns từ Bài 6 áp dụng ở component level; System Design áp dụng ở infrastructure level — cùng nguyên tắc, khác scale.

🧑‍💻

1 User

  • ✓ SQLite đủ dùng
  • ✓ Monolith on 1 server
  • ✓ No cache needed
  • ✓ Sync operations OK
  • ✓ 1ms latency irrelevant
🌐

1,000,000 Users

  • ⚡ Distributed DB required
  • ⚡ Multiple servers + LB
  • ⚡ Multi-layer caching
  • ⚡ Async + queues
  • ⚡ 1ms latency = $millions lost

🔗 Case Study: URL Shortener Design

Level 1 system design — walkthrough từng bước. Click mỗi bước để expand.

1
Requirements
Functional: Nhập URL dài → nhận URL ngắn. Click URL ngắn → redirect đến URL gốc.

Non-functional: 100M URLs/day. Latency < 10ms redirect. 99.9% availability. URLs không expire (mặc định).

Scope out: Analytics, custom slug, account management (scope for v2).
2
Estimation
100M writes/day = 1,160 writes/sec
Read:Write ratio = 100:1 → 116,000 reads/sec
Storage: 100M × 500 bytes × 5 years = 182TB
Bandwidth write: 1,160 × 1KB = 1.16 MB/s
Cache: 20% hot URLs cover 80% traffic (Pareto)
3
API Design
POST /api/urls → body: { longUrl } → response: { shortCode }
GET /{shortCode} → 301/302 redirect → longUrl

301 = permanent (browser cache) — ít server load
302 = temporary (always hit server) — dùng nếu cần analytics
4
Data Model
URLs table: shortCode (PK), longUrl, createdAt, userId?

shortCode: 7 ký tự, base62 [a-z A-Z 0-9] → 62^7 = 3.5 tỷ combinations
Generate: hash(longUrl + timestamp) → take first 7 chars
Collision: check DB, regenerate nếu exists
5
Architecture + Scaling
Client → CDN → Load Balancer → App Servers (x N) → Cache (Redis) → DB (PostgreSQL)

Read path: App → Redis → PostgreSQL (cache miss only)
Write path: App → PostgreSQL → invalidate cache
DB: Primary-Replica (write → primary, read → replicas) — xem thêm Bài 7 DB Scaling

⚡ Caching Layers

Cache gần user nhất = nhanh nhất. Click từng layer để xem chi tiết. DB optimization ở Bài 7 là tiền đề cho DB cache layer hiệu quả.

🌐 Browser Cache
~0ms
Cache-Control headers, Service Worker, localStorage. Không cần hit server. Nhất: static assets (JS, CSS, images). Cache-Control: max-age=31536000
🌍 CDN Cache
~5ms
Cloudflare, CloudFront. Serve từ edge node gần user nhất. Tốt cho: HTML tĩnh, images, videos. Cache invalidation: purge API.
🚀 App Cache (Redis)
~1ms
In-memory key-value. Tốt cho: session, computed results, rate limiting, leaderboard. TTL-based expiry. Cần handle cache invalidation strategy.
🗄️ DB Cache (Query)
~10ms
PostgreSQL buffer pool, query plan cache. Tự động — nhưng index đúng chỗ giúp query plan cache hiệu quả. EXPLAIN ANALYZE để kiểm tra.
💾 Disk (DB)
~100ms+
Chậm nhất. Mọi cache trên đều cố tránh hit DB. Nếu phải hit → đảm bảo query có index đúng chỗ, tránh N+1 query, limit result size.

🟢 EASY
Estimation: URL Shortener cần bao nhiêu storage?

Tính toán: 50 triệu URLs mới mỗi ngày. Mỗi record: shortCode (7 bytes) + longUrl (100 bytes avg) + metadata (50 bytes). Giữ data 10 năm. Tính tổng storage cần.

💡 Xem lời giải 
## Back-of-envelope estimation

Record size = 7 + 100 + 50 = 157 bytes ≈ 200 bytes (với overhead)

Daily: 50M × 200 bytes = 10 GB/day
Yearly: 10 GB × 365 = 3.65 TB/year
10 năm: 3.65 × 10 = 36.5 TB

## Traffic estimation

Writes: 50M/day = 50,000,000 / 86,400 ≈ 578 writes/sec
Read:Write = 10:1 → 5,780 reads/sec

## Cache requirement

Daily reads: 578 × 10 = 5,780/sec = ~500M reads/day
20% URLs cover 80% traffic → cache top 100M URLs
100M × 200 bytes = 20 GB RAM cho cache layer

## Kết luận hardware

- Storage: 40TB (dư 10% buffer)
- Redis: 2 servers × 16GB RAM
- DB: 1 primary + 2 replicas (read load)
- App servers: 4 servers (each handles ~1500 reads/sec)
🟢 EASY
Design API cho Notification System

Một app cần gửi notification qua 3 channels: Email, Push (mobile), In-app. Design REST API endpoints và data model. Identify đâu nên dùng Queue.

💡 Xem lời giải 
## API Endpoints

POST /notifications
  body: { userId, type: "email|push|in_app", template, data }
  response: { notificationId, status: "queued" }
  → Trả ngay, không đợi gửi xong

GET /notifications?userId=123&status=unread
  → In-app notifications list

PATCH /notifications/:id/read
  → Mark as read

DELETE /notifications/:id
  → Cancel if pending

## Data Model

notifications {
  id: UUID (PK),
  userId: string,
  channel: enum(email, push, in_app),
  templateId: string,
  data: JSON,  -- dynamic content
  status: enum(pending, sent, failed, read),
  scheduledAt: timestamp?,
  sentAt: timestamp?,
  createdAt: timestamp
}

## Queue Design

POST /notifications → DB insert (status=pending)
                     → Enqueue to channel-specific queue

email-queue    → EmailWorker → SendGrid API
push-queue     → PushWorker  → FCM/APNS
in_app-queue   → (save to DB, status=delivered, real-time via WebSocket)

## Tại sao Queue?

1. Email SendGrid: rate limited, retry on failure
2. Push FCM: batch có thể fail, cần retry logic
3. In-app: user có thể offline, deliver khi reconnect
4. Decouple API response (fast) từ delivery (slow)
🟡 MEDIUM
Caching strategy cho Product Listing page

E-commerce site: /products?category=electronics&sort=price&page=1. Products update mỗi giờ. Flash sale có thể xảy ra bất cứ lúc nào. Design caching strategy với cache invalidation.

💡 Xem lời giải 
## Cache Key Strategy

key = `products:${category}:${sort}:${page}:${version}`
version = daily timestamp → auto-invalidate mỗi ngày

## TTL Policy

Bình thường: TTL = 1 giờ (products update mỗi giờ)
Flash sale: TTL = 30 giây (cần reflect stock changes nhanh)

## Implementation (NestJS + Redis)

async getProducts(params) {
  const cacheKey = buildKey(params);
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  const data = await db.query(...)
  const ttl = await isFlashSaleActive() ? 30 : 3600;
  await redis.setex(cacheKey, ttl, JSON.stringify(data));
  return data;
}

## Flash Sale Invalidation

// Khi flash sale bắt đầu:
async startFlashSale(categoryId) {
  const keys = await redis.keys(`products:${categoryId}:*`);
  await redis.del(...keys); // Purge toàn bộ category
  await redis.set('flash_sale_active', '1', 'EX', 3600);
}

## Cache Stampede Prevention

// Dùng "lock" để tránh nhiều requests hit DB cùng lúc
const lock = await redis.set(`lock:${cacheKey}`, '1', 'NX', 'EX', 5);
if (!lock) {
  await sleep(100); // Wait for first request to populate
  return redis.get(cacheKey); // Retry from cache
}
🟡 MEDIUM
Message Queue cho Order Processing flow

Khi user đặt hàng, system cần: (1) reserve inventory, (2) charge payment, (3) send confirmation email, (4) notify warehouse. Design queue-based flow đảm bảo idempotency và retry.

💡 Xem lời giải 
## Flow Design (BullMQ / NestJS)

POST /orders
  → Save order (status: PENDING)
  → Enqueue "order.created" event
  → Return 202 Accepted + orderId

## Queue Topology

order.created
  ├─ InventoryWorker   → reserve stock → emit "inventory.reserved"
  └─ (wait for reserved before charging)

inventory.reserved
  └─ PaymentWorker     → charge card → emit "payment.completed"

payment.completed
  ├─ EmailWorker       → send confirmation (idempotent: check sent flag)
  └─ WarehouseWorker   → notify warehouse (webhook)

## Idempotency Pattern

// Mỗi job có unique ID → nếu processed rồi → skip
async processPayment(job) {
  const { orderId } = job.data;
  const alreadyCharged = await db.findPayment({ orderId });
  if (alreadyCharged) return { skipped: true }; // Idempotent

  const result = await stripe.charge(...);
  await db.savePayment({ orderId, chargeId: result.id });
}

## Retry Config

{ attempts: 3, backoff: { type: 'exponential', delay: 1000 } }
// Retry: 1s → 2s → 4s → Dead Letter Queue

## Dead Letter Queue

// Failed jobs → DLQ → Alert team → manual review
// Không bao giờ silently drop failed jobs
🔴 HARD
Full System Design: Chat Application

Design một real-time chat app: 10M daily active users, 1B messages/day, message history 2 năm, support group chat (max 500 members), read receipts. Estimate storage, design architecture, identify bottlenecks.

💡 Xem lời giải (High-level) 
## Estimation

Messages: 1B/day = 11,574/sec = ~12K msg/sec
Avg message size: 100 bytes
Storage/day: 1B × 100 = 100 GB/day
2 năm: 100 × 730 = 73 TB
+ Media (50% messages): 73 TB × 5x avg = 365 TB total

## Architecture Components

Client → WebSocket Gateway → Message Service → Kafka
                           ↓
                    Presence Service (online status)
                           ↓
                    Fan-out Service → WebSocket push to recipients

## Data Stores

Messages: Cassandra (time-series, wide column, write-heavy)
  key: (conversationId, timestamp) → partition by conv
  → Đọc recent messages fast, old messages warm tier

Users/Conversations: PostgreSQL
Media: S3 + CDN (Cloudflare)
Presence/online status: Redis (SET user:123:online EX 30)
Push when offline: APNs / FCM via BullMQ

## Why Cassandra for messages?

- Write throughput: 12K msg/sec → needs distributed writes
- Time-series access pattern: recent > old (fits Cassandra)
- Horizontal scale: add nodes = more write capacity
- Vs PostgreSQL: single-node write bottleneck at this scale

## Real-time Delivery (WebSocket)

User connects → WS Gateway (stateful, sticky session)
Message sent → Kafka topic: messages
Fan-out consumer:
  - Find all group members
  - For each online member: push via WS Gateway
  - For each offline: queue push notification

## Read Receipt (Bài toán at-scale)

Naive: UPDATE messages SET readBy = [...] → N+1 problem in group chat

Solution: Separate read_receipts table
  (messageId, userId, readAt) → index on messageId
  Batch update every 5 seconds (không update mỗi message)

## CAP Choice: AP (Availability + Partition)

Message delivery: user thấy message sau 1-2s delay = OK
vs: user thấy error khi network partition = BAD
→ Choose eventual consistency (AP) for message delivery

## Security layer (Bài 12)

- E2E encryption: client-side, server stores ciphertext only
- Rate limit: 100 messages/min per user (anti-spam)
- Auth: JWT + refresh token per connection

📋 Tóm Tắt Bài 13

  • 📐 10-step process: requirements → monitoring
  • 📈 Vertical có ceiling; Horizontal là default choice
  • ⚡ Cache: Browser → CDN → Redis → DB (gần → xa)
  • 📨 Queue: decoupling + async heavy work
  • 🔌 Circuit breaker: fail fast, protect downstream
  • 🔺 CAP: network partition = pick CP hoặc AP
  • 🔗 Liên quan: Bài 7 DB · Bài 12 Security
  • 🏗️ Design thực chiến: URL Shortener → Chat App

🎯 Key Takeaways

  • ✅ System design = requirements → constraints → trade-offs. Không có "perfect" solution
  • ✅ Vertical scale có giới hạn. Horizontal scale phức tạp hơn nhưng unlimited
  • ✅ Cache aggressively — CDN → Redis → DB. Cache miss = latency spike
  • ✅ Queue = async heavy work. User không cần chờ email gửi xong
  • ✅ Circuit breaker ngăn cascade failure — fail fast tốt hơn fail slow
  • ✅ CAP: network partition luôn xảy ra → chọn CP hoặc AP. Hiểu DB của bạn đang chọn gì
  • ✅ Đừng over-engineer sớm — profile first, scale where bottleneck is
