Cache Patterns

Cache-Aside (Lazy)

App checks cache. Miss → load from DB → populate cache → return. Most common. App controls what's cached.

Write-Through

Write to cache AND DB together. Cache always current. Higher write latency (both systems must ack).

Write-Behind (Write-Back)

Write to cache, async to DB. Low write latency. Risk: data loss if cache dies before DB write.

Read-Through

Cache sits in front of DB. Miss → cache loads from DB transparently. Cache provider manages it.

// Cache-Aside with Redis (NestJS)
async getProduct(id: string): Promise {
  const key = `product:${id}`;
  const cached = await this.redis.get(key);
  if (cached) return JSON.parse(cached);          // Cache HIT

  const product = await this.productRepo.findById(id); // Cache MISS
  await this.redis.setex(key, 3600, JSON.stringify(product)); // 1hr TTL
  return product;
}

🔬 Exercise — When to Use Which

  1. Your product catalog (10K products) is read 100K times/day, updated hourly. Cache pattern?
  2. User sends 1,000 emails at once. Your email provider rate-limits at 10/sec. Solution?
  3. A payment triggers: update DB, send email, update inventory, create invoice. All must succeed. How do you coordinate?
  4. Product prices change frequently (every 5 min). If you cache them, what TTL do you set?
  5. A "flash sale" will cause 50,000 concurrent users in 60 seconds. What two patterns protect your DB?

Key Takeaways

  • Cache-aside is the default pattern — simple, effective, app controls what's cached
  • TTL = cache invalidation strategy — choose based on data change frequency
  • Queues decouple producer from consumer — producer doesn't wait for all downstream effects
  • Queues absorb traffic spikes — consumers process at their own rate
  • BullMQ (Redis-backed) = standard NestJS queue. Supports retries, priorities, delays.
