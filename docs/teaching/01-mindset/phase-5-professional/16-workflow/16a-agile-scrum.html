🏃 Agile & Scrum

Quy trình làm việc team-based mà mọi professional engineer đều cần hiểu. Sprint cycle, daily standup, review, retrospective — không phải bureaucracy mà là coordination system.

Tại Sao Agile?

❌ Waterfall

  • Plan 6 tháng trước, không đổi
  • Ship khi "xong hết"
  • Khách hàng thấy sản phẩm sau 6-12 tháng
  • Nếu requirements sai → disaster

✅ Agile

  • Plan 2 tuần (1 sprint)
  • Ship working software mỗi sprint
  • Feedback ngay từ sprint 1
  • Adapt khi requirements thay đổi

🔄 Sprint Cycle (2 tuần)

📋

2-4 giờ / sprint

⌨️ Day 2-9: Build
🧪 Day 8-9: Test
🎯 Day 10: Review
🔄 Day 10: Retro

↺ Lặp lại mỗi 2 tuần

☕ Daily Standup — 3 Câu Hỏi

Mục đích: sync, không phải status report cho manager. Mỗi người nói không quá 2 phút.

✅
Hôm qua làm gì?
"Xong phần JWT guard, viết tests cho auth module."
🎯
Hôm nay làm gì?
"Implement forgot-password endpoint, integrate Nodemailer."
🚧
Có bị blocked không?
"Cần SMTP credentials từ anh Minh để test email flow."
Anti-pattern: Standup kéo dài 45 phút vì team thảo luận technical details. Rule: nếu discussion cần > 5 phút → schedule separate meeting. Standup = sync only, không giải quyết problems.

🎯 Sprint Review vs Retrospective

Sprint Review

Hướng ra ngoài — khách hàng / stakeholder

  • Demo features đã done (only done = deployable)
  • Gather feedback từ PO / stakeholder
  • Accept hoặc reject items
  • Update backlog dựa trên feedback

Retrospective

Hướng vào trong — cải thiện team process

  • Went well → celebrate, keep doing
  • To improve → specific pain points
  • Action items → ai làm gì, khi nào
  • Không blame cá nhân — blame process

Ví dụ Retrospective:

✅ Went Well
CI/CD pipeline hoạt động tốt, 0 deploy issues
Code review chất lượng, bugs bắt được sớm
Team communicate tốt qua Slack
⚠️ To Improve
Estimation sai → 3 tasks spill sang sprint sau
Không có definition of done rõ ràng
Testing bị dồn vào ngày cuối sprint
🎯 Action Items
Thêm buffer 30% vào estimate (Linh lead)
Viết DoD cho mỗi task (cả team, sprint planning)
Test viết cùng với feature (Minh + Thảo)

📋 Backlog Management

Product Backlog vs Sprint Backlog

Product Backlog

  • Tất cả features/bugs chưa làm
  • Ordered by priority (PO quyết định)
  • Thay đổi liên tục khi có info mới
  • Items lớn được break down khi cần

Sprint Backlog

  • Subset chọn từ product backlog
  • Team cam kết hoàn thành trong 2 tuần
  • Không thêm item giữa sprint (trừ P0)
  • Team tự organize how để đạt sprint goal
Definition of Done (DoD): Mỗi team phải có DoD rõ ràng. Ví dụ: Code written + tests pass + code reviewed + deployed to staging + QA sign-off. "Done" không phải "code chạy trên máy tôi".
🎯 Bài Tập Thực Hành
🟢 DễBài 1
Viết daily standup cho ngày hôm nay
Nhìn vào task đang làm. Viết 3 câu cho daily standup: hôm qua, hôm nay, blocker. Mỗi câu phải cụ thể (không vague như "làm backend"), không quá 15 giây khi đọc to.
Tốt vs không tốt:
❌ "Hôm qua làm auth, hôm nay cũng auth"
✅ "Hôm qua: implement JWT refresh token flow, tests pass. Hôm nay: forgot-password endpoint với Redis OTP storage. Blocked: cần SMTP config từ DevOps team."

Key: cụ thể, actionable, nếu blocked → tag người cần giúp ngay
🟡 Trung bìnhBài 2
Retrospective: phân tích sprint vừa rồi theo format Went Well / To Improve / Actions
Nhớ lại 1 project/sprint gần đây (cá nhân hoặc team). Viết retrospective đầy đủ với ít nhất 3 items mỗi category. Action items phải có owner và deadline.
Template action item tốt:
"[Tên] sẽ [action cụ thể] trước [ngày] để giải quyết [problem]"

Ví dụ: "Linh sẽ thêm buffer 30% vào estimate formula trong planning doc trước Sprint 5 planning để giải quyết vấn đề tasks spill."

Anti-pattern: "Team cần communicate tốt hơn" → quá vague, không ai chịu trách nhiệm, không đo được
🔴 KhóBài 3
Sprint planning: chọn tasks cho sprint 2 tuần, capacity 40 points
Backlog: Auth system (L=13pts), Dashboard UI (M=8pts), CSV Export (M=8pts), Fix checkout bug (S=3pts), Email notifications (L=13pts), Search autocomplete (S=5pts), Dark mode (M=8pts). Team capacity = 40 points. Chọn tasks, justify priority, explain trade-offs.
Approach:
1. P0 bugs first: Fix checkout bug (3pts) — revenue-blocking
2. High value: Auth system (13pts) — blocking nhiều features khác
3. Dashboard UI (8pts) — users cần để thấy value
4. Search autocomplete (5pts) — UX improvement, low effort
= 29pts. Buffer 20% → còn dư 3-4pts cho interruptions

Skip và lý do:
- Email notifications (13pts) — cần auth xong trước (dependency)
- CSV Export (8pts) — lower priority vs core features
- Dark mode (8pts) — nice-to-have, not urgent

Sprint goal: "Auth + core UI working = users can login và see dashboard"

📌 Tóm Tắt — Agile & Scrum

  • Sprint = 2 tuần, commit vào goal, deliver working software
  • Standup = 15 phút, 3 câu. Sync và surface blockers — không status report
  • Sprint Review = demo cho stakeholders, collect feedback, update backlog
  • Retrospective = cải thiện process, không blame người. Action items có owner
  • DoD = team phải đồng ý "done" nghĩa là gì trước khi bắt đầu
  • Backlog = product (tất cả) vs sprint (cam kết 2 tuần)
