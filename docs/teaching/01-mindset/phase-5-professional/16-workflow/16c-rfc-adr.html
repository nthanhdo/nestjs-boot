📄 RFC & Code Review

Technical proposals và collaborative quality check — hai kỹ năng communication không thể thiếu của professional engineer.

📋 RFC — Request for Comments

RFC = document propose một technical change lớn, để team review TRƯỚC khi implement. Tránh "tại sao chúng ta làm thế này?" sau 6 tháng.

Khi nào viết RFC? Khi decision ảnh hưởng đến nhiều người, có trade-offs không rõ ràng, hoặc không thể undo dễ dàng. XS/S tasks = không cần RFC. L/XL hoặc system design = cần RFC.
📄
RFC-001: Switch Authentication từ Session sang JWT
ACCEPTED
Context & Problem
Hiện tại dùng server-side sessions (Redis). Mobile app cần stateless auth. Session store thêm latency ~20ms mỗi request. Mobile cần token để gọi API.
Proposal
Migrate sang JWT với access token 15min + refresh token 7 ngày. Keep Redis cho refresh token revocation list. Implement @nestjs/jwt + custom guards.
Trade-offs
✅ Pros: stateless, mobile-friendly, no Redis latency trên normal requests.
⚠️ Cons: token không thể invalidate ngay (phải chờ expire), revocation list phức tạp hơn session.
Alternatives Considered
1. Keep session + add mobile API key — simpler nhưng 2 auth systems.
2. Opaque tokens với lookup — tradeoff giữa stateless và immediate revocation.
Decision & Migration Plan
ACCEPTED. Sprint 5: implement JWT. Sprint 6: migrate users, deprecate session. Backward compat trong 2 sprints.
RFC anti-pattern: Viết RFC sau khi implement rồi — đó không phải RFC mà là announcement. RFC phải được viết TRƯỚC khi code, với genuine openness to alternative approach.

👀 Code Review — Collaborative Quality

Code review không phải "tìm lỗi của người khác" — đó là collaborative quality check và knowledge sharing.

AspectReviewer nhìn gì✅ Comment tốt
Correctness Logic đúng không? Edge case handled? "What happens when userId is null? I'd add a guard clause at L12."
Security Input validated? Auth checked? Injection risk? "This query concatenates user input — should use parameterized form to prevent SQL injection."
Readability Code self-explanatory? Naming clear? "[nit] x on L30 could be userCount for clarity."
Performance N+1 query? Missing index? Unnecessary loop? "This calls DB inside a loop (L45-52). Consider findMany with ID array."
Tests Test coverage đủ không? Edge case có test? "Missing test case for empty array input — the function returns undefined instead of []."

❌ Comments cần tránh

  • "This is wrong." → Không explain tại sao, không suggest fix
  • "Bad code." → Vague, demoralizing, không actionable
  • "Why would you do this???" → Aggressive, không professional
  • "I would have done it differently." → Personal preference, không có technical basis
Rule: Mỗi comment phải có: (1) observation, (2) tại sao nó quan trọng, (3) suggestion. Dùng "nit:" prefix cho minor style issues — author có thể ignore nit comments.

📝 PR Description Template

PR tốt = reviewer không cần hỏi gì thêm

## What does this PR do?
Implement JWT authentication (access token 15m + refresh token 7d).
Replaces server-side session with stateless auth.

## Why?
Mobile app integration requires stateless auth (RFC-001 ACCEPTED).

## How to test?
1. POST /auth/login → get access + refresh token
2. Use access token in Authorization header
3. After 15min, use refresh token at POST /auth/refresh
4. Test revocation: POST /auth/logout → refresh should fail

## Breaking changes?
Session cookie auth deprecated. Existing sessions invalidated.
Migration guide: docs/auth-migration.md

## Checklist
- [x] Tests pass
- [x] Documentation updated
- [x] No sensitive data logged
- [x] Migration plan documented
🎯 Bài Tập Thực Hành
🟢 DễBài 1
Viết PR description cho feature bất kỳ
Chọn 1 feature bạn đã implement gần đây. Viết PR description đầy đủ theo template: What, Why, How to test, Breaking changes, Checklist. Reviewer phải hiểu feature mà không cần hỏi thêm.
Đánh giá PR description tốt bằng test: "Nếu tôi join team ngày mai và cần review PR này, tôi có hiểu không?"

Checklist:
✓ What: 2-3 câu mô tả feature, không phải technical detail
✓ Why: business reason, không chỉ technical reason
✓ How to test: cụ thể, step-by-step, không phải "test it"
✓ Breaking changes: mention nếu có, "None" nếu không
✓ Checklist: tick tất cả trước khi assign reviewer
🟡 Trung bìnhBài 2
Viết RFC: propose adding rate limiting vào public API
Viết RFC hoàn chỉnh đề xuất rate limiting (100 req/min per IP) cho public API. Phải có Context, Proposal, Trade-offs, Alternatives, và Migration plan.
RFC structure:
Context: API bị abuse, 1 IP gọi 1000 req/sec, costs tăng, service degraded for others
Proposal: 100 req/min per IP using @nestjs/throttler, return 429 với Retry-After header
Pros: Protect against abuse, fair usage, standard HTTP behavior
Cons: Legitimate heavy users bị ảnh hưởng, need whitelist mechanism
Alternatives: (1) API key based (track by key not IP), (2) Cloudflare rate limiting (infrastructure level)
Migration: Document rate limits, add Retry-After header, 1 sprint notice trước khi enforce
Metrics: Monitor 429 rate, adjust limits nếu too aggressive
🔴 KhóBài 3
Code review simulation: review PR và viết 5 constructive comments
Tìm một PR public (NestJS/TypeORM repo hoặc project của bạn). Review và viết ít nhất 5 comments: cover correctness, security, readability, performance, tests. Mỗi comment phải có category tag, observation, reason, và suggestion.
Template mỗi comment:
[Category] Observation. Reason why it matters. Suggested fix.

Ví dụ:
"[Security] L45: User input is concatenated into SQL query directly. This is vulnerable to SQL injection — attacker can pass ' OR '1'='1'-- to return all rows. Use parameterized query: WHERE id = $1 with [userId] as param array."

"[nit] L30: Variable name r could be response for readability — makes the code self-documenting without needing to trace back to function signature."

After writing: read all your comments — if any sounds aggressive, reword. Target: developer feels helped, not attacked.

📌 Tóm Tắt — RFC & Code Review

  • RFC = propose trước khi implement. L/XL decisions cần RFC để align team
  • RFC structure = Context → Proposal → Trade-offs → Alternatives → Decision
  • Code review = collaborative quality check. 5 aspects: correctness, security, readability, performance, tests
  • Good comment = observation + reason + suggestion. Không phải "bad code"
  • "nit:" prefix = minor/optional, author có thể ignore
  • PR description = What + Why + How to test + Breaking changes. Reviewer không cần hỏi thêm
