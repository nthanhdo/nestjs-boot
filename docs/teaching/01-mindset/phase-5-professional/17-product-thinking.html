Product Thinking

Engineer giỏi không chỉ build đúng — mà build đúng thứ. Product thinking là kỹ năng phân biệt senior khỏi junior.

2. User Problem vs Business Problem

Feature tốt nhất nằm ở giao điểm của cả hai. Feature chỉ solve business problem mà không giúp user = không sustainable. Ngược lại = company sập.

3. Functional vs Non-functional Requirements

⚙️ Functional (cái gì)
User có thể register bằng email
Admin xem được danh sách orders
System gửi email confirmation
Product có thể search theo tên
User có thể cancel order trong 24h
📊 Non-functional (như thế nào)
API response < 200ms (P95)
System uptime 99.9%
Handle 1000 concurrent users
GDPR compliant — data deletion
Password hashed, không plain text
Sai lầm phổ biến: Junior engineer chỉ implement functional requirements, bỏ qua non-functional. Product đến production mới phát hiện performance issues, security holes. Non-functional = phải design từ đầu, không thể add-on sau.

4. MVP — Ship Fast, Learn Fast

MVP (Minimum Viable Product) = strip mọi thứ không cần thiết → ship core value → học từ real users → iterate.

Full Vision
Auth Create post Comments Rich editor Mentions Reactions AI summary Dark mode Analytics
↓ Strip to core
MVP
Auth Create post Comments …everything else → backlog
↓ Ship → Learn → Iterate
v2 — Data-driven
Auth Create post Comments Rich editor Reactions (users asked) AI summary (low demand)

5. Product Metrics — Đo Cái Gì?

Engineer cần hiểu metrics để biết feature mình build có tác động gì. "If you can't measure it, you can't improve it."

↓ 60%

Engineer's role với metrics: Đảm bảo tracking events được log đúng, không bị miss. Sau deploy, check dashboard — nếu metric không di chuyển như expect → bug hoặc wrong feature.

7. Should We Build This? — Decision Tree

❓ Feature request: "Thêm dark mode"
✓ Build nếu:
• >30% users đã request
• Core user persona cần
• Low effort (S/M)
• Accessibility requirement
• Competitors đã có
→ Add to next sprint
✗ Skip nếu:
• Chỉ 1-2 người hỏi
• Effort lớn, unclear ROI
• Core problems chưa solve
• Technical debt cao hơn
• Team bandwidth thấp
→ Backlog / decline

8. Khi nào Engineer Push Back?

✅ Engineer nên push back khi:

  • Feature tạo security risk nghiêm trọng và scope chưa account cho việc mitigate
  • Technical debt đã quá cao — thêm feature sẽ làm system fragile
  • Estimate unrealistic — "làm trong 1 ngày" nhưng thực tế cần 1 tuần
  • Feature contradicts với architectural decision đã được ratify

❌ Engineer không nên push back khi:

  • Không thích feature nhưng không có technical reason
  • Prefer một tech stack khác mà không có data để back up
  • Business decision — đó là role của PM/founder, không phải engineer

9. Câu Hỏi Nên Hỏi Trước Khi Build

①
"Tại sao cần feature này?"
Understand the "why" trước khi implement "how". Tránh build wrong thing.
②
"Problem thực sự là gì?"
User request ≠ user need. "Add a faster horse" → thực ra cần xe hơi.
③
"Ai sẽ dùng? Bao nhiêu người?"
Scale ảnh hưởng design. 10 user vs 10 triệu user = different architecture.
④
"Thành công trông như thế nào?"
Define metric trước khi build. Không thì không biết feature có work không.
⑤
"Nếu không build, điều gì xảy ra?"
Đôi khi câu trả lời là "không sao" — giúp deprioritize đúng.

🎯 Exercise: Feature Analysis

Feature request: "Thêm tính năng cho phép user export data của họ ra CSV/Excel."

  • ①Hỏi 5 câu "tại sao" — identify user problem thực sự
  • ②List functional requirements (3-5 items)
  • ③List non-functional requirements (performance, security, format)
  • ④MVP vs Full feature — what's the minimum to ship?
  • ⑤Identify metrics — làm sao biết feature successful?
  • ⑥Cost vs value analysis — có nên build không? Khi nào?
🎯 Bài Tập Thực Hành
🟢 DễBài 1
User Problem: phỏng vấn "user" → identify real problem
Pair với một bạn: một người đóng vai user cần "export data ra Excel". Người kia phỏng vấn bằng 5 câu "tại sao" để tìm real problem. Ghi lại: request ban đầu là gì, real need là gì.
5 "Why" chain mẫu:
→ "Tại sao muốn export?" "Để gửi cho manager hàng tuần."
→ "Tại sao gửi bằng Excel?" "Manager dùng Excel để tổng hợp nhiều report."
→ "Tại sao không tổng hợp trong app?" "App không có view tổng hợp nhiều accounts."
→ Real problem: thiếu consolidated view, không phải thiếu export feature

Solution có thể là: dashboard tổng hợp (10x giá trị) thay vì CSV export (1x)
🟢 DễBài 2
MVP: feature list cho Todo App → strip tới MVP (3 features)
Bạn có 15 feature ideas cho Todo App. Strip xuống còn đúng 3 features cho MVP. Giải thích tại sao 3 feature đó, và tại sao 12 feature còn lại vào backlog.
Framework chọn MVP features:
Câu hỏi: "Nếu không có feature này, user có thể dùng app không?"

MVP = (1) Tạo task, (2) Mark done, (3) Xem danh sách tasks

Backlog: tags, labels, priority, due date, reminders, share, comments, attachments, themes, keyboard shortcuts, history, analytics, bulk actions, templates

Rule: MVP phải giải quyết được core problem. Mọi thứ khác = hypothesis cần validate
🟡 Trung bìnhBài 3
Metrics: define 5 KPIs cho e-commerce app
Cho e-commerce app (product catalog + cart + checkout). Define 5 KPIs quan trọng nhất: tên metric, cách đo, target value, và tại sao metric đó quan trọng với business.
KPIs gợi ý:
1. Conversion Rate = Orders/Sessions × 100%. Target: ≥2%. Vì: revenue metric cốt lõi
2. Cart Abandonment Rate = (Carts created - Orders)/Carts × 100%. Target: <70%. Vì: identify UX friction
3. Average Order Value (AOV) = Revenue/Orders. Target: tăng 10%/quarter. Vì: revenue efficiency
4. Page Load Time (P95). Target: <2s. Vì: mỗi 100ms chậm = -1% conversion
5. Search Zero Results Rate = Searches trả 0 kết quả/Total searches. Target: <5%. Vì: catalog gap indicator
🟡 Trung bìnhBài 4
Trade-off: build feature X (2 tuần) vs improve performance (1 tuần)?
Feature X = "AI-powered product recommendations". Performance = "Reduce P95 API latency from 800ms to 200ms". Team có 2 tuần. Phân tích trade-offs và recommend quyết định có lý do.
Framework phân tích:
Data cần biết: Current conversion rate là bao nhiêu? Bounce rate ở trang nào cao? User feedback về gì?

Argument cho Performance: 800ms → nghiên cứu: mỗi 100ms chậm → -1% conversion. Nếu 50K sessions/month, improvement có thể +$X/month ngay lập tức. ROI đo được rõ ràng.

Argument cho Feature X: AI recommendations → AOV tăng, longer session, retention. Nhưng cần 2 tuần và kết quả không chắc chắn.

Recommendation mẫu: Nếu bounce rate cao → Performance first. Nếu conversion rate đã tốt → Feature X. Không có đúng/sai tuyệt đối, quan trọng là lý luận có data.
🔴 KhóBài 5
Product decision: phân tích feature request → accept/reject với lý do
Feature request: "Thêm tính năng social: user có thể follow nhau, share todo lists, và comment trên task của người khác." Phân tích đầy đủ theo Product Thinking framework và đưa ra quyết định accept/reject/defer với lý do chi tiết.
Phân tích framework:
User Problem: Feature này giải quyết gì? "Cộng tác nhóm" — nhưng đã có apps chuyên (Notion, Asana). Là Todo app thì core value là cá nhân hay nhóm?

Effort vs Value: Social features = L-XL (authentication cho shared resources, real-time, notification system, moderation, privacy). ROI uncertain.

Risks: Mission drift (cá nhân → nhóm), security complexity (shared data), moderation cost

Decision mẫu: "Defer — scope quá lớn, mission drift risk cao. Thay vào đó: M2 research — survey 50 users về collaboration need. Nếu >40% confirm → thiết kế minimal version: chỉ share list (không comment, không follow) — estimate lại."

Điểm quan trọng: không chỉ accept/reject — còn propose counter-proposal

📌 Tóm Tắt Bài 17

  • Engineer ≠ Code Monkey: Product Engineer hỏi "tại sao" trước khi code
  • User problem ≠ Business problem: feature tốt = giao điểm của cả hai
  • Functional vs Non-functional: non-functional phải design từ đầu, không thể add-on
  • MVP: strip mọi thứ không cần → ship core value → learn → iterate
  • Metrics: define KPIs trước khi build. Không đo được = không cải thiện được
  • ROI thinking: mọi feature = cost vs value analysis. Không phải feature nào cũng nên build
  • Push back: khi có technical reason, không phải khi không thích
Key Takeaway: Product thinking không phải là "làm việc của PM". Đó là kỹ năng giúp engineer build đúng thứ, đúng cách, đúng lúc. Senior engineer được pay cao hơn không chỉ vì biết code tốt hơn — mà vì họ biết quyết định cái gì cần code.
