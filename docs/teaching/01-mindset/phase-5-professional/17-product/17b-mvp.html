🚀 MVP — Ship Fast, Learn Fast

MVP (Minimum Viable Product) = strip mọi thứ không cần thiết → ship core value → học từ real users → iterate. Không phải ship sản phẩm tệ — mà ship đúng thứ tối thiểu.

Common misconception: MVP không phải "phiên bản lỗi". MVP là phiên bản đơn giản nhất có thể deliver core value và thu thập real feedback. Chất lượng vẫn phải đảm bảo — scope mới nhỏ.

📦 Strip to Core — 3 Stage

Full Vision
Auth Create post Comments Rich editor Mentions Reactions AI summary Dark mode Analytics dash Mobile app
↓ Strip to core — "nếu không có cái này, app vô nghĩa không?"
MVP
Auth Create post Comments → everything else = backlog
↓ Ship → Collect feedback → Learn → Prioritize next
v2 — Data-driven
Auth Create post Comments Rich editor Reactions (users asked) AI summary (low demand)
MVP test question: "Nếu không có feature này, liệu user có thể achieve core value của app không?" Nếu "có" → feature không phải core, cut khỏi MVP.

⚙️🎨 Functional vs Non-functional Requirements

Non-functional phải design từ đầu — không thể add-on sau. Junior thường bỏ qua đây.

⚙️ Functional (cái gì)
User register bằng email
Tạo và edit post
Comment trên post
Admin xem dashboard
Search posts theo title
📊 Non-functional (như thế nào)
API response < 200ms P95
Uptime 99.9%
Handle 1000 concurrent users
Password hashed, GDPR compliant
Accessible (WCAG 2.1 AA)

🔄 Build-Measure-Learn Loop

Lean Startup cycle — lặp lại mỗi 2-4 tuần:

💡 Idea / Hypothesis
→
⌨️ Build (small)
→
📊 Measure (data)
→
🧠 Learn
→
↺ Iterate
Cycle tốt: hypothesis rõ ràng trước khi build ("Nếu thêm X, retention tăng Y%"). Sau ship: verify hypothesis, không phải "xem có người dùng không".

🤔 Khi Nào Push Back Feature?

✅ Push back khi có technical reason:

  • Feature tạo security risk chưa được mitigate trong scope
  • Technical debt đã quá cao — thêm feature làm system fragile
  • Estimate unrealistic — "1 ngày" nhưng thực tế cần 1 tuần
  • Feature contradicts architectural decision đã ratify

❌ Không push back khi:

  • Không thích feature nhưng không có technical reason
  • Prefer tech stack khác mà không có data backup
  • Business decision — đó là role của PM/founder
🎯 Bài Tập Thực Hành
🟢 DễBài 1
Strip Todo App xuống còn 3 features cho MVP
Feature list: Create task, Edit task, Delete task, Mark done, Due dates, Labels/tags, Priority levels, Recurring tasks, Reminders, Subtasks, Comments, Share with team, Dark mode, Keyboard shortcuts, Import CSV. Strip xuống còn đúng 3 features. Justify từng decision.
MVP = (1) Create task, (2) Mark done, (3) View list

Test: "Nếu không có X, user có thể dùng app không?"
- Edit task? → Nếu không có thì phải delete và create lại → painful nhưng possible. KEEP vì UX tệ nếu thiếu
- Due dates? → User có thể ghi vào task title → cut
- Labels? → Nice-to-have → cut
- Dark mode? → Zero core value → cut

Real MVP là tối giản nhất cho phép user achieve "manage my tasks" — không phải "use all features I want"
🟡 Trung bìnhBài 2
Define MVP cho "E-commerce với AI recommendations"
Feature ideas: Product catalog, Search, Cart, Checkout, Payment (Stripe), User accounts, Order history, AI recommendations, Reviews, Wishlist, Product comparison, Email confirmation, Admin dashboard, Inventory management. Chia thành: MVP / V2 / V3 / Never. Justify.
MVP: Product catalog, Search (basic), Cart, Checkout, Stripe payment, Email confirmation
→ Core = user có thể browse và mua. Đây là core value.

V2 (after validation): User accounts, Order history, Admin dashboard, Basic inventory
→ Cần khi có returning customers

V3 (after product-market fit): Reviews, Wishlist, AI recommendations
→ AI recommendations cần data để train — không thể ship khi chưa có orders

Never (for now): Product comparison — complex, niche use case

Key: AI recommendations phụ thuộc vào data → phải có V1+V2 first. Đây là common mistake: ship AI feature khi chưa có đủ data
🔴 KhóBài 3
Design Build-Measure-Learn cycle cho feature mới
Feature hypothesis: "Nếu thêm 'Save for Later' button trên product page, Cart abandonment rate sẽ giảm 15%." Design full BML cycle: (1) Specific hypothesis, (2) What to build (smallest version), (3) Metrics cần measure, (4) How to interpret results, (5) What to do nếu hypothesis confirmed/rejected.
BML Design:
Hypothesis: "Adding 'Save for Later' reduces cart abandonment by ≥10% in 2 weeks"

Build (smallest): Single button, items saved in localStorage (no backend), simple "Saved Items" page. No account sync yet.

Measure:
- Cart abandonment rate (primary)
- "Save for Later" click rate (usage signal)
- Return rate of saved-item users vs normal
- Session duration on saved-items page

Interpret:
- ≥10% reduction + high click rate → confirmed, build full (backend sync, cross-device)
- ≥10% reduction + low click rate → maybe coincidental, run longer
- <10% reduction → abandonment cause is elsewhere (checkout friction? price? trust?)

If rejected: Investigate checkout flow, run separate A/B on payment options or trust signals

📌 Tóm Tắt — MVP

  • MVP = smallest version that delivers core value và thu thập real feedback
  • Strip test = "nếu không có X, user có achieve core value không?" Nếu "có" → cut
  • Non-functional = phải design từ đầu, không add-on sau. Security, performance, scale
  • Build-Measure-Learn = hypothesis → build → measure → learn → iterate
  • Push back khi có technical reason. Không push back vì personal preference
