Khái niệm 02
Trừu Tượng Hóa
Bỏ đi những chi tiết không cần thiết, giữ lại những gì quan trọng cho bài toán hiện tại.
🗺️ Ví dụ: Bản đồ vs Thực tế
Google Maps không hiện từng viên gạch, mỗi tòa nhà. Nó chỉ hiện những gì bạn cần để điều hướng.
🌆 Thực tế
Màu sắc, vật liệu, kiến trúc...
🗺️ Trừu tượng hóa
Chỉ: đường + địa điểm + khoảng cách
💻 Trong lập trình
Khi viết hàm sendEmail(to, subject, body), người dùng không cần biết SMTP, TCP/IP handshake, hay email server hoạt động thế nào. Đó là abstraction.
❌ Không abstraction
openSocket(host, 587)
auth(user, pass)
helo(domain)
rcptTo(email)
data(content)
quit()
✅ Có abstraction
sendEmail({
  to: 'user@mail.com',
  subject: 'Hello',
  body: 'Welcome!'
})
🎯 Key Takeaway
  • Ẩn đi chi tiết phức tạp, chỉ lộ giao diện cần thiết
  • Abstraction giúp code dễ đọc, dễ dùng, dễ thay thế
  • Câu hỏi hay: "Người dùng hàm này có cần biết điều này không?"

✓ Cùng Pattern: QUEUE (FIFO)

Tại sao Pattern Recognition quan trọng?
Khi bạn nhận ra "à, bài này giống Stack/Queue/Graph tôi từng làm", bạn không cần giải lại từ đầu. Đây là cách các senior engineer làm việc nhanh hơn junior.
🎯 Key Takeaway

  • Data Structures = patterns lưu trữ, Algorithms = patterns xử lý
  • Pattern mới = pattern cũ + biến thể nhỏ
Khái niệm 04
Tư Duy Thuật Toán
Mọi giải pháp đều có thể diễn đạt thành: Input → Xử lý → Output. Hãy luyện cách nghĩ có hệ thống.
🔄 Bấm để reveal từng bước của thuật toán
Bài toán: Tìm phần tử lớn nhất trong mảng
📥 Input: mảng [3, 7, 1, 9, 4]
↓
max = arr[0] = 3
↓
lặp qua từng phần tử
arr[i] > max?
↓
Có → cập nhật max
max = arr[i]
↓
hết mảng
📤 Output: max = 9
🎯 Key Takeaway
  • Viết pseudocode trước khi code — ngôn ngữ không quan trọng
  • Xác định rõ Input / Output trước khi nghĩ đến Process
  • Thuật toán tốt = đúng + nhanh + dễ đọc
Khái niệm 05
Edge Cases — Góc Tối
Code chạy đúng với dữ liệu bình thường chưa đủ. Phải test với những trường hợp bất thường.
⚠️ Bài toán: Tính điểm trung bình
Với hàm average(scores), những gì có thể xảy ra?
  • ⚡
    Mảng rỗng [] → chia cho 0 → NaN / ExceptionCRASH
  • ⚡
    Có giá trị null hoặc undefined trong mảngWRONG
  • ⚡
    Số âm hoặc số rất lớn (overflow)OVERFLOW
  • ⚡
    Chỉ 1 phần tử — kết quả có đúng không?CHECK
  • ⚡
    Dữ liệu string thay vì number: ["a", "b"]TYPE ERROR
Checklist Edge Case
EMPTY (rỗng) · ONE (1 phần tử) · MANY (số lượng lớn) · NULL (giá trị null/undefined) · NEGATIVE (số âm) · BOUNDARY (giá trị biên) · OVERFLOW (quá lớn)
🎯 Key Takeaway
  • Bug trong production thường đến từ edge cases bị bỏ qua
  • Hỏi: "Điều gì xảy ra nếu input là... rỗng? null? cực lớn?"
  • Viết unit test cho edge cases — không chỉ happy path

Không có giải pháp hoàn hảo. Mọi quyết định đều là sự đánh đổi.
⚖️ Chọn trade-off để xem cán cân nghiêng

Cách đưa ra quyết định
Đặt câu hỏi: "Bài toán của tôi ưu tiên điều gì?" Rồi chọn giải pháp phù hợp với ngữ cảnh, không phải giải pháp "tốt nhất trên lý thuyết".
🎯 Key Takeaway
  • Không có "đúng" hay "sai" — chỉ có "phù hợp" hay "không phù hợp"
  • Document lý do chọn trade-off để team hiểu sau này
  • Trade-off thay đổi khi ngữ cảnh thay đổi (scale, budget, team)
Khái niệm 07
Debugging Mindset
Debug không phải may rủi. Đó là phương pháp khoa học áp dụng cho code.
🔬 Scientific Method cho Code
1
Quan sát
Bug xảy ra khi nào? Input gì? Error message gì?
2
Giả thuyết
"Có lẽ vì... Tôi nghĩ nguyên nhân là..."
3
Thí nghiệm
Thêm log, viết test, reproduce bug
4
Kết quả
Bug xác nhận? Giả thuyết đúng/sai?
5
Sửa
Fix nguyên nhân gốc, không phải triệu chứng
6
Confirm
Test lại, đảm bảo không break gì khác
❌ Anti-pattern: Debug mò
"Thử thay cái này xem... không được. Thử cái kia... cũng không. Thêm console.log ở đây... ở đó..." — Không có phương pháp = mất hàng giờ cho lỗi đơn giản.
🎯 Key Takeaway
  • Reproduce bug trước — nếu không reproduce được, chưa debug được
  • Thay đổi một biến mỗi lần — không thay nhiều thứ cùng lúc
  • Đọc error message KỸ — thường có câu trả lời ngay trong đó
Bài Tập Thực Hành
Phân Rã Bài Toán Thực Tế
Áp dụng tư duy tính toán vào bài toán quen thuộc.
📚 Bài toán: Tổ chức lịch thi cho trường đại học
Trường có 500 sinh viên, 50 môn học, 20 phòng thi. Không sinh viên nào bị trùng lịch 2 môn cùng lúc. Phòng không được vượt quá sức chứa. Giám thị phải được phân công.
Decomposition: Chia thành: quản lý sinh viên, quản lý phòng, quản lý môn học, phân công giám thị, generate lịch, kiểm tra xung đột
Abstraction: Mô hình hóa: sinh viên ↔ môn học (enrollment), phòng ↔ slot thời gian, môn ↔ slot (assignment)
Pattern: Đây là bài toán Graph Coloring — môn học là node, xung đột là edge, màu là time slot
Algorithm: 1. Build conflict graph → 2. Color graph (greedy) → 3. Assign rooms by capacity → 4. Assign supervisors
Edge Cases: Môn có 500 sinh viên (phải thi nhiều phòng), giám thị nghỉ ốm, phòng bảo trì, môn online
Insight
Bài toán "tổ chức lịch thi" và bài toán "tô màu bản đồ" nhìn bề ngoài rất khác nhau nhưng cùng một pattern. Đây là sức mạnh của Computational Thinking.
🏆 Tổng kết Phase 1.1
  • Decomposition — chia nhỏ bài toán
  • Abstraction — bỏ chi tiết không cần
  • Pattern Recognition — nhận ra điểm chung
  • Algorithmic Thinking — Input → Process → Output
  • Edge Cases — luôn hỏi "điều gì có thể sai?"
  • Trade-off — không có hoàn hảo, chỉ có phù hợp
  • Debug — phương pháp khoa học, không phải may rủi
