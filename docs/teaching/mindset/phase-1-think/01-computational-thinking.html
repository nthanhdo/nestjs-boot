Khái niệm 02
Trừu Tượng Hóa
Bỏ đi những chi tiết không cần thiết, giữ lại những gì quan trọng cho bài toán hiện tại.
🗺️ Ví dụ: Bản đồ vs Thực tế
Google Maps không hiện từng viên gạch, mỗi tòa nhà. Nó chỉ hiện những gì bạn cần để điều hướng.
🌆 Thực tế
Màu sắc, vật liệu, kiến trúc...
🗺️ Trừu tượng hóa
Chỉ: đường + địa điểm + khoảng cách
💻 Trong lập trình
Khi viết hàm sendEmail(to, subject, body), người dùng không cần biết SMTP, TCP/IP handshake, hay email server hoạt động thế nào. Đó là abstraction.

✅ Có abstraction
sendEmail({
  to: 'user@mail.com',
  subject: 'Hello',
  body: 'Welcome!'
})
🎯 Key Takeaway
  • Ẩn đi chi tiết phức tạp, chỉ lộ giao diện cần thiết
  • Abstraction giúp code dễ đọc, dễ dùng, dễ thay thế
  • Câu hỏi hay: "Người dùng hàm này có cần biết điều này không?"

Khái niệm 04
Tư Duy Thuật Toán
Mọi giải pháp đều có thể diễn đạt thành: Input → Xử lý → Output. Hãy luyện cách nghĩ có hệ thống.
🔄 Bấm để reveal từng bước của thuật toán
Bài toán: Tìm phần tử lớn nhất trong mảng
📥 Input: mảng [3, 7, 1, 9, 4]
↓
max = arr[0] = 3
↓
lặp qua từng phần tử
arr[i] > max?
↓
Có → cập nhật max
max = arr[i]
↓
hết mảng
📤 Output: max = 9
🎯 Key Takeaway
  • Viết pseudocode trước khi code — ngôn ngữ không quan trọng
  • Xác định rõ Input / Output trước khi nghĩ đến Process
  • Thuật toán tốt = đúng + nhanh + dễ đọc
Khái niệm 05
Edge Cases — Góc Tối
Code chạy đúng với dữ liệu bình thường chưa đủ. Phải test với những trường hợp bất thường.
⚠️ Bài toán: Tính điểm trung bình
Với hàm average(scores), những gì có thể xảy ra?
  • ⚡
    Mảng rỗng [] → chia cho 0 → NaN / ExceptionCRASH
  • ⚡
    Có giá trị null hoặc undefined trong mảngWRONG
  • ⚡
    Số âm hoặc số rất lớn (overflow)OVERFLOW
  • ⚡
    Chỉ 1 phần tử — kết quả có đúng không?CHECK
  • ⚡
    Dữ liệu string thay vì number: ["a", "b"]TYPE ERROR
Checklist Edge Case
EMPTY (rỗng) · ONE (1 phần tử) · MANY (số lượng lớn) · NULL (giá trị null/undefined) · NEGATIVE (số âm) · BOUNDARY (giá trị biên) · OVERFLOW (quá lớn)
🎯 Key Takeaway
  • Bug trong production thường đến từ edge cases bị bỏ qua
  • Hỏi: "Điều gì xảy ra nếu input là... rỗng? null? cực lớn?"
  • Viết unit test cho edge cases — không chỉ happy path

Khái niệm 07
Debugging Mindset
Debug không phải may rủi. Đó là phương pháp khoa học áp dụng cho code.
🔬 Scientific Method cho Code
1
Quan sát
Bug xảy ra khi nào? Input gì? Error message gì?
2
Giả thuyết
"Có lẽ vì... Tôi nghĩ nguyên nhân là..."
3
Thí nghiệm
Thêm log, viết test, reproduce bug
4
Kết quả
Bug xác nhận? Giả thuyết đúng/sai?
5
Sửa
Fix nguyên nhân gốc, không phải triệu chứng
6
Confirm
Test lại, đảm bảo không break gì khác
❌ Anti-pattern: Debug mò
"Thử thay cái này xem... không được. Thử cái kia... cũng không. Thêm console.log ở đây... ở đó..." — Không có phương pháp = mất hàng giờ cho lỗi đơn giản.
🎯 Key Takeaway
  • Reproduce bug trước — nếu không reproduce được, chưa debug được
  • Thay đổi một biến mỗi lần — không thay nhiều thứ cùng lúc
  • Đọc error message KỸ — thường có câu trả lời ngay trong đó
Bài Tập Thực Hành
Phân Rã Bài Toán Thực Tế
Áp dụng tư duy tính toán vào bài toán quen thuộc.
📚 Bài toán: Tổ chức lịch thi cho trường đại học
Trường có 500 sinh viên, 50 môn học, 20 phòng thi. Không sinh viên nào bị trùng lịch 2 môn cùng lúc. Phòng không được vượt quá sức chứa.
Decomposition: Chia thành: quản lý sinh viên, quản lý phòng, quản lý môn học, phân công giám thị, generate lịch, kiểm tra xung đột
Abstraction: Mô hình hóa: sinh viên ↔ môn học (enrollment), phòng ↔ slot thời gian, môn ↔ slot (assignment)
Pattern: Đây là bài toán Graph Coloring — môn học là node, xung đột là edge, màu là time slot
Algorithm: 1. Build conflict graph → 2. Color graph (greedy) → 3. Assign rooms by capacity → 4. Assign supervisors

Ex 1 Decompose "đặt pizza online" thành các bước nhỏ 🟢 Dễ ▶
Bạn được giao task: xây dựng hệ thống đặt pizza online. Hãy áp dụng Decomposition để phân rã bài toán này thành các module độc lập. Mỗi module phải có thể phát triển và test riêng lẻ.
💡 Gợi ý: Nghĩ theo luồng người dùng — từ lúc mở app đến khi nhận pizza. Mỗi bước có thể làm gì sai?
Decomposition của hệ thống đặt pizza:
  • 📋 MenuModule — hiển thị sản phẩm, giá, tùy chọn topping
  • 🛒 CartModule — thêm/xóa/sửa items, tính tổng tiền
  • 👤 UserModule — đăng nhập, địa chỉ giao hàng, lịch sử đơn
  • 💳 PaymentModule — xử lý thanh toán, mã giảm giá, hoàn tiền
  • 📦 OrderModule — tạo đơn, trạng thái đơn, hủy đơn
  • 🚗 DeliveryModule — tính thời gian, phân tài xế, tracking
  • 🔔 NotificationModule — SMS/email/push khi đơn thay đổi trạng thái
Mỗi module có thể được phát triển bởi team riêng biệt và test độc lập.
Ex 2 Tìm pattern trong 3 bài toán khác nhau nhưng cùng cấu trúc 🟢 Dễ ▶
Đọc 3 bài toán sau và xác định chúng có cùng pattern gì:

A. Trình duyệt Chrome có nút Back/Forward để điều hướng lịch sử trang web.
B. Ctrl+Z trong Word/Excel để undo thao tác vừa làm.
C. Git có thể checkout về bất kỳ commit nào trong lịch sử.
💡 Gợi ý: Nghĩ về cấu trúc dữ liệu nào phù hợp để lưu lịch sử và navigate back/forward.
Cả 3 đều dùng Stack + History Pattern:
// Pattern chung: Stack-based History class HistoryManager { private past: T[] = [] private future: T[] = [] push(state: T) { this.past.push(state) this.future = [] // clear future khi action mới } undo() { // Back / Ctrl+Z / git checkout const state = this.past.pop() this.future.push(state) return state } redo() { // Forward / Ctrl+Y const state = this.future.pop() this.past.push(state) return state } }

Nhận ra pattern → implement 1 lần → dùng cho mọi use case!

Abstraction phụ thuộc vào người dùng và mục đích. Hãy mô tả "xe hơi" (interface/model) cho 3 đối tượng:

A. Tài xế Uber
B. Thợ sửa xe
C. Hệ thống thanh toán phí đường bộ (ETC)
💡 Gợi ý: Mỗi đối tượng chỉ cần biết những thuộc tính phục vụ cho công việc của họ. Hãy bỏ qua mọi chi tiết không liên quan.
3 abstractions khác nhau cho cùng 1 đối tượng:

Ex 4 Edge cases: liệt kê 10 edge cases cho form đăng ký tài khoản 🟡 Trung bình ▶
Form đăng ký có các fields: email, password, username, date of birth. Hãy liệt kê ít nhất 10 edge cases mà hệ thống cần xử lý. Với mỗi edge case, cho biết loại lỗi và cách xử lý.
💡 Gợi ý: Dùng checklist EMPTY · ONE · BOUNDARY · NULL · OVERFLOW · FORMAT · DUPLICATE · SECURITY
10 edge cases cần xử lý:
  1. Email không có @ — FORMAT ERROR → "Email không hợp lệ"
  2. Email đã tồn tại — DUPLICATE → "Email này đã được đăng ký"
  3. Password quá ngắn (< 8 ký tự) — BOUNDARY → "Mật khẩu tối thiểu 8 ký tự"
  4. Password chứa toàn số / toàn chữ — WEAK → "Cần kết hợp chữ số và ký tự đặc biệt"
  5. Username có khoảng trắng — FORMAT → Trim hoặc báo lỗi
  6. Username chứa SQL injection — SECURITY → Sanitize input
  7. Date of birth trong tương lai — LOGICAL → "Ngày sinh không hợp lệ"
  8. Tuổi dưới 13 — BUSINESS RULE → "Cần có sự đồng ý của phụ huynh"
  9. Email quá dài (> 254 ký tự) — OVERFLOW → "Email không hợp lệ"
  10. Tất cả fields để trống — EMPTY → "Vui lòng điền đầy đủ thông tin"
Ex 5 Trade-off analysis: chọn giữa 2 giải pháp caching 🔴 Khó ▶
Bạn cần cache dữ liệu user profile. Có 2 giải pháp:

Giải pháp A: In-memory cache — Lưu trong RAM của server
- Tốc độ: cực nhanh (~0.1ms)
- Memory: tốn RAM
- Nhược điểm: mất data khi restart server, không share giữa nhiều server

Giải pháp B: Redis cache — Lưu trong Redis server riêng
- Tốc độ: nhanh (~1-5ms)
- Memory: tốn infrastructure
- Ưu điểm: persistent, share được, TTL tự động

Hãy phân tích trade-off và đề xuất giải pháp cho 2 context: (1) startup nhỏ 1 server và (2) production có 10 server instances.
💡 Gợi ý: Trade-off không có đáp án đúng/sai — phụ thuộc vào context. Hãy liệt kê criteria và đánh giá từng giải pháp.
Trade-off Analysis:
Context 1: Startup 1 server
✅ Chọn In-memory
- Không cần infrastructure thêm
- 0 latency overhead
- Đủ dùng khi traffic thấp
- Khi cần scale → migrate sang Redis
Context 2: Production 10 servers
✅ Chọn Redis
- 10 servers = 10 in-memory caches khác nhau → cache invalidation hell
- Redis = single source of truth
- TTL tự động, persist qua restart
Bài học: Không có "best solution" — chỉ có "best for this context". Document lý do bạn chọn và khi nào cần review lại quyết định này.
