Khái niệm 01
Data & State
Lập trình là quản lý dữ liệu thay đổi theo thời gian. State là "trạng thái hiện tại" của chương trình.

State Management là gì?
Khi ứng dụng lớn, state thay đổi ở nhiều nơi → khó theo dõi → bug khó tìm. Ðây là lý do React có useState, Redux có Store — để quản lý state có hệ thống.
🎯 Key Takeaway
  • State = dữ liệu + vị trí hiện tại + lịch sử thay đổi
  • Bug thường là: state không nhất quán giữa các phần của app
  • Nguyên tắc: state phải có nguồn duy nhất (Single Source of Truth)
Khái niệm 02
Control Flow
Chương trình không chạy thẳng từ trên xuống. Nó rẽ nhánh, lặp, nhảy — đây là Control Flow.
If / Else — Rẽ nhánh
if (score >= 8) {
  grade = "Giỏi"
} else if (score >= 6) {
  grade = "Khá"
} else {
  grade = "TB"
}
Loop — Lặp
for (let i = 0; i < n; i++) {
  process(items[i])
}

while (!done) {
  step = next()
}
🌊 Control Flow như nước chảy
Hãy hình dung code như ống nước. if/else là chỗ nước chọn đường. loop là chỗ nước quay vòng. function call là nước đi vào nhánh phụ rồi về. return là chốt chặn — nước dừng lại tại đây.
🎯 Key Takeaway
  • Trace qua code bằng tay với input cụ thể để debug control flow
  • Loop luôn cần điều kiện dừng rõ ràng
  • Early return giúp code phẳng, dễ đọc hơn nested if/else

Functions nhỏ kết hợp tạo ra chức năng lớn:

Nguyên tắc thiết kế Function
Do one thing — hàm chỉ làm 1 việc  ·  Small — ≤ 20 dòng lý tưởng  ·  Descriptive name ·  Ít tham số — ≤ 3
🎯 Key Takeaway
  • Function tốt = đọc tên biết làm gì, không cần đọc code bên trong
  • Composition mạnh hơn tạo 1 hàm siêu to làm hết mọi thứ
  • Test dễ nhất khi function là pure (không side effects)
Khái niệm 04
Module & Dependency
Module là nhóm các functions liên quan. Dependency là mối quan hệ giữa các modules.
❌ Coupling cao (Tight Coupling)
🐙 UserModule
login, register, profile,
sendEmail, generatePDF,
processPayment, createOrder
ĐA TRÁCH NHIỆM
Thay đổi một thứ → phá vỡ nhiều thứ
✅ Cohesion cao (Loose Coupling)
👤 UserModule
login, register, profile
📧 MailModule
sendEmail, templates
💳 PaymentModule
processPayment, refund
Quy tắc vàng
High cohesion + Low coupling = codebase dễ maintain, dễ test, dễ thay thế.
🎯 Key Takeaway
  • Module = ranh giới logic, không phải ranh giới file
  • Khi module A biết quá nhiều về module B → coupling cao → nguy hiểm
  • Dependency Injection giúp giảm coupling, tăng testability
Khái niệm 05
Interface & Abstraction
Interface là "hợp đồng" — quy định những gì bạn cần cung cấp. Không quan tâm bạn thực hiện nó thế nào.
🔌 Ví dụ: Ẩ điện — Thiết bị
Ầ điện có interface chuẩn (220V, 50Hz, 2 lỗ). Bất kỳ thiết bị nào đúng interface đều cắm được — TV, quạt, máy tính, không cần biết thiết bị làm gì bên trong.

🎯 Key Takeaway
  • Program to an interface, not an implementation
  • Interface cho phép swap implementation mà không sửa caller
  • Test dùng mock implementation của interface — không cần real service
Khái niệm 06
Composition over Inheritance
Kế thừa tạo ra cây phân cấp cứng nhắc. Composition linh hoạt hơn — lắp ghép như Lego.
🌳 Inheritance — Cây

🧩 Composition — Lego

🎯 Key Takeaway
  • Inheritance → "is-a" relationship (Duck IS an Animal)
  • Composition → "has-a" relationship (Duck HAS ability to swim)
  • Composition dễ thay đổi hơn — thêm/bỏ behavior mà không phá hierarchy
Khái niệm 07
Side Effects & Pure Functions
Pure function: cùng input → cùng output, không thay đổi gì bên ngoài. Đây là mục tiêu lý tưởng.
❌ Impure Function
let total = 0

function addToTotal(n) {
  total += n // side effect!
  console.log(total)
  return total
}
Gọi 2 lần với cùng input → kết quả khác nhau → khó test
✅ Pure Function
function add(a, b) {
  return a + b
}

// Luôn đúng:
add(2, 3) === 5
add(2, 3) === 5
Predictable, dễ test, dễ cache, dễ parallelize
Side effects không phải luôn xấu
Ghi DB, gọi API, in màn hình — đây đều là side effects và cần thiết. Nguyên tắc: isolate side effects — đẩy chúng ra rìa, giữ core logic pure.
🎯 Key Takeaway
  • Maximize pure functions → minimize surface area của bugs
  • Side effects phải rõ ràng — đặt tên hàm phản ánh (saveUser, sendEmail)
  • Pure functions dễ test: không cần mock, không cần setup
Checklist + Bài tập
5 Câu Hỏi & Thực Hành
Trước khi viết code, hãy tự hỏi 5 câu này. Click vào từng câu khi bạn đã suy nghĩ xong.
  • 1. Bài toán thực sự là gì?Không phải "implement feature X" mà là "user cần đạt được kết quả Y".
  • 2. Code này sẽ thay đổi như thế nào?Thiết kế cho change, không chỉ cho requirement hiện tại.
  • 3. Có giải pháp đơn giản hơn không?KISS principle. Nếu có thể solve bằng 10 dòng, đừng dùng design pattern phức tạp.
  • 4. Điều gì có thể sai?Edge cases, failure modes, race conditions.
  • 5. Làm thế nào để test điều này?Nếu khó test → design có vấn đề. Good design = testable design.
🏆 Hoàn thành checklist!
Bạn đã suy nghĩ qua 5 câu hỏi cốt lõi. Đây là mindset của một software engineer chuyên nghiệp!

🏋 Bài tập thực hành

Ex 1 Vẽ Control Flow diagram cho hàm tính điểm trung bình 🌺 Dễ ►
Cho hàm calculateGrade(scores: number[]): string. Xác định TẤT CẢ các nhánh Control Flow và liệt kê các điều kiện biên cần xử lý.
💡 Gợi ý: Nghĩ: Input → Validate → Calculate avg → Compare thresholds → Return. Mỗi bước rẽ nhánh ở đâu?
Tất cả control flow branches:
START ↓ [Input: scores array] ↓ {scores.length === 0?} → YES → return "N/A" ← edge case! ↓ NO {có null/undefined?} → YES → filter hoặc throw ↓ NO [avg = sum / length] ↓ {avg >= 8.5?} → YES → return "Giỏi" ↓ NO {avg >= 7.0?} → YES → return "Khá" ↓ NO {avg >= 5.0?} → YES → return "Trung bình" ↓ NO return "Yếu" END

Có 5 nhánh return cần test riêng. Mỗi threshold cần test = và < (boundary values).

Ex 2 Tách 1 hàm 50 dòng thành 3-4 hàm nhỏ 🌺 Dễ ►
Xác định các nhóm logic trong hàm dưới và đề xuất cách tách thành 3-4 hàm nhỏ, mỗi hàm làm 1 việc:

async function handleRegistration(req) { /* validate + check duplicate + hash + save + sendEmail */ }
💡 Gợi ý: Mỗi comment section = 1 hàm riêng. Hàm controller chỉ orchestrate.
function validateRegistrationData(body) { /* validates email + password */ } async function assertEmailNotTaken(email) { /* DB lookup, throws if exists */ } async function createUserRecord(email, password) { /* hash + save to DB */ } // Controller: chỉ orchestrate async function handleRegistration(req, res) { validateRegistrationData(req.body) await assertEmailNotTaken(req.body.email) const user = await createUserRecord(req.body.email, req.body.password) await mailer.sendWelcome(user) res.json({ success: true, userId: user.id }) } // Mỗi hàm có thể test độc lập!
Ex 3 Xác định side effects trong đoạn code cho sẵn 🏱 Trung bình ►
Liệt kê TẤT CẢ side effects trong hàm sau, phân loại "cần thiết" hay "nên tách":

async function fetchUser(id) { requestCount++; console.log(...); const user = await api.get(...); cache.set(id, user); localStorage.setItem('lastUser', id); document.title = user.name; return user; }
💡 Gợi ý: Side effect = bất kỳ thay đổi nào bên ngoài function scope
  1. requestCount++ — mutation global var — Nên tách
  2. console.log — I/O side effect — Dùng injected logger
  3. api.get() — network call — Cần thiết (core purpose)
  4. cache.set() — external state mutation — Borderline
  5. localStorage.setItem — không liên quan fetchUser — Nên tách hoàn toàn
  6. document.title = — DOM trong data layer — Sai! Lên UI layer
Ex 4 Thiết kế interface cho module "Notification" 🏱 Trung bình ►
Thiết kế TypeScript interface cho Notification Service hỗ trợ Email/SMS/Push. Yêu cầu: caller không biết kênh nào, dễ thêm kênh mới (Slack, Webhook) mà không sửa caller code, hỗ trợ batch send và delivery status.
💡 Gợi ý: Interface Segregation — có thể cần nhiều interface nhỏ. Orchestrator pattern.
interface INotification { to: string; subject?: string; body: string } // All channels implement this interface INotificationSender { send(n: INotification): Promise<DeliveryResult> sendBatch(ns: INotification[]): Promise<DeliveryResult[]> readonly channel: 'email' | 'sms' | 'push' } // Caller uses this only interface INotificationService { notify(channel: string, n: INotification): Promise<DeliveryResult> register(sender: INotificationSender): void } // Adding Slack = new SlackSender implements INotificationSender // Zero changes to caller code!

📝 Tóm tắt bài học

  • ✅ State Management — Single Source of Truth, tánh state không nhất quán
  • ✅ Control Flow — rẽ nhánh và lặp có hệ thống, tánh infinite loop và off-by-one
  • ✅ Function Design — do one thing, small, descriptive name, ≤3 params
  • ✅ Module & Dependency — high cohesion + low coupling
  • ✅ Interface & Abstraction — program to contract, swap implementations freely
  • ✅ Composition over Inheritance — has-a linh hoạt hơn is-a
  • ✅ Pure Functions — predictable, testable — isolate side effects
