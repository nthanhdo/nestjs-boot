Khái niệm 01
Đặt Tên Có Ý Nghĩa
"Code được đọc nhiều hơn viết." Tên biến, hàm, class phải tự giải thích mà không cần comment.
❌ Tên xấu
let d = 86400
let tmp = getList()
function proc(l) {
  return l.filter(i =>
    i.f === 1)
}
✅ Tên tốt
const SECONDS_PER_DAY = 86400
const activeUsers = getUsers()
function filterActive(users) {
  return users.filter(user =>
    user.isActive === true)
}
📋 Quy tắc đặt tên
✅ BIẾN — noun phrase
elapsedTimeInDays
userAccountBalance
isEmailVerified
MAX_RETRY_COUNT
✅ HÀM — verb phrase
getUserById()
sendWelcomeEmail()
calculateMonthlyFee()
isValidEmail()
🎯 Key Takeaway
  • Nếu cần comment để giải thích tên → tên đó cần đổi
  • Tránh: d, tmp, data, info, manager, processor (quá mơ hồ)
  • Boolean: is/has/can prefix (isActive, hasPermission, canEdit)
Khái niệm 02
Hàm Nhỏ
Hàm lý tưởng đủ nhỏ để thấy toàn bộ trên màn hình. Khi hàm làm nhiều việc → tách ra.
❌ processUserRegistration() — 100 dòng
Validate input + Hash password + Save DB + Send email + Create session + Log event + Notify admin...
✅ 5 hàm nhỏ, mỗi hàm 15-20 dòng
validateInput()
hashPassword()
saveUser()
sendEmail()
createSession()
Rule of Thumb
Nếu bạn cần scroll để đọc hết 1 hàm → hàm đó quá dài. Nếu bạn cần comment "// Step 1:", "// Step 2:" trong 1 hàm → đó là dấu hiệu cần tách hàm.
🎯 Key Takeaway
  • Hàm nhỏ → dễ đọc, dễ test, dễ tái sử dụng, dễ debug
  • Mỗi hàm chỉ làm 1 việc ở 1 level abstraction
  • Extract method là refactoring an toàn nhất để học
Khái niệm 03
DRY · KISS · YAGNI
Ba nguyên tắc cốt lõi giúp code không bị "thối" theo thời gian.
🔁 DRY — Don't Repeat Yourself
❌ Lặp code
// Ở User service
email = email.trim()
        .toLowerCase()

// Ở Auth service
email = email.trim()
        .toLowerCase()
✅ Extract
function normalizeEmail(e) {
  return e.trim().toLowerCase()
}

// Dùng ở mọi nơi
normalizeEmail(email)
💎 KISS — Keep It Simple, Stupid
❌ Over-engineered
class AbstractUserFactory
extends BaseEntityBuilder
implements ICreatable {
  createFromStrategy()
  ...
}
✅ Đủ đơn giản
function createUser(data) {
  return { ...data,
    id: uuid(),
    createdAt: new Date()
  }
}
🚫 YAGNI — You Aren't Gonna Need It
❌ Anti-pattern
"Tôi sẽ thêm multi-tenancy ngay từ đầu... thêm caching layer... thêm plugin system... thêm A/B testing framework..."
→ Tốn 3 tuần cho tính năng mà chưa ai cần.
✅ Build when needed
Ship MVP → nhận feedback → refactor → thêm tính năng thực sự được yêu cầu.
🎯 Key Takeaway
  • DRY: mỗi piece of knowledge có 1 nơi duy nhất trong hệ thống
  • KISS: simple code làm đúng > clever code làm sai
  • YAGNI: đừng viết code cho tương lai tưởng tượng
Khái niệm 04
SOLID Principles
5 nguyên tắc OOP giúp code linh hoạt, dễ mở rộng, ít bug. Click vào từng card để xem chi tiết.
S
Single Responsibility
Mỗi class chỉ có 1 lý do để thay đổi
// ❌ UserService làm quá nhiều
class UserService {
  getUser() { ... }
  sendEmail() { ... } ← sai chỗ
  generatePDF() { ... } ← sai chỗ
}

// ✅ Mỗi service 1 việc
UserService, MailService, PdfService
O
Open/Closed
Mở để mở rộng, đóng để sửa đổi
// Thêm shape mới không cần
// sửa code cũ
interface Shape {
  area(): number
}
class Circle implements Shape { }
class Square implements Shape { }
L
Liskov Substitution
Subclass thay thế được parent class
// Code dùng Bird phải hoạt động
// với mọi subclass của Bird
function makeFly(bird: Bird) {
  bird.fly() ← phải work
}
// Penguin extends Bird ← sai!
// Penguin không bay được
I
Interface Segregation
Nhiều interface nhỏ hơn 1 interface lớn
// ❌ 1 interface quá rộng
interface Worker { work(); eat(); sleep() }

// ✅ Tách nhỏ
interface Workable { work() }
interface Feedable { eat() }
D
Dependency Inversion
Depend on abstractions, not concretions. High-level không phụ thuộc low-level.
// ❌ Tight coupling
class OrderService {
  private db = new MySQLDatabase() ← bad
}

// ✅ Inject dependency
class OrderService {
  constructor(private db: IDatabase) {} ← good
}
🎯 Key Takeaway
  • SOLID không phải rules phải follow mọi lúc — đây là guidelines
  • Áp dụng khi thấy code khó test, khó thay đổi, hay break
  • Bắt đầu với S và D — 80% benefit từ 2 nguyên tắc này
Khái niệm 05
Code Smells
Code smells là dấu hiệu cảnh báo — code có thể chạy đúng nhưng có vấn đề về thiết kế. Click vào từng smell để nhận diện.
🔍 Tìm code smells trong đoạn code sau:
function doThings(a, b, c, d, e, f) {
  if (a === 1) {
    if (b === 2) {
      if (c === 3) { // Arrow code!
        if (d === 4) {
          result = process(e, f)
        }
      }
    }
  }
  const x = a * 0.1728
  return x
}
📦 Long Parameter List (6 params)
🏹 Arrow Code / Deeply Nested
🔮 Magic Number (0.1728)
🔁 Duplicate Code
💀 Dead Code
🗒️ Danh sách Code Smells phổ biến
Long Method — hàm > 30 dòng
God Class — class biết quá nhiều
Shotgun Surgery — 1 change → sửa nhiều nơi
Feature Envy — method dùng data class khác nhiều
Data Clumps — nhóm biến luôn đi cùng nhau
Comments — comment giải thích code xấu
🎯 Key Takeaway
  • Code smell ≠ bug, nhưng là tiền thân của bug
  • Khi thấy smell → không phải lúc nào cũng refactor ngay, nhưng ghi chú lại
  • Boy Scout Rule: "Leave the code cleaner than you found it"
Khái niệm 06
Refactoring từng bước
Refactoring = thay đổi cấu trúc code mà không thay đổi behavior. Click để xem từng bước.
❌ Code gốc — messy
function a(u) {
  if (!u.email || !u.email.includes('@')) return false
  if (!u.password || u.password.length < 8) return false
  db.save({ email: u.email.trim().toLowerCase(), password: hash(u.password), createdAt: new Date() })
  mail(u.email, 'Welcome!', '...')
  return true
}
🔧 Bước 1: Extract method
function isValidEmail(email) {
  return !!email && email.includes('@')
}
function isValidPassword(pw) {
  return !!pw && pw.length >= 8
}
function a(u) {
  if (!isValidEmail(u.email)) return false
  if (!isValidPassword(u.password)) return false
  ...
}
🏷️ Bước 2: Rename + Separate concerns
function registerUser(userData) {
  if (!isValidEmail(userData.email)) return false
  if (!isValidPassword(userData.password)) return false
  const user = buildUser(userData)
  db.save(user)
  sendWelcomeEmail(user.email)
  return true
}
✅ Final: Clean, readable, testable
// Mỗi hàm 1 việc, tên rõ ràng
async function registerUser(userData: CreateUserDto) {
  validateRegistrationData(userData)
  const user = await userService.create(userData)
  await mailService.sendWelcome(user)
  return user
}
🎯 Key Takeaway
  • Refactor thành từng bước nhỏ, test sau mỗi bước
  • Không refactor và thêm feature cùng lúc — nguy hiểm
  • Có test coverage trước khi refactor — safety net
Khái niệm 07
Technical Debt
Nợ kỹ thuật tích lũy theo thời gian. Giống như lãi suất ngân hàng — càng để lâu, càng tốn kém.
📉 Velocity giảm theo thời gian khi không refactor
💸 Deliberate Debt
Cố tình "nợ" để ship nhanh. Chấp nhận được nếu có kế hoạch trả nợ rõ ràng. "Cần ship trong 2 ngày, sau đó refactor sprint sau."
☠️ Reckless Debt
Không biết mình đang nợ. Không có kế hoạch. Accumulate mãi đến khi team không dám đụng vào code nữa.
🎯 Key Takeaway
  • Tech debt không phải xấu — là công cụ nếu quản lý có ý thức
  • Track tech debt: ghi vào backlog, schedule refactoring sprints
  • 20% thời gian sprint cho tech debt — đây là investment, không phải waste
