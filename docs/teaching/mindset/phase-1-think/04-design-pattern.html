Quan trọng
Học pattern không phải để áp dụng mọi lúc. Mà để nhận ra khi nào thì pattern này phù hợp — và khi nào thì không.
Creational Patterns
Cách Tạo Objects
Kiểm soát quá trình khởi tạo objects — linh hoạt, có thể cấu hình, dễ thay thế.
Factory — Nhà máy sản xuất objects
Thay vì new Dog() hay new Cat(), bạn gọi AnimalFactory.create(type). Factory quyết định tạo loại nào.
🐕 'dog'
🐈 'cat'
🐦 'bird'
→
🏭 AnimalFactory
.create(type)
→
?
✅ Dùng khi
Không biết trước sẽ tạo object loại nào. Type phụ thuộc vào runtime data. Muốn ẩn logic khởi tạo phức tạp.
Factory Method · Abstract Factory
❌ Không dùng khi
Chỉ có 1 loại object. Logic tạo object đơn giản. Việc thêm Factory tạo ra complexity không cần thiết.
Singleton — Chỉ 1 instance duy nhất
Đảm bảo class chỉ có 1 instance và cung cấp global access point. Ví dụ: Logger, DB Connection Pool, Config.
Client A
getInstance()
→
💎 DatabasePool
Instance: #0x4A2F
maxConnections: 10
←
Client B
getInstance()
Cả hai Client đều nhận cùng 1 instance: #0x4A2F
✅ Dùng khi
Cần đúng 1 instance (DB connection, logger, config). Cần global access point được kiểm soát.
❌ Cảnh báo
Global state = khó test. Overuse Singleton = anti-pattern. Trong NestJS, dùng @Injectable() scope thay thế.
Builder — Tạo object phức tạp từng bước
Tách construction của complex object khỏi representation. Tạo object có nhiều optional params một cách readable.
// ❌ Không có Builder
new HttpRequest('GET', '/api', null, {}, 30, true)

// ✅ Có Builder
new HttpRequestBuilder()
  .method('GET')
  .url('/api/users')
  .timeout(30)
  .withAuth()
  .build()
🎯 Key Takeaway
  • Factory: khi cần linh hoạt trong việc tạo objects
  • Singleton: dùng cẩn thận, tránh global state
  • Builder: khi object có nhiều optional configurations
Structural Patterns
Cấu Trúc Classes & Objects
Cách tổ chức classes và objects để tạo cấu trúc lớn hơn, linh hoạt hơn.
Adapter — Chuyển đổi interface
Giống bộ chuyển đổi ổ điện khi đi nước ngoài. Cho phép hai interfaces không tương thích làm việc với nhau.
🇺🇸 US Plugin
charge(110V)
→
🔌 Adapter
110V → 220V
→
🇻🇳 VN Socket
accept(220V)
// Old payment API
legacyPay.processCC(cardNum, amount)

// Adapter → new interface
class PaymentAdapter {
  pay(method, amount) { // new interface
    legacy.processCC(...) // gọi old API
  }
}
✅ Dùng khi
Tích hợp thư viện third-party với interface khác. Reuse legacy code mà không sửa nó.
❌ Không dùng khi
Có thể sửa trực tiếp source code. Thêm Adapter chỉ tạo thêm complexity không cần.
Decorator — Thêm behavior mà không sửa class gốc
Wrap object với layers để thêm chức năng. Như gói quà — bên trong không đổi, bên ngoài thêm giấy gói, nơ, hộp...
LoggingDecorator
CachingDecorator
AuthDecorator
UserService
NestJS @UseGuards, @UseInterceptors là Decorator pattern!
Facade — Giao diện đơn giản cho hệ thống phức tạp
Remote TV = Facade cho hàng trăm mạch điện phức tạp bên trong. Người dùng chỉ cần biết nút ON/OFF.
🎬 OrderFacade
placeOrder(cart)
→
PaymentService.charge()
InventoryService.reserve()
ShippingService.create()
EmailService.confirm()
🎯 Key Takeaway
  • Adapter: "kết nối" hai thứ không tương thích
  • Decorator: thêm chức năng mà không sửa code gốc
  • Facade: đơn giản hóa interface cho hệ thống phức tạp
Behavioral Patterns
Giao Tiếp Giữa Objects
Cách các objects giao tiếp, chia sẻ trách nhiệm và thực hiện hành động.
Strategy — Swap thuật toán lúc runtime
Định nghĩa một family of algorithms, đóng gói từng cái, và làm chúng interchangeable.
🛒 SortContext
Đang dùng: Bubble Sort
🫧 Bubble Sort
O(n²)
⚡ Quick Sort
O(n log n)
🔀 Merge Sort
O(n log n)
Click để swap strategy — context code không thay đổi!
Observer — Đăng ký và nhận thông báo
Giống đăng ký báo — khi có số mới, toà soạn tự gửi cho tất cả subscribers.
📰 EventBus — "order.created"
📧 EmailService
subscriber
📊 Analytics
subscriber
📦 Inventory
subscriber
Command — Đóng gói action thành object
Biến request thành object độc lập. Cho phép queue, log, và undo operations.
User clicks Ctrl+Z
→
Command Stack
[DeleteCmd] ← top
[InsertCmd]
[MoveCmd]
→
DeleteCmd.undo()
→ restore deleted text
Undo/Redo, Job Queue, Transaction log — tất cả dùng Command pattern
🎯 Key Takeaway
  • Strategy: khi cần thay đổi algorithm linh hoạt
  • Observer: khi một event cần thông báo cho nhiều consumers
  • Command: khi cần queue, undo, hoặc log operations
Anti-Patterns
Khi Nào KHÔNG Dùng Patterns
Pattern áp dụng sai chỗ còn tệ hơn không có pattern. Over-engineering là vấn đề phổ biến nhất.
⚠️ Over-Engineering Trap
Junior dev sau khi học Design Patterns thường có xu hướng áp dụng mọi lúc mọi nơi:
❌ Factory cho 1 loại object
Dùng Factory khi chỉ tạo UserObject → needless complexity
❌ Singleton cho mọi thứ
Global state = testability nightmare. NestJS DI đã handle việc này.
❌ Observer cho simple data flow
Gọi function trực tiếp rõ ràng hơn event chain khó trace.
❌ Builder cho 2-3 params
new User(email, name) đơn giản hơn UserBuilder().setEmail().setName().build()
Rule of Three
Chỉ áp dụng pattern khi bạn thấy cùng vấn đề 3 lần. Lần đầu — giải thẳng. Lần hai — ghi chú. Lần ba — refactor với pattern.
✅ Checklist trước khi dùng Pattern
? Vấn đề này có thực sự phức tạp đến mức cần pattern không?
? Giải pháp đơn giản hơn có đủ không?
? Team có hiểu pattern này không?
? Trade-off của pattern này có chấp nhận được không?
