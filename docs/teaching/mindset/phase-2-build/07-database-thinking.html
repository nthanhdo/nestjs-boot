Tại sao cần Database?
Vấn Đề Của File Storage
Lưu data vào file hoạt động tốt cho một người. Nhưng sẽ sụp đổ ngay khi có nhiều người dùng cùng lúc.
💥 File Storage gặp vấn đề gì?
❌ Race Condition
User A và B cùng đọc balance=1000. A trừ 200, ghi lại 800. B trừ 300, ghi lại 700. Balance đúng phải là 500!
❌ Search chậm
Tìm user theo email → phải đọc toàn bộ file. 1M records = đọc 1M dòng mỗi lần tìm.
❌ Integrity
Không có way nào đảm bảo email là unique, hay quantity > 0, hay format đúng.
❌ Crash recovery
Server crash giữa chừng khi đang ghi → file corrupt, data mất một phần.
Database giải quyết tất cả những vấn đề này
ACID Transactions, Indexes, Constraints, WAL (Write-Ahead Logging) — database là software phức tạp được build để handle những vấn đề này một cách reliable.
🎯 Key Takeaway
  • Database = file system + concurrency + search + integrity + recovery
  • Hiểu vấn đề nó giải quyết → mới hiểu tại sao ACID quan trọng
  • JSON file là DB đơn giản nhất — SQLite là bước tiếp theo

Khái niệm 02
Normalization
Chuẩn hóa database để tránh data trùng lặp và update anomalies.
❌ Unnormalized: Mọi thứ trong 1 bảng

Khái niệm 03
Index — Mục Lục Của Database
Index giống mục lục sách — thay vì đọc hết, bạn tra ngay vào trang cần.
🔍 Tìm email "z@mail.com" trong 1 triệu records
❌ Không có Index
SELECT * FROM users
WHERE email = 'z@mail.com'
→ Full Table Scan: đọc 1,000,000 rows
→ Thời gian: ~500ms
✅ Có Index trên email
CREATE INDEX idx_email
ON users (email)
→ B-tree lookup: ~20 nodes
→ Thời gian: ~1ms
B-Tree Index — Simplified
m
f
s
a-e
g-l
n-r
z@…
Tìm 'z' → đi phải (>m) → đi phải (>s) → found! Chỉ 3 bước thay vì 1M bước.
Index Trade-off
Index tăng tốc READ nhưng làm chậm WRITE (phải cập nhật index khi insert/update). Đừng index mọi column — chỉ index những column thường được query/filter.
🎯 Key Takeaway
  • Luôn index FK columns (foreign keys)
  • Index columns thường xuất hiện trong WHERE, JOIN, ORDER BY
  • EXPLAIN ANALYZE để kiểm tra query có dùng index không

ACID & N+1 Problem
ACID đảm bảo data integrity. N+1 là bug phổ biến nhất khi làm việc với DB trong code.
💸 ACID — Chuyển tiền A→B, server crash giữa chừng

📤

💥
SERVER CRASH! Chưa cộng được vào B
↩️
ROLLBACK! Tài khoản A phục hồi về 1,000,000. Không mất tiền!

⚠️ N+1 Query Problem
Lấy 100 orders, mỗi order gọi thêm 1 query để lấy user. Kết quả: 1 + 100 = 101 queries!
0
queries
✅ Fix: JOIN hoặc eager load
// 1 query thay vì N+1
SELECT o.*, u.name
FROM orders o
JOIN users u ON o.user_id = u.id
→ 1 query, thay vì 101!
🎯 Key Takeaway
  • Dùng Transaction cho operations cần atomicity
  • N+1 hay xuất hiện khi dùng ORM + lazy loading
  • Detect N+1: đếm queries trong log, dùng query analyzer
Thực hành
Scale từ 100 → 10M Users
Mỗi level có challenges khác nhau. Click vào từng level để xem phải làm gì.
100 users
Simple setup
Single server, single DB. SQLite hoặc PostgreSQL. Không cần gì phức tạp. Tập trung vào features, không phải infra.
10K users
Add indexes + basic caching
Tạo index cho các queries chậm. Thêm Redis cache cho data ít thay đổi. Connection pooling. Bắt đầu monitor query performance.
1M users
Read replicas + CDN
Primary DB cho writes, Read Replicas cho reads (80-90% traffic thường là reads). CDN cho static assets. Horizontal scaling app servers. Queue cho heavy operations.
10M users
Sharding + Microservices
DB sharding theo user ID range hoặc hash. Tách services theo domain. Message queues (Kafka). Time-series DB cho metrics. Distributed cache (Redis Cluster). Đây là "Google scale" — hầu hết app không cần đến đây.
Bài học quan trọng nhất
Đừng over-engineer ngay từ đầu. Xây cho 100 users trước. Khi có vấn đề ở 10K users — fix. Mỗi optimization tốn chi phí, đừng trả chi phí trước khi cần.
