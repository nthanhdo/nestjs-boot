Khái niệm 01
API là gì?
API = Application Programming Interface. Cầu nối giữa hai phần mềm. API là contract — giống như Interface trong OOP Thinking (Bài 2): caller không cần biết implementation bên trong.
🍽️ Nhà hàng analogy
👤
Khách hàng
Frontend / App / Developer
→
📋
Menu (API)
Endpoint docs, request format, response format
→
🧁‍🍳
Bếp (Server)
Xử lý business logic, trả kết quả
Khách không cần vào bếp. Bếp không cần biết khách là ai. Menu = API contract.
🎯 Key Takeaway
  • API là interface, không phải implementation
  • Caller không biết và không cần biết server làm gì bên trong
  • Good API = consistent, predictable, well-documented
Khái niệm 02
HTTP — Ngôn Ngữ Của Web
HTTP là giao thức request/response. Client gửi request, server trả response. Mọi query trong Database (Bài 7) đều được trigger bởi HTTP request này.
🔄 Request/Response Flow
1
Client gửi HTTP Request
POST /api/users HTTP/1.1 Host: api.example.com Content-Type: application/json Authorization: Bearer eyJhbG... {"name": "Nguyễn A", "email": "a@mail.com"}
2
Server xử lý
→ Parse request body → Validate dữ liệu (Controller layer) → Business logic (Service layer) → Ghi vào database (Repository layer)
3
Server trả HTTP Response
HTTP/1.1 201 Created Content-Type: application/json {"id": "u_123", "name": "Nguyễn A", "createdAt": "2026-08-14T..."}
🎯 Key Takeaway
  • HTTP là stateless — mỗi request độc lập, server không nhớ request trước
  • Headers mang metadata: auth token, content type, caching hints
  • HTTPS = HTTP + TLS encryption — luôn dùng cho production
Khái niệm 03
REST — Cách Thiết Kế API
REST là convention để thiết kế API nhất quán. Resources = nouns, HTTP methods = verbs. API layer là Presentation Layer trong Layered Architecture (Bài 6).
🔗 REST Resource Mapping
MethodURLActionBody
GET/usersLấy danh sách users–
GET/users/:idLấy 1 user–
POST/usersTạo user mớiJSON
PUT/users/:idUpdate toàn bộ userJSON
PATCH/users/:idUpdate một phần userJSON
DELETE/users/:idXóa user–
REST URL Best Practices
✅ /users · /orders/:id/items
❌ /getUsers · /createOrder
🎯 Key Takeaway
  • URL = resource (noun), Method = action (verb)
  • Plural nouns: /users, /orders, /products
  • Nested: /orders/:id/items → items của order cụ thể
Khái niệm 04
HTTP Status Codes
Status code là cách server "nói chuyện" với client về kết quả request. Phải dùng đúng!
✅ 2xx — Thành công
200
OK — Request thành công
201
Created — Tạo mới thành công
204
No Content — Success, không có data
↪️ 3xx — Redirect
301
Moved Permanently
302
Found — Redirect tạm thời
304
Not Modified — Dùng cache
❌ 4xx — Lỗi từ Client
400
Bad Request — Dữ liệu sai
401
Unauthorized — Chưa đăng nhập
403
Forbidden — Không có quyền
404
Not Found
422
Unprocessable — Validation error
429
Too Many Requests — Rate limit
💥 5xx — Lỗi từ Server
500
Internal Server Error
502
Bad Gateway — Upstream error
503
Service Unavailable
Lỗi phổ biến về Status Code
❌ Return 200 với body {"success": false, "error": "..."}
✅ Return 400/404/422 đúng → Frontend dễ handle, monitoring alert đúng

401 vs 403: "Ai vậy?" (401) vs "Biết anh là ai, nhưng không cho vào" (403)
🎯 Key Takeaway
  • Dùng status code semantically đúng — không phải mọi thứ là 200
  • 4xx = lỗi của client (họ cần sửa request)
  • 5xx = lỗi của server (chúng ta cần fix)
Khái niệm 05 + 06
Authentication & Pagination
JWT authentication flow và cách xử lý large datasets. Queries phía sau pagination chính là những gì bạn học ở Database (Bài 7).
🔐 JWT Authentication Flow
👤 Client: POST /auth/login

🔐 Server: verify credentials → tạo JWT

Authorization: Bearer eyJhbG...

🔐 Server verify signature → biết user là ai → cho phép
JWT = 3 phần: Header (algo) + Payload (user data) + Signature (verify). Payload không bị mã hóa — chỉ signed. Đừng lưu secret trong JWT.

  • Luôn set token expiry (accessToken 15m, refreshToken 7d)
  • Pagination: tất cả list endpoint đều cần limit/page — không return all
Khái niệm 07 + 08
Validation & API Contract
Validate input sớm. Treat API spec như hợp đồng — giống Interface trong OOP (Bài 2). API là cầu nối giữa Architecture layers (Bài 6) và Database queries (Bài 7).
✅ Validation — Fail Fast
❌ Không validate sớm
POST /orders {"productId": "abc", "qty": -5} → Service gọi DB → DB gọi payment → Crash ở payment → Error message mơ hồ
✅ Validate ở Controller
POST /orders {"productId": "abc", "qty": -5} → Validate ở Controller → 422 Unprocessable: {"errors": [ "qty must be > 0" ]}

API Versioning
Khi cần thay đổi API breaking → tạo version mới: /api/v1/users → /api/v2/users. Giữ v1 chạy cho client cũ, migrate dần.
🏆 Tổng kết Bài 08 & Phase 2
  • API: interface giữa hai systems, không lộ implementation
  • HTTP: stateless request/response với method + status code
  • REST: resources (nouns) + HTTP methods (verbs)
  • Status codes: dùng semantically đúng
  • JWT: stateless auth, verify bằng signature
  • Validation: fail fast ở Controller
  • Contract: spec trước khi code — FE và BE song song

🌀 Dễ Ex 1: Thiết kế REST endpoints cho Blog (Post, Comment, Like) ▼
Thiết kế đầy đủ REST endpoints cho Blog system với: Posts (CRUD), Comments (nested), Likes (toggle). Follow REST conventions.
Giải
Posts: GET /posts → list (paginated) GET /posts/:id → single post POST /posts → create (auth required) PUT /posts/:id → full update (owner only) PATCH /posts/:id → partial update DELETE /posts/:id → delete (owner/admin) Comments (nested resource): GET /posts/:id/comments → list comments POST /posts/:id/comments → add comment (auth) DELETE /posts/:id/comments/:commentId → delete Likes (toggle pattern): POST /posts/:id/likes → like (idempotent) DELETE /posts/:id/likes → unlike Bonus — useful filters: GET /posts?author=userId&tag=nestjs&page=1&limit=20
🌀 Dễ Ex 2: Map HTTP status code đúng cho 10 tình huống ▼
Chọn status code đúng cho: (1) User created, (2) Login wrong password, (3) User not found, (4) Validation failed, (5) Server crash, (6) No auth token, (7) No permission, (8) Rate limited, (9) Success delete, (10) Redirect.
Giải
1. User created → 201 Created 2. Wrong password → 401 Unauthorized 3. User not found → 404 Not Found 4. Validation failed → 422 Unprocessable Entity 5. Server crash → 500 Internal Server Error 6. No auth token → 401 Unauthorized 7. No permission → 403 Forbidden 8. Rate limited → 429 Too Many Requests 9. Success delete → 204 No Content 10. Redirect → 301 (permanent) or 302 (temp)
🌁 Trung bình Ex 3: Thiết kế pagination + filtering + sorting cho GET /products ▼
Thiết kế query parameters + response schema cho endpoint GET /products với: cursor/offset pagination, multi-field filter, sort by nhiều field, response kèm metadata.
Giải
Request: GET /products ?page=2&limit=20 // offset pagination &category=electronics // filter &minPrice=100&maxPrice=500 &inStock=true &sortBy=price,name // multi-field sort &order=asc,desc Response schema: { "data": [...products], "meta": { "page": 2, "limit": 20, "total": 156, "totalPages": 8, "hasNext": true, "hasPrev": true } } // Cursor pagination (better for large datasets): GET /products?cursor=eyJpZCI6MTIzfQ==&limit=20 Response: { "data": [...], "nextCursor": "eyJpZCI6MTQzfQ==" }
🌁 Trung bình Ex 4: Viết validation rules cho registration form (class-validator style) ▼
Viết DTO với class-validator decorators cho registration form: name, email, password, confirmPassword, age (optional), role.
Giải — NestJS DTO
import { IsEmail, IsString, MinLength, MaxLength, IsInt, Min, Max, IsEnum, IsOptional, Matches } from 'class-validator'; import { Match } from './match.decorator'; // custom export class RegisterDto { @IsString() @MinLength(2) @MaxLength(50) name: string; @IsEmail() email: string; @IsString() @MinLength(8) @Matches(/^(?=.*[A-Z])(?=.*[0-9])/, { message: 'Password must have uppercase + number' }) password: string; @Match('password', { message: 'Passwords must match' }) confirmPassword: string; @IsOptional() @IsInt() @Min(13) @Max(120) age?: number; @IsEnum(['user', 'seller']) role: 'user' | 'seller'; }
🔴 Khó Ex 5: API Versioning — thiết kế v1 → v2 migration strategy ▼
API v1 trả về user object với field "name". v2 cần tách thành "firstName" và "lastName". Thiết kế migration strategy không breaking client v1, và viết NestJS controller cho cả 2 versions.
Migration Strategy
// Strategy: URL versioning + backward compatibility // NestJS controllers @Controller('v1/users') export class UsersV1Controller { @Get(':id') async getUser(@Param('id') id: string) { const user = await this.usersService.findById(id); return { id: user.id, name: user.name, // legacy: full name email: user.email, }; } } @Controller('v2/users') export class UsersV2Controller { @Get(':id') async getUser(@Param('id') id: string) { const user = await this.usersService.findById(id); const [firstName, ...rest] = user.name.split(' '); return { id: user.id, firstName, lastName: rest.join(' ') || null, // new fields email: user.email, }; } } // Migration timeline: // Month 1: Launch v2, keep v1, add deprecation header: // Deprecation: true // Sunset: Mon, 1 Jan 2027 00:00:00 GMT // Month 6: Warn all v1 clients via email + docs // Month 12: Sunset v1, return 410 Gone
