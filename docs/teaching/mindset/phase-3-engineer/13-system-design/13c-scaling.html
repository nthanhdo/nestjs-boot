Scaling Strategies

Vertical vs horizontal scaling, load balancing algorithms, and DB replication patterns.

Vertical vs Horizontal Scaling

⬆️ Vertical Scaling (Scale Up)

  • Add CPU/RAM/disk to existing server
  • Simple — no code changes
  • Hard ceiling — biggest machine available
  • SPOF — one machine = one failure point
  • Downtime during upgrade
  • Best for: DBs (complex to shard), initial growth

↔️ Horizontal Scaling (Scale Out)

  • Add more servers (nodes)
  • Complex — needs load balancer, stateless app
  • No hard ceiling — add more machines
  • No SPOF — failure of one node ≠ outage
  • Zero downtime with rolling deploys
  • Best for: stateless API servers, CDN nodes

Rule: vertical first (simpler), horizontal when you hit the ceiling or need HA.

DB Replication

# Primary-Replica (Leader-Follower)
# Writes go to primary, replicated async to replicas
# Reads can go to any replica → scales read throughput

// NestJS with read/write split (TypeORM example)
@Module({
  imports: [
    TypeOrmModule.forRoot({
      replication: {
        master: { host: 'primary-db' },
        slaves: [
          { host: 'replica-1' },
          { host: 'replica-2' },
        ]
      }
    })
  ]
})

# Trade-off: async replication = replication lag
# "Read your own writes" problem: write to primary,
# immediately read from replica that hasn't caught up yet
# Solution: read from primary for recent writes, replica for others

🔬 Exercise — Scaling Decision

  1. Your API handles 2,000 QPS on 1 server (4 CPU, 8GB RAM). CPU is at 90%. What do you do first?
  2. Your DB read QPS is 8,000. A single replica can do 2,000 QPS. How many replicas do you need?
  3. A user logs in (session stored on Server 1). Next request goes to Server 2 via round-robin. What problem occurs and how do you fix it?
  4. You add a 4th server to the pool. A user who was doing a file upload gets their request routed to the new server mid-upload. What breaks?

Key Takeaways

  • Vertical scaling is simpler but has a ceiling — start here
  • Horizontal scaling requires stateless servers — session state must be external (Redis)
  • Round-robin = simple and effective for equal-cost stateless requests
  • DB replication scales reads, not writes — the primary is still the write bottleneck
  • Replication lag is real — design for eventual consistency or route critical reads to primary
