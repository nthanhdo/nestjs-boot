Engineering Workflow

Từ Requirement đến Deploy — quy trình làm việc của một Professional Engineer trong môi trường team thực tế.

1. Full Engineering Cycle

Một engineer không chỉ "viết code" — mà đi qua một cycle đầy đủ với mỗi task. Hiểu cycle = không bị lost trong project thực tế.

📋
Require-ment
Đọc spec kỹ. Identify ambiguities. List câu hỏi cần hỏi.
🧠
Under-stand
Hiểu "tại sao" feature này tồn tại, không chỉ "cái gì".
❓
Ask
Hỏi trước khi implement. "Better to ask stupid question than code stupid thing."
🏗️
Design
Schema, API contract, architecture. Viết ra trước khi code.
⏱️
Estimate
T-shirt sizing: XS/S/M/L/XL. Buffer 30-50% cho unknown.
⌨️
Implement
Small commits. Feature branches. Follow conventions.
🧪
Test
Unit + integration + manual. Test edge cases trước khi PR.
👀
Review
Tự review trước. Gửi PR với description đầy đủ.
🚀
Deploy
CI/CD green → deploy staging → verify → production.
📊

Check logs, metrics 24h sau deploy. Không rời đi ngay.

2. Requirement Reading — Đọc Spec Đúng Cách

Đọc spec không phải "scan qua" — mà là active reading với checklist câu hỏi.

Checklist khi đọc một ticket/spec

  • ①"Tại sao?" — Business value là gì? User problem thực sự là gì?
  • ②"Ai dùng?" — User role nào? Permissions cần gì?
  • ③"Edge cases?" — Empty state, error state, boundary values
  • ④"Dependencies?" — Cần API nào? Cần data gì từ đâu?
  • ⑤"Definition of Done?" — Khi nào thì task này được coi là xong?
  • ⑥"Non-functional?" — Performance, security, logging requirements?
Rule của Senior Engineer: Không bao giờ bắt đầu code khi còn câu hỏi chưa được trả lời. "Hỏi trước mất 5 phút. Implement sai mất 2 ngày."

3. Task Breakdown — Chia Nhỏ Vấn Đề

Kỹ năng chia task nhỏ = kỹ năng tư duy của engineer. Task nhỏ = dễ estimate, dễ track, dễ review.

Rule: Nếu một task mất > 1 ngày → chia nhỏ hơn. Task tốt nhất = hoàn thành trong 2-4h và có thể describe trong 1 câu.

4. Estimation — T-shirt Sizing

Không ai estimate chính xác 100%. Mục tiêu = đủ để plan sprint và detect khi vượt scope.

XS
< 2 giờ
Config thay đổi, typo fix, comment update
S
2–4 giờ
Simple endpoint, single field validation
M
1–2 ngày
Feature với logic + test, simple integration
L
3–5 ngày
Complex feature, nhiều services, cần design
XL
> 1 tuần
System redesign → nên chia thành L tasks

Estimation formula

// Estimate = Optimistic + Buffer + Risk base = thời gian nếu mọi thứ suôn sẻ (4h) buffer = unknown/integration issues (+50%) (2h) risk = dependency / unclear spec (+20%) (1h) ───────────────────────────────────────────── total = 7h → estimate "1 ngày" (working day)

5. Agile / Scrum Basics

Sprint = chu kỳ 2 tuần. Team commit vào một set of tasks, deliver vào cuối sprint.

Sprint Planning
Chọn tasks từ backlog vào sprint. Estimate + commit.
Daily Standup
15 phút. 3 câu: làm gì hôm qua? hôm nay? blocked gì?
Sprint Review
Demo những gì hoàn thành. Stakeholder feedback.
Retrospective
Làm tốt gì? Cải thiện gì? Action items cụ thể.

6. Code Review — Nhìn Gì, Nói Gì

Code review không phải "tìm lỗi" — mà là collaborative quality check và knowledge transfer.

Khía cạnhReviewer nhìn gìComment constructive
Correctness Logic đúng không? Edge case handle không? "What happens when userId is null here?"
Security Input validated? Auth checked? Injection possible? "This query should use parameterized form to prevent injection."
Readability Code tự giải thích không? Naming clear? "Could we rename 'x' to 'userCount' for clarity?"
Performance N+1 query? Missing index? Unnecessary loop? "This calls DB inside loop — consider batch query."
Tests Test cases đủ không? Edge case có test? "Missing test for empty array input."
Tránh: "This is wrong." | "Bad code." | "This is ugly."
Thay bằng: Explain tại sao, suggest alternative, dùng "nit:" prefix cho minor issues.

7. Technical Discussion — RFC Format

Khi propose một technical change lớn → viết RFC (Request for Comments) để team review trước khi implement.

📄
RFC: Switch từ REST sang GraphQL cho Public API
DRAFT
Context
Mobile client hiện tại over-fetching data → performance issues. 3 endpoints khác nhau cho cùng user data.
Proposal
Migrate public API sang GraphQL. Keep REST cho internal services. Sử dụng Apollo Server + code-first approach.
Trade-offs
Pros: flexible queries, type safety, single endpoint.
Cons: learning curve, N+1 problem nếu không có DataLoader, caching phức tạp hơn.
Alternatives Considered
1. BFF pattern với REST — giữ REST nhưng thêm Backend-for-Frontend layer.
2. OpenAPI với sparse fieldsets — simpler nhưng ít flexible.
Decision needed by
2026-08-20. Request: feedback on trade-off #3 (caching strategy).

8. Communication — Explain to the Right Audience

💬 Giải thích cho non-technical (PM, Designer)
"Feature này cần lưu thêm thông tin về lịch sử đơn hàng. Khi user nhìn vào profile, họ thấy được mọi order từ trước đến nay. Mất khoảng 2 ngày để xây."
💬 Giải thích cho Senior Engineer (Design Review)
"Sẽ thêm OrderHistory collection trong MongoDB với TTL index 90 ngày. API GET /users/:id/orders với cursor-based pagination, limit 20. Event-driven: OrderPlaced → append to history. Estimate 2 days bao gồm integration tests."
Skill quan trọng: Đọc audience → calibrate technical depth → luôn kết thúc với "action item" hoặc "decision needed". Không để meeting end với ambiguity.

🎯 Exercise: Feature Breakdown + Estimate

Feature request: "Thêm hệ thống notification — user nhận được email khi có order mới, order shipped, và order delivered. Admin có thể toggle từng loại notification."

  • ①Đọc spec → list 5+ câu hỏi cần hỏi trước khi code
  • ②Chia thành sub-tasks với T-shirt size cho từng task
  • ③Identify dependencies — task nào phải xong trước?
  • ④Tính total estimate với buffer
  • ⑤Viết 1 RFC ngắn: approach, trade-offs, alternatives
  • ⑥Practice: giải thích feature cho "PM" (bạn cùng nhóm) trong 2 phút
Key Takeaway: Engineer giỏi dành 40% thời gian trước khi code: đọc, hỏi, design, estimate. Code nhanh không phải là engineer giỏi — deliver đúng mới là engineer giỏi.
