🔵🟣 Venn Diagram: Sweet Spot

Rule: Feature chỉ solve business problem → không sustainable (user churn). Chỉ solve user problem → company không tồn tại để serve users. Feature tốt nhất = solve cả hai đồng thời.

❓ 5 Whys — Tìm Real Problem

Hỏi "tại sao" 5 lần để uncover root cause thay vì implement symptom.

Hỏi 1:
"Tại sao user muốn export CSV?"
→ "Để gửi cho manager hàng tuần."
Hỏi 2:
"Tại sao gửi bằng CSV, không phải trong app?"
→ "Manager dùng Excel để tổng hợp nhiều report từ nhiều nguồn."
Hỏi 3:
"Tại sao không tổng hợp trong app?"
→ "App không có view cross-account hoặc multi-period comparison."
Kết luận:
Real problem = thiếu consolidated reporting view
Giải pháp tốt hơn: aggregation dashboard → 10x giá trị hơn CSV export

🗝️ 5 Câu Hỏi Trước Khi Build

①
"Tại sao cần feature này?"
Understand the "why" trước khi implement "how". Tránh build wrong thing đúng cách.
②
"Problem thực sự là gì?"
User request ≠ user need. "Cần thêm faster horse" → thực ra cần xe hơi.
③
"Ai sẽ dùng? Bao nhiêu người?"
Scale ảnh hưởng design. 10 users vs 10 triệu users = different architecture decisions.
④
"Thành công trông như thế nào?"
Define metric trước khi build. Nếu không define → sau khi ship không biết có work hay không.
⑤
"Nếu không build, điều gì xảy ra?"
Đôi khi câu trả lời là "không sao" → giúp deprioritize đúng và ship faster ở chỗ khác.
🎯 Bài Tập Thực Hành
🟢 DễBài 1
Phân loại: User Problem hay Business Problem?
Phân loại từng item sau: (1) "App chậm khi load" (2) "Conversion rate thấp" (3) "Khó tìm sản phẩm" (4) "Churn rate cao" (5) "Form đăng ký quá dài" (6) "Không có upsell flow". Một số có thể là cả hai.
1. App chậm → User problem (UX) + Business (bounce rate↑ → revenue↓)
2. Conversion rate thấp → Business problem (nhưng cần diagnose: UX issue? trust issue? pricing?)
3. Khó tìm sản phẩm → User problem → có business impact (abandonment rate↑)
4. Churn rate cao → Business problem → symptom của user problem cần investigate
5. Form đăng ký quá dài → User problem → business impact (signup rate↓)
6. Không có upsell flow → Business problem (revenue) — user-neutral nếu done right

Key insight: Business problems thường là symptoms của user problems không được solved
🟡 Trung bìnhBài 2
5 Whys: feature "Add forgot password" → tìm real problem
Pair với một bạn: một người đóng vai user vừa request "forgot password feature". Người kia hỏi 5 whys để tìm xem real problem là gì và liệu forgot password có phải solution tốt nhất không.
5 Whys mẫu:
Why? "Tôi thường xuyên quên mật khẩu"
Why? "Mỗi site tôi dùng password khác nhau"
Why? "Vì sợ security breach"
Why? "Đã bị hack 2 lần từ dùng cùng 1 password"

Real problem: user cần password management, không phải forgot-password flow.
Better solutions: (1) OAuth login (Google/GitHub) eliminates password entirely, (2) Magic link login, (3) Forgot password là tactical fix, không giải quyết root cause

Exercise insight: đôi khi feature được request không phải solution tốt nhất cho real problem
🔴 KhóBài 3
Phân tích feature request từ Sweet Spot perspective
Feature request: "Thêm social features: user có thể follow nhau, share todo lists, và comment trên task của người khác." Phân tích: (1) User problem thực sự là gì? (2) Business problem là gì? (3) Feature này có nằm trong sweet spot không? (4) Recommend: build, defer, hay reject?
Phân tích:
User problem: "Muốn collaborate với team trên tasks" → nhưng đã có apps chuyên (Notion, Asana)
Business problem: Tăng engagement, virality (social = viral loops). Nhưng mission của app là gì — cá nhân hay nhóm?

Sweet spot check:
- User problem: MAYBE (nếu codebase đang target teams)
- Business value: YES nếu team tier có pricing
- Technical cost: XL — auth cho shared resources, real-time, notification, moderation
→ Có thể không phải sweet spot vì cost/value ratio xấu

Recommendation: DEFER — research first. Survey 50 users: "Do you need collaboration?", "Would you pay for it?". Nếu >40% confirm với willingness to pay → design minimal version (just share, no comment/follow). Re-estimate sau research.

📌 Tóm Tắt — User Problem

  • Product Engineer hỏi "tại sao" trước khi code, theo dõi metrics sau khi ship
  • Sweet spot = giao điểm User Problem + Business Problem. Build features ở đây
  • 5 Whys = hỏi "tại sao" 5 lần để uncover real problem, không chỉ symptom
  • 5 câu hỏi = tại sao, real problem, ai dùng, thành công là gì, nếu không build thì sao
  • User request ≠ user need — always dig deeper trước khi implement
