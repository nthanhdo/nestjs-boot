Documentation

Doc tốt = explain cho engineer khác mà không cần ngồi cạnh. Không doc = technical debt không nhìn thấy được.

1. Tại Sao Docs Quan Trọng?

❌ Không có Doc

  • Onboard member mới mất 2-3 tuần
  • Mỗi lần debug phải đọc toàn bộ code
  • PM không biết API có gì để plan feature
  • "Chỉ mình tôi biết phần này" → knowledge silo
  • 6 tháng sau chính mình không nhớ code viết gì

✅ Có Doc tốt

  • Onboard trong 2-3 ngày
  • Debug bắt đầu từ troubleshooting guide
  • PM tự query API docs khi cần
  • Team member thay thế được nhau
  • 6 tháng sau extend feature dễ dàng

2. README Anatomy

README là "front door" của project. Bất kỳ developer nào clone repo cần biết ngay: đây là gì, cách chạy, cách contribute.

📄 README.md — Anatomy of a Good README
🏷️ Project Title + One-liner MUST
Tên project và giải thích trong 1 câu. Ai đọc 10 giây biết đây là gì.
# OrderService — REST API quản lý orders cho e-commerce platform
🚀 Quick Start MUST
Copy-paste commands để chạy project lần đầu. Không assume prior knowledge.
git clone → npm install → cp .env.example .env → npm run dev
📋 Prerequisites MUST
Node v20+, Docker, MongoDB. Version cụ thể, không viết "latest".
🏗️ Architecture Overview SHOULD
Diagram hoặc mô tả ngắn về structure: folder layout, key modules, data flow.
📖 API Reference (link) SHOULD
Link tới Swagger UI hoặc Postman collection. Không viết inline — quá dài.
🧪 Running Tests SHOULD
npm test, npm run test:e2e. Kết quả expected là gì.
🤝 Contributing Guide MAY
Branch naming, commit convention, PR process cho open-source projects.
📄 License MAY
MIT, Apache 2.0, proprietary — quan trọng cho open-source.

4. Architecture Diagrams — C4 Model

C4 Model cung cấp 4 levels of abstraction — từ high-level (business) đến low-level (code). Mỗi audience cần một level khác nhau.

C1
Context — "System trong ecosystem"
System của bạn + external users + external systems. PM, stakeholder xem level này.
User → [E-commerce App] → [Payment Gateway] + [Email Service]
C2
Container — "Technical components"
Các container chạy được: web app, API, database, message queue. Tech Lead xem level này.
[Web App] → [API Server] → [MongoDB] + [Redis]
C3
Component — "Modules inside container"
Modules/services bên trong một container. Developer xem level này khi onboard.
API Server: [AuthModule] [OrderModule] [NotificationModule]
C4
Code — "Class/function level"
UML class diagram. Thường auto-generated, chỉ dùng khi cần explain complex logic.
OrderService → OrderRepository → MongooseModel

7. ADR — Architecture Decision Records

ADR document tại sao một quyết định kỹ thuật được đưa ra. 6 tháng sau, không ai nhớ context — ADR giải quyết điều đó.

ADR-001
Sử dụng MongoDB thay vì PostgreSQL
Accepted
Context
Product catalog có flexible schema — mỗi category có attributes khác nhau. Team quen NoSQL hơn SQL. Scale read-heavy.
Decision
Dùng MongoDB với Mongoose. Collection per entity. Indexes trên frequently-queried fields.
Consequences
✓ Flexible schema cho product attributes
✓ Team ramp-up nhanh hơn
✗ No ACID transactions → cần xử lý manually với sessions
✗ Complex joins phải handle ở application layer
Date & Author
2026-08-14 — Nguyen Van A (Tech Lead)

8. Troubleshooting Guide

Format: "Nếu X xảy ra → check Y → fix Z". Engineer mới có thể tự debug mà không cần hỏi senior.

🔴 App crash với "MongoServerError: Authentication failed"
↓
🔍 Check
  • MONGO_URI trong .env đúng không?
  • MongoDB đang chạy? (docker ps)
  • Username/password match DB config
🔧 Fix
  • cp .env.example .env → điền lại
  • docker-compose up -d mongo
  • Check docker logs mongo
🔴 API trả về 401 mặc dù đã login
↓
🔍 Check
  • Header: Authorization: Bearer {token}
  • Token đã expire? (check exp claim)
  • JWT_SECRET match giữa env và code
🔧 Fix
  • Login lại để get fresh token
  • Verify JWT_SECRET env variable
  • Check token ở jwt.io

🎯 Exercise: Write Real Documentation

Cho project NestJS simple (User + Auth + Orders)

  • ①Viết README đầy đủ với Quick Start, Prerequisites, và Architecture
  • ②Add Swagger decorators vào 3 endpoints — verify tại /api/docs
  • ③Vẽ ERD cho Users + Orders + Products (dùng draw.io hoặc text-based)
  • ④Viết 1 ADR cho một decision bạn đã đưa ra trong project
  • ⑤Vẽ Sequence Diagram cho flow login (User → FE → BE → DB)
  • ⑥Viết Troubleshooting Guide cho 3 common errors trong project
Key Takeaway: Documentation không phải "việc cuối cùng sau khi xong feature". Viết README trước khi code (README-Driven Development), viết ADR khi đưa ra decision, update docs khi thay đổi API. Docs outdated còn tệ hơn không có docs.
