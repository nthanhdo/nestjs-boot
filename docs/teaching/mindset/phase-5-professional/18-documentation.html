Documentation

Doc tốt = explain cho engineer khác mà không cần ngồi cạnh. Kết hợp với Architecture diagrams (Bài 6) và API knowledge (Bài 8). Không doc = technical debt không nhìn thấy được.

1. Tại Sao Docs Quan Trọng?

❌ Không có Doc

  • Onboard member mới mất 2-3 tuần
  • Mỗi lần debug phải đọc toàn bộ code
  • PM không biết API có gì để plan feature
  • "Chỉ mình tôi biết phần này" → knowledge silo
  • 6 tháng sau chính mình không nhớ code viết gì

✅ Có Doc tốt

  • Onboard trong 2-3 ngày
  • Debug bắt đầu từ troubleshooting guide
  • PM tự query API docs khi cần
  • Team member thay thế được nhau
  • 6 tháng sau extend feature dễ dàng

2. README Anatomy

README là "front door" của project. Bất kỳ developer nào clone repo cần biết ngay: đây là gì, cách chạy, cách contribute.

📄 README.md — Anatomy of a Good README
🏷️ Project Title + One-liner MUST
Tên project và giải thích trong 1 câu. Ai đọc 10 giây biết đây là gì.
# OrderService — REST API quản lý orders cho e-commerce platform
🚀 Quick Start MUST
Copy-paste commands để chạy project lần đầu. Không assume prior knowledge.
git clone → npm install → cp .env.example .env → npm run dev
📋 Prerequisites MUST
Node v20+, Docker, MongoDB. Version cụ thể, không viết "latest".
🏗️ Architecture Overview SHOULD
Diagram hoặc mô tả ngắn về structure: folder layout, key modules, data flow.
📖 API Reference (link) SHOULD
Link tới Swagger UI hoặc Postman collection. Không viết inline — quá dài.
🧪 Running Tests SHOULD
npm test, npm run test:e2e. Kết quả expected là gì.
🤝 Contributing Guide MAY
Branch naming, commit convention, PR process cho open-source projects.
📄 License MAY
MIT, Apache 2.0, proprietary — quan trọng cho open-source.

4. Architecture Diagrams — C4 Model

C4 Model cung cấp 4 levels of abstraction — từ high-level (business) đến low-level (code). Mỗi audience cần một level khác nhau.

C1
Context — "System trong ecosystem"
System của bạn + external users + external systems. PM, stakeholder xem level này.
User → [E-commerce App] → [Payment Gateway] + [Email Service]
C2
Container — "Technical components"
Các container chạy được: web app, API, database, message queue. Tech Lead xem level này.
[Web App] → [API Server] → [MongoDB] + [Redis]
C3
Component — "Modules inside container"
Modules/services bên trong một container. Developer xem level này khi onboard.
API Server: [AuthModule] [OrderModule] [NotificationModule]
C4
Code — "Class/function level"
UML class diagram. Thường auto-generated, chỉ dùng khi cần explain complex logic.
OrderService → OrderRepository → MongooseModel

7. ADR — Architecture Decision Records

ADR document tại sao một quyết định kỹ thuật được đưa ra. 6 tháng sau, không ai nhớ context — ADR giải quyết điều đó.

ADR-001
Sử dụng MongoDB thay vì PostgreSQL
Accepted
Context
Product catalog có flexible schema — mỗi category có attributes khác nhau. Team quen NoSQL hơn SQL. Scale read-heavy.
Decision
Dùng MongoDB với Mongoose. Collection per entity. Indexes trên frequently-queried fields.
Consequences
✓ Flexible schema cho product attributes
✓ Team ramp-up nhanh hơn
✗ No ACID transactions → cần xử lý manually với sessions
✗ Complex joins phải handle ở application layer
Date & Author
2026-08-14 — Nguyen Van A (Tech Lead)

8. Troubleshooting Guide

Format: "Nếu X xảy ra → check Y → fix Z". Engineer mới có thể tự debug mà không cần hỏi senior.

🔴 App crash với "MongoServerError: Authentication failed"
↓
🔍 Check
  • MONGO_URI trong .env đúng không?
  • MongoDB đang chạy? (docker ps)
  • Username/password match DB config
🔧 Fix
  • cp .env.example .env → điền lại
  • docker-compose up -d mongo
  • Check docker logs mongo
🔴 API trả về 401 mặc dù đã login
↓
🔍 Check
  • Header: Authorization: Bearer {token}
  • Token đã expire? (check exp claim)
  • JWT_SECRET match giữa env và code
🔧 Fix
  • Login lại để get fresh token
  • Verify JWT_SECRET env variable
  • Check token ở jwt.io

Viết README cho project cá nhân (template provided)
Dùng template sau để viết README cho một project của bạn: Title + One-liner / Badges (CI status) / Quick Start (3 commands) / Prerequisites với version cụ thể / Architecture overview / API reference link / Running tests / Contributing.
Template mẫu:

[![CI](badge-url)](actions-url)

## Quick Start
```bash
git clone https://github.com/user/project
npm install
cp .env.example .env # điền credentials

```

## Prerequisites

Test checklist: Đưa README cho người chưa biết project → họ có thể setup và chạy trong 10 phút không? Nếu không → README chưa đủ tốt
🟢 DễBài 2
Viết API docs cho 3 endpoints (Swagger format)
Chọn 3 endpoints trong project của bạn (ví dụ: POST /users, GET /users/:id, DELETE /users/:id). Viết đầy đủ: operation summary, request body schema, response schemas (200, 400, 401, 404), và add NestJS Swagger decorators vào code.
Checklist cho mỗi endpoint:
✓ @ApiOperation({ summary: '...' })
✓ @ApiBody({ type: CreateUserDto }) — nếu có body
✓ @ApiParam({ name: 'id', description: '...' }) — nếu có param
✓ @ApiResponse({ status: 201, type: UserResponseDto }) — success
✓ @ApiResponse({ status: 400, description: 'Validation failed' })
✓ @ApiResponse({ status: 401, description: 'Unauthorized' })
✓ @ApiResponse({ status: 404, description: 'User not found' })
✓ @ApiBearerAuth() — nếu cần auth

Verify: truy cập /api/docs → xem docs tự generate
🟡 Trung bìnhBài 3
Vẽ sequence diagram cho login flow
Vẽ sequence diagram đầy đủ cho flow: User nhập email+password → Frontend gửi request → Backend validate → Query DB → Verify bcrypt → Generate JWT → Response. Dùng draw.io, Mermaid.js, hoặc bản tay chụp ảnh.
Actors: User, Browser/Frontend, Backend API, Database

Sequence:
User → Browser: submit form {email, password}
Browser → API: POST /auth/login
API → DB: findOne({email})
DB → API: UserDocument | null
API: if null → throw UnauthorizedException
API: bcrypt.compare(password, user.hash)
API: if invalid → throw UnauthorizedException
API: jwt.sign({sub: user.id, role})
API → Browser: {accessToken, refreshToken}
Browser → User: redirect to dashboard

Tools: sequencediagram.org (text-based, nhanh nhất)
🟡 Trung bìnhBài 4
Viết ADR: chọn MongoDB vs PostgreSQL cho project
Viết một ADR (Architecture Decision Record) hoàn chỉnh document tại sao bạn chọn MongoDB (hoặc PostgreSQL) cho project của bạn. Phải có: Context, Decision, Consequences (✓ và ✗), Date và Author.
ADR template:
ADR-001: Sử dụng MongoDB thay vì PostgreSQL
Status: Accepted | Date: 2026-08-14

Context: Product catalog có flexible attributes mỗi category. Team quen NoSQL. Scale read-heavy workload.

Decision: MongoDB với Mongoose. Collection per entity. Indexes on frequently-queried fields.

Consequences:
✓ Flexible schema for catalog attributes
✓ Team ramp-up nhanh hơn
✗ Không có ACID transactions → cần MongoDB sessions cho multi-document ops
✗ Complex aggregations phải handle ở app layer

ADR tốt: 6 tháng sau đọc lại là hiểu ngay context và lý do
🔴 KhóBài 5
Full docs package: README + API docs + ERD + architecture diagram
Chọn một project (capstone project hoặc project cá nhân). Tạo đầy đủ: (1) README với Quick Start, (2) Swagger API docs cho ≥5 endpoints, (3) ERD với ít nhất 3 entities, (4) C4 Level 1+2 diagram. Đây là "documentation package" như trong môi trường thực tế.
Tools khuyến nghị:
README: Markdown trong GitHub
API docs: NestJS + @nestjs/swagger → /api/docs tự generate
ERD: dbdiagram.io (text-based, link shareable)
C4: structurizr.com hoặc draw.io với C4 template

Thứ tự làm:
1. ERD trước (define schema rõ ràng)
2. C4 C1 (system context trong 10 phút)
3. C4 C2 (containers: app, DB, cache, queue)
4. Swagger decorators trong code
5. README sau cùng (link tới 1,2,3,4)

Tiêu chí hoàn thành: Engineer mới có thể onboard project trong 30 phút chỉ bằng docs này

📌 Tóm Tắt Bài 18

  • README = front door của project. MUST: title, quick start, prerequisites. SHOULD: architecture, API link, tests
  • API docs = code-first với Swagger. Không viết tay — luôn outdated
  • C4 Model = 4 levels abstraction. PM xem C1, Tech Lead xem C2, Dev xem C3
  • Sequence diagram = best way to explain async flow và time-ordering
  • ERD = blueprint của database. Phải có trước khi code schema
  • ADR = document "tại sao" khi đưa ra architectural decision. 6 tháng sau vẫn hiểu
  • Docs outdated = tệ hơn không có docs. Update docs khi thay đổi code
Key Takeaway: Documentation không phải "việc cuối cùng sau khi xong feature". Viết README trước khi code (README-Driven Development), viết ADR khi đưa ra decision, update docs khi thay đổi API. Docs outdated còn tệ hơn không có docs.
